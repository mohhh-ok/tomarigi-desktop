# Turn verdicts

The speech bubble summary, the "?", and the anger mark come from the requests of each finished turn to the summary provider: one that answers all of them, and a second, narrow one that checks asking and writes the line (see the item on the second request below) (the user, on the first: 「それぞれのようやくにふぃーるどついかして、そのままこんしぇるじゅにわたしたらどうや」, 「いかりまーくもふぃーるどついかでいけるやろ？」). Before, the "?" and the anger mark came from TypeSafe's Jev, which mistook replies that only promised to ask later for questions (p=0.51 and 0.86–0.87 on the same day) and fed those to the concierge; Jev and TypeSafe were dropped (the user: 「やめよう」)

- One verdict per turn: a turn (session id and the time of its last reply) is asked about once, and its first answer is the one used. Answers are kept in the settings store (IndexedDB, the same place as the event log: kept across a reload and a restart), the last 200 turns, cut by count only, never by time, the oldest first; only answers are kept, so a request that failed is asked again after a reload or a restart (`src/lib/turn-verdict-store.ts`, `useTurnJudgements` in `src/perch/use-turn-judgements.ts`). Nothing is asked until the kept answers are loaded. (Claude's own decision, approved by the parent session.) Why: the answers were kept only in memory, so every reload asked about every turn on screen again. The dev app reloaded its page whenever an agent added or removed a worktree under `.claude` (the dev server watched it; it no longer does, README "Other notes"), and a restart does the same in every build. Haiku gave the same reply asking, asking, then not asking on three reloads, and the last answer replaced the earlier ones, so a session waiting on the user dropped out of the concierge (the user: 「コンシェルジュがはんのうしてない」). The first answer is used rather than asking several times and voting: asking again costs a request per turn and changes a "?" and a line the user has already seen; how often a reply is answered each way is measured with the regression test instead
- Input: the last reply (`assistantText`, last 2000 characters) and the user's messages sent since the previous turn ended. Both are untrusted input
  - The user's messages come first in the request, in the order things happened, and the prompt says they were all sent before the reply and count only for abusive. Before, a turn started by 「いいよ。」 (approving an earlier question) that ended with 「この 17 件を作ってよいですか。」 got asking no and continuing yes in 8 of 8 runs: the model read 「いいよ。」 as the answer, and the concierge's advice to reply was dropped (the user: 「こんしぇるじゅがはんのうしてない」; Claude's own decision)
- Output (one structured answer, the same schema for OpenAI / Anthropic / Local): the summary line, asking (yes / no), abusive (yes / no), and continuing (yes / no): whether work goes on after the turn: a job the session itself started (a measurement, export, build) is still running in the background, work it handed to another session or a chick is still going on, or the session says it will itself receive, check, or report a result later, e.g. "I'll check the report when it arrives and tell you" (the user, after the concierge said 「idle-renderが終わりました。計測結果を確認してください」 while that session's last reply said the measurement runs until 18:47: 「おk」 to Claude's proposal; for handed-off work, the user: 「子がすすめてるならcontinuingにすべきやとおもうんやが？」)
  - A request to choose or check something that hasn't been shown yet is asking later, not asking: the prompt tells the model to test whether the user can answer right now from the reply alone. Before, app-v's reply 「候補を最大 3 枚、ラベル付きで並べてお見せするので、1 枚選んでください。選んでいただくまで B 版は生成しません。…写真の候補が届いたら、すぐお見せします。」 got asking yes, and the concierge told the user to pick photo candidates that hadn't been shown (the user: 「コンシェルジュのはんのうがおかしい。べつせっしょんでちょうささせて」; Claude's own decision). Only adding that reply's shape as an example didn't help (1/8 and 4/8). Its continuing with OpenAI fell from 5/8 to 2/8 (Haiku 8/8 both); adding "showing something once it arrives is continuing" fixed that but brought back app-o's child case (continuing 3/8 and 6/8), so it was left out

  - A session that is watching (a linked session moves, or moved within the grace period and the session hasn't finished a turn since; see "Watching") is continuing, whatever the reply says. This comes from the app's own facts, the same for every provider, and covers a reply that only says the child still works or that relays another session's question next to a status list of other sessions' work. The reply's text still counts for work the app sees no link for, such as a child started in a terminal that hasn't sent or got a message yet (see "Watching"; a Claude desktop app child is linked from its start since commit 759d2b5, so it is no longer such a case) (`src/lib/turn-verdict.ts`, `sessionContinuing`)
  - continuing from the reply's text expires 30 minutes after the session last wrote to its transcript: past that, the session counts as finished (not continuing), so the concierge can suggest checking its result. continuing from watching is not touched: it already ends with the watching grace period. Before, a reply saying the session would go on once something arrived kept it working with no end: app-w waited 46 hours for its parent's result after its parent session had gone (the user, shown the 30 minutes as Claude's proposal: 「30min」). The 30 minutes is kept in one constant (`TEXT_CONTINUING_EXPIRES_MS` in `src/lib/turn-verdict.ts`)
  - For a Claude Code session, continuing from the reply's text also ends at once, before the 30 minutes, when nothing the app sees can start its next turn without the user (Claude's own decision, the parent session's choice; `wakeSourceOf` in `src/lib/session-wake.ts`, `wakeable` on the session). After a turn ends, a Claude Code session goes on only when something wakes it: a background command's or a chick's notification, a message from another session, or a wakeup it scheduled. So a reply that ends by saying what it will do next, with none of these left, has stopped, and the user has to tell it to go on or look at its result. What can wake it:
    - a background command started with `run_in_background` that has no completion notification yet (the ledger used for the done readout, under `BACKGROUND_TASK_STALE_MS`)
    - a chick (subagent) still running (`isChickRunning`, as for the done readout; an abandoned chick is already dozing, see "Chicks that have finished"); not an SDK chick, which is a process running alongside
    - watching (above), which makes it continuing anyway
    - a wakeup it set up with Claude Code's own tools, from the results confirming them: ScheduleWakeup (`scheduledFor`; pending until that time; cancelled by a result with `stopped`), CronCreate (`id`, `nextFireAt`, `recurring`; a one-shot one until `nextFireAt`, a recurring one until CronDelete with its `id`), and Monitor (`taskId`, `timeoutMs`, `persistent`; until it times out, a `<task-notification>` for its task id with a `<status>` (its events come without one), or TaskStop with its `task_id`). Kept in a ledger across polls, as their lines leave the tail window (`wakeCache`)
    - in the same config root, a session another session started that is still linked to no one, within 30 minutes of its start (`FRESH_UNLINKED_CHILD_MS`). A child started from a terminal is linked only from its first message (see "Watching"), so until then the app can't tell whose child it is, and every parent in that root keeps its continuing
  - The expiry counts from its moment for the concierge (see "Concierge": it counts as done for 5 minutes after it): the turn's end when nothing could wake it then, or the poll that first found the last thing that could wake it gone (`unwakeableForMs`, `continuingExpired.forMs`), or the 30 minutes, whichever came first. An expiry at the turn's end is asked about with that done, and dozing 5 minutes later doesn't ask again
