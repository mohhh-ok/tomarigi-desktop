# Settings file

The settings shown on the settings screen live in one JSON file that the user, an editor, or a coding agent edits; Tomarigi reads it at launch and applies an edit as soon as the file is saved. API keys stay in the OS store and are never in the file.

This replaces "Settings by an AI agent (MCP)" (a local MCP server through which the agent changed settings), which is removed. The user asked: 「設定をmcpでいじれるようにしたけど、正直、たんなるせっていふぁいるのほうがよくない？」, then 「mcpだと、仮にソフトウェアがしんがいされたときのひがいがおおきいから、せっていふぁいるのほうがいいかなと」「つまりゆーざーがしんがいされたときじゃなく、そふとがしんがいされたときな。」. Claude's analysis, which the user took (「なるほど、そのほうしんで」): the MCP tool list and every tool result were written by the page's JavaScript and reached every project's Claude Code session (registered with `--scope user`), and that agent can run commands; so a compromise of only the page (a bad npm dependency, an XSS from transcript text) could put instructions into the agents and get out of the Tauri sandbox. A file sends nothing from Tomarigi into the agents' context unasked, opens no port, needs no registration or token, works with any agent and by hand, and can be edited while the app isn't running. What MCP gave and the file doesn't (Claude's own assessment): the agent got the lists of models and voices and the connection test's result through the tools; with a file the agent asks the servers itself (VOICEVOX `GET /speakers`, OpenAI-compatible `GET /v1/models`), the schema says how, and the result of applying the file is in the app and its log.

## Requirements

The first minutes, for each kind of user:
- A user updating from a version with MCP and settings already made: nothing changes on the screen; every setting is the same after the update. If they had turned "Let an AI agent change settings" on, the settings say once that it was removed, why in one line, and show `claude mcp remove --scope user tomarigi` with a copy button, until they close the note (Claude's own decision: their Claude Code otherwise keeps a server that never connects)
- A user who never edits the file: the settings screen works as before; the file exists and follows the screen's saves
- A user who wants an agent to set things up: in the settings' "Settings file" section, they press a button that copies a short instruction for the agent (in the UI language) naming the file, the schema and the log, paste it into their agent with what they want (「読み上げを VOICEVOX にして」), and see the app change at once with the usual note
- A user editing by hand in an editor: the schema gives completion and checks in editors that read `$schema` (VS Code, Zed)

What the file holds and how edits are taken:
- Every setting the settings screen shows, except API keys: the summary provider choice, Local AI (base URL, model), the readout voice (source, server kind, base URL, voice, model), "Read aloud" and its volume, mute and the chirp volume, the window mode, icon sets per project, the concierge's look, the watched folders and their labels. What isn't a setting (window size and place, the last section shown, notes already closed, migration marks) stays where it is now (Claude's own decision)
- Pretty-printed JSON (2 spaces), no comments (Claude's own decision: the app rewrites the file on every save from the screen, which would drop comments; plain JSON is what agents and editors handle best). A `"$schema": "./settings.schema.json"` key at the top
- An edit saved while the app runs is applied within 1 second (Claude's own decision), and shows the same kind of note the agent's changes showed: 「設定ファイルから変更: 読み上げの声 システムの声 → VOICEVOX（四国めたん（ノーマル））」 (6 seconds, ×, stacked); the settings window, if open, shows the new values at once. An edit made while the app wasn't running is applied at the next launch without a note, except refused values (below)
- Each value goes through the same check as the settings screen (one function for both). A value that fails is not applied: the previous value stays, the other values in the same save are applied, and the app shows the reason in words in a note and in the "Settings file" section and writes it to the log. The file is not rewritten to undo the refused value (the user's text is left for them to fix). A server URL may point at any host, as on the screen: the rule that limited the agent to this machine and the local network is gone, since the file can't tell who wrote it and an agent with a shell can already read the transcripts itself (Claude's own decision, see above)
- A file that isn't valid JSON (half saved, a typo) applies nothing: every setting keeps its value, and the app says the file couldn't be read, with the line and column. When the screen saves while the file is broken, the broken text is first copied to `settings.invalid.json` beside it (one file, replaced each time) so the user's edit isn't lost, and the note says so (Claude's own decision: the screen and the mute button must keep saving)
- Keys the app doesn't know are left in the file as they are and reported once per launch as ignored; an API key written in the file is never read, and the report says keys go on the settings screen
- A file that is deleted while the app runs is written again from the current values (deleting is not a reset; Claude's own decision). With no file at launch it is written from the current values (or the defaults)
- Saves from the settings screen, the menu bar and the mute button write the file; the app's own writes never produce a "changed from the file" note, and dragging a slider doesn't write the file more than a few times a second (Claude's own decision)
- An agent or an editor never reads a half-written file from the app (the app writes a new file and renames it over the old one)
- The schema file `settings.schema.json` describes every key in English (agents read it): what it does, its allowed values, and for voices and models how to get the list from the server (VOICEVOX `GET <baseUrl>/speakers`, OpenAI-compatible `GET <baseUrl>/v1/models`). The app writes it at every launch, so it matches the running version
- The log has one line per applied change and per refused value, `[settings-file] applied <setting>` / `[settings-file] refused <setting>: <reason>` / `[settings-file] unreadable <line>:<column>`, with no value that could be a secret (URLs and voice names are settings and are logged as the screen's saves log them)
- A `README.md` for agents sits beside the file (the user: 「settings.jsonといっしょに、aiむけの文書もいれれる？自動更新する前提で。README.mdとかかな」). In English (Claude's own decision, as the schema): what the file is, how to change a setting and that the app applies a save at once, how to get the lists of voices and models from the servers, where the result is (the log's path and its `[settings-file]` lines), that API keys can't be set there and go on the settings screen, and that the app must be running for an edit to show at once (otherwise at the next launch). The app writes it at every launch, so it always matches the running version; an edit to it by hand is replaced at the next launch, and it says so at the top
- The copied instruction for the agent is short and points at that README: 「Tomarigi の設定を変えて: <what you want>。やり方は ~/.tomarigi/README.md」 (the path of the build's own folder)
- macOS, Windows and Linux

MCP removed:
- No port is opened; the MCP server, its token, the registration command, the port field and "Renew token" are gone, with the dependencies only it used. The token is deleted from the OS store on the first launch of the new version
- README (every language) explains the settings file instead of the MCP registration; the debug-only `TOMARIGI_AGENT_ACCESS` and `tools/mcp-call.sh` are removed, and the checks that used them read the file instead

Pass/fail:
- Updating a build that has settings (and MCP turned on) to the new one: every setting is the same, the file holds them, the MCP note shows with the remove command, nothing listens on 4844, the token is gone from the OS store
- With the app running, edit the file by hand: switch the readout voice to a VOICEVOX server, set Local AI's URL and model, add and remove a watched folder, change the window mode; each is applied within 1 second with a note, shows in the open settings window, and is in the log
- A real Claude Code session given the copied instruction and 「読み上げを VOICEVOX にして」 changes the file, and the app applies it (the session finds the voices from the server itself)
- A wrong value (malformed URL, unknown voice, a volume out of range) is refused with the screen's reason, the previous value stays, other values in the same save are applied, the file is not rewritten
- Broken JSON applies nothing and says where; then a save from the screen keeps the broken text in `settings.invalid.json`
- A save from the screen updates the file and shows no note; dragging a volume slider for a few seconds writes the file only a few times a second
- Edit the file while the app is closed; launch: applied
- `README.md` and `settings.schema.json` are there after launch and match the version; an edit to the README by hand is replaced at the next launch
- dev, verify and the everyday build each use their own file
- Volume (below) measured after 1,000 saves from the screen and 1,000 edits of the file
- Unit tests for reading, checking and merging the file (each setting's check is the screen's function), and UI check of the "Settings file" section in Japanese and English

## Basic design

- Place: the everyday build `~/.tomarigi/settings.json`; dev `~/.tomarigi/dev/settings.json`; verify `~/.tomarigi/verify/settings.json`, each with its `README.md`, `settings.schema.json` and `settings.invalid.json` beside it (`~` is the home folder on every platform, as `~/.tomarigi/vscode/` already is). Debug builds only: `TOMARIGI_SETTINGS_FILE=<path>` uses another file for a check (Claude's own decisions; the everyday path is the one users and agents are told)
- One source of truth: the file is the settings' store; the screen's saves write it and every window reloads from it through the app-wide `settings-changed` event, as now. The values these settings had in IndexedDB are copied into the file once (when there is no file yet) and then no longer read; they are left in IndexedDB, not deleted, so going back to the previous version keeps its settings (Claude's own decision). API keys stay in the OS store through Rust (`keys.rs`), untouched
- Nothing goes from Tomarigi into an agent's context except what the agent chooses to read (the file, the README, the schema, the log). No listener, no IPC an outside program can call to change settings
- The README and the schema are fixed text built into the app at build time and written by Rust, with only the paths filled in; the page's JavaScript never supplies their text, so a compromise of only the page can't change what agents are told to do (Claude's own decision, for the reason MCP was removed)
- Volume: one `settings.json` of a few KB, one `README.md` and one `settings.schema.json`, all replaced in place; one `settings.invalid.json` at most, replaced each time; no other file is created per save. The log gets one line per applied or refused change, and one when writes start failing and one when they work again (e)(2); it is already rotated at 10 MB (README "Other notes")
- The settings window's section "AI agent access" becomes "Settings file": the path with a copy button, a button that shows the file in the file manager (Finder / Explorer / the Linux file manager), "Copy instructions for an agent", this launch's changes from the file and refused values (the last 10, as the agent card listed), and the MCP removal note when it applies
- Out of scope: settings that aren't on the settings screen (debug, mock, updates), a file format other than JSON, a CLI
- The implementing session updates the other sections that mention MCP or IndexedDB as the settings' store ("Settings window", the README's environment variables and checks) in the same work

## Detailed design

Written by the implementing session; Claude's own decisions unless said otherwise.

(a) The file's shape. Top-level keys are flat, one per setting, camelCase, so an agent changes one key without reading a nested structure. Pretty-printed with 2 spaces; keys sorted (serde_json's map), which puts `$schema` first:

```json
{
  "$schema": "./settings.schema.json",
  "chirpVolume": 100,
  "chirps": true,
  "conciergeLook": "owl",
  "defaultFolderLabels": { "claude": "Claude Code" },
  "iconSets": { "-Users-me-Dev-app": { "label": "app", "set": "cat" } },
  "localAi": { "baseUrl": "http://localhost:11434/v1", "model": "qwen3:8b" },
  "readAloud": false,
  "readAloudVolume": 100,
  "readoutVoice": { "server": { "baseUrl": "http://localhost:50021", "kind": "voicevox", "voice": "2" }, "source": "local" },
  "summaryProvider": "local",
  "watchedFolders": [{ "agent": "codex", "id": "6f1c…", "label": "Codex work", "path": "/Users/me/.codex-work" }],
  "windowMode": "floating"
}
```

| File key | Value | Store key it stands for (today's IndexedDB key) | Check (lib/settings-checks.ts, the screen's functions) |
|---|---|---|---|
| `chirps` | boolean | `muted` (inverted) | boolean |
| `chirpVolume` | integer 0–100 (percent, as the slider) | `chirpVolume` (0–1) | `checkVolume` |
| `readAloud` | boolean | `voiceEnabled` | boolean |
| `readAloudVolume` | integer 0–100 | `voiceVolume` (0–1) | `checkVolume` |
| `readoutVoice` | `{ source: "system" \| "local", server?: { kind: "voicevox" \| "openai", baseUrl, voice, model? } }` | `readoutVoice` | `checkOption`, `checkLocalTts`, `checkVoiceInList` against the server's list when it can be read |
| `summaryProvider` | `"anthropic" \| "openai" \| "local"` or `null` | `aiProvider` | `checkOption`, `checkProviderChoice` |
| `localAi` | `{ baseUrl, model }` or `null` | `localAi` | `checkLocalAi` |
| `windowMode` | `"floating" \| "normal"` | Rust's `window-mode.json` | `checkOption` |
| `conciergeLook` | `"owl" \| "penguin"` | `conciergeLook` | `checkOption` |
| `iconSets` | `{ <project key>: { set, label } }` | `projectIconSets` | `checkOption` per entry; `birds` (the default) drops the entry, as on the screen |
| `watchedFolders` | `[{ agent, path, label, id? }]`, the folders the user added | `roots` | `checkOption` (agent), `checkTypedRootPath`, `checkNewRoot`, readable, `checkRootLabel`, per entry |
| `defaultFolderLabels` | `{ <agent>: label }`, the labels of the default folders | `defaultRootLabels` | `checkOption` (agent), `checkRootLabel` |

- `watchedFolders[].id` is the folder's id, which session ids start with (lib/agents.ts), so it stays across launches. The app writes it; an entry an agent adds without one gets `path:<pathKey(path)>`, the same on every launch without writing it back. An entry is matched to the current folders by `id`, else by `samePath`
- The readout voice's label, speaker name and VOICEVOX credit are not in the file (an agent would leave them stale). They are looked up from the server when a server, kind or voice is applied (`GET /speakers` and the engine manifest, as the screen's card does) and kept in IndexedDB under `readoutVoiceInfo`, keyed by kind, base URL and voice: a cache, not a setting. A miss at launch (the file was edited while the app was closed) is looked up in the background; until then the voice shows by its id and no credit
- A top-level key left out keeps its value and is written back with its current value, the same as a deleted file is written again (the parent session's decision): a file an agent writes with only the keys it wants becomes whole again, so the next agent that reads it sees every value. Refused values and keys the app doesn't know are still not written back. `localAi: null` removes Local AI as the screen's Delete does
- A setting with nothing saved is written with the default the screen shows (`toFile(field, undefined)`; the whole file with nothing saved is `defaultFileDoc()`), so every value the app writes fits the schema: `null` only where the schema allows it (`NULLABLE_FIELDS`: `localAi` and `summaryProvider`, "not set"). A `null` in another key (an earlier version wrote `"conciergeLook": null` when no look had been chosen) is read as nothing saved: at launch the value in use becomes the default (or the applied value, if there is one) without a note, and the key is written again with it, as a key left out is; log `[settings-file] <key> was null in the file: wrote the value in use` / `… was null in use: took the default`
- Applied in the order of the table except `localAi` before `summaryProvider`, so a file that sets up Local AI and chooses it in one save passes `checkProviderChoice`

(b) Who does what.
- Rust `src-tauri/src/settings_file.rs` owns the files: the paths, the applied values (the last values that passed, file-shaped), writing, and noticing edits. It never checks a setting's meaning; the checks stay in the page's functions (one function for the screen and the file)
- The floating window's page (the owner, as for every setting) checks an edit (`src/lib/settings-file.ts`, pure functions with unit tests: the table above, the conversions both ways, `applyFileDoc(doc, applied, deps)` → accepted / refused / ignored / API-key fields / the change lines for the note) and runs it (`src/perch/use-settings-file.ts`: the startup, the listeners, the notes, this launch's list, the `[settings-file]` log lines)
- `lib/kv.ts` routes the store keys of the table to Rust and keeps every other key in IndexedDB (window size and place are Rust's, the last section, the event log, turn verdicts, garden positions, notes closed): `kvGet(key)` → `settings_get(field)` and the conversion; `kvPut` → `settings_set(field, value)`; `notifySettingChanged` as now. So `settings-store.ts`, `api-keys.ts`, `readout-voice.ts`, `icon-set-store.ts` and every caller keep their functions. Outside the app (the browser mock, no Tauri) the keys stay in IndexedDB
- Commands (the app's own windows only, through Tauri's invoke; nothing outside the app can call them): `settings_file_open`, `settings_file_fill(values)`, `settings_get(field)`, `settings_set(field, value)`, `settings_accept(field, value)`, `settings_file_paths`

(c) Paths. From the identifier: `net.mohtech.tomarigi-desktop` → `~/.tomarigi/`; `….dev` → `~/.tomarigi/dev/`; `….verify` → `~/.tomarigi/verify/`; any other suffix → `~/.tomarigi/<suffix>/`. Debug builds only: `TOMARIGI_SETTINGS_FILE=<path>` puts `settings.json` at that path, with the other files beside it and the copy of the applied values at `<path without .json>.applied.json`, so a check touches nothing of the build's own. The folder is made with 0700 and `settings.json` / `settings.invalid.json` with 0600 on macOS / Linux (`README.md` and the schema hold no user data and are 0644, inside the 0700 folder), as the log (folder paths and server URLs are the user's)

(d) Launch.
1. Rust (setup, before the window): resolves the paths; writes `README.md` and `settings.schema.json` from the text built in with `include_str!` (`src-tauri/settings-file/README.md`, `settings.schema.json`), filling in only the paths and the version; deletes the MCP token from the OS store (every launch; nothing when it's gone); reads `settings.json`; reads the last applied values from `settings-applied.json` in the app's config folder (below); takes `windowMode` from the file if it is one of the two, else from the applied values, else from `window-mode.json` (the version before), else floating. `window-mode.json` is read only for that migration and is no longer written: from then on the window mode's store is `settings.json`, with `settings-applied.json` as its fallback (the parent session's decision, so the mode isn't kept in two places)
2. The owner page, before loading the folders and the settings (App.tsx's startup load), calls `settings_file_open` → `missing` / `ok` / `unreadable` with the file's values or the line and column
3. `missing` with no applied values: the first launch of this version. The page reads the table's keys from IndexedDB (they are left there), builds the values with `fileDocFromStore`, and `settings_file_fill` writes the file from them. If `agentAccess.enabled` was true in IndexedDB, `mcpRemovedNote` is set to `shown` in IndexedDB. Log `[settings-file] created from the earlier settings`
4. `missing` with applied values (deleted while the app was closed): written from the applied values
5. `ok`: `applyFileDoc` against the applied values; a key that differs is checked and, when it passes, applied without a note; a refused one keeps the applied value and gets a note and a log line. Keys the app doesn't know get one note per launch. Table keys missing from the file are marked dirty and written back with the applied values (a)
6. `unreadable`: nothing is applied, the applied values are used, and the note says the line and column. The file is left as it is: `settings_file_fill` marks no key dirty (a table key the applied values don't have yet takes the page's value without being written), so the worker doesn't rewrite it on its first tick. It is copied to `settings.invalid.json` and written only when the screen saves (e)(2)

`settings-applied.json` (in the app's config folder beside `window-mode.json`, not where users and agents look) holds the values that passed, so that "the previous value stays" also holds across a launch: an edit made while the app was closed that fails, or a file broken at launch, falls back to the values of the last run, not to the defaults. It is replaced in place with the file, at most a few times a second. This is a second file beside the four the basic design lists; it is a copy, read only for the fallback, never by agents (the file is the source of truth; the copy is what was taken from it)

(e) While the app runs.
- Rust's worker thread wakes every 250 ms: (1) a `stat` of `settings.json`; when the modified time or size changed, it reads the text; text equal to what the app wrote last is its own write and is skipped. Otherwise: not valid JSON → log `[settings-file] unreadable <line>:<column>` (serde_json's) and emit `settings-file-unreadable` to the owner; valid → emit `settings-file-edited` with the values and the file as it was before the edit (the text the app last wrote or saw), so the page checks only the keys this edit changed: a refused value left in the file isn't refused again on the next edit, and a key set back by hand to what it was before a save from the screen is still seen. A missing file is written again from the applied values (log `[settings-file] rewritten (the file was deleted)`). Polling instead of OS file events (no new dependency; editors that save by rename and network home folders behave the same; one `stat` per 250 ms). So an edit is seen within 250 ms and applied well within 1 second
- (2) Writes: `settings_set` (a save from the screen, the menu bar, the mute button) puts the value in the applied values and marks the key dirty; the worker writes dirty keys at most every 250 ms (a dragged slider writes at most 4 times a second; the last value is always written). A write reads the file first: valid → only the dirty keys are replaced, so a refused value or a key the app doesn't know in other keys stays as the user wrote it; not valid → the text is copied to `settings.invalid.json` (replaced), the file is written from the applied values, and `settings-file-invalid-kept` is emitted for the note. If the file changed since the worker last looked, step (1) runs first and the write waits for the next tick, so an edit and a save at the same moment don't lose the edit. Written as `settings.json.tmp` then renamed over (rename replaces on Windows too). A write that fails (another program holding the file open on Windows, permissions, a full disk) puts its keys back in the dirty set, so a later tick writes them again, with any save made in between; the same holds for a missing file written again. While writes keep failing, the next try waits 5 seconds after the last failed one instead of 250 ms (Claude's own decision), a tick tries at most one write, the log gets `[settings-file] couldn't write the file` once for the first failure, and the same unreadable text is copied to `settings.invalid.json` once, not at every try. When the copy to `settings.invalid.json` fails, the file is not written over (the user's text stays in it) and it counts as a failed write: the keys stay dirty and the copy and the write are tried again after 5 seconds; `settings-file-invalid-kept` is emitted only when both the copy and the write are done; the first write that works logs `[settings-file] wrote again after a failure` and the 250 ms spacing comes back. On exit (`RunEvent::Exit`) dirty keys are written at once, through the same write, even while a retry is waiting
- The owner, on `settings-file-edited`: `applyFileDoc`; table keys missing from the edited file are written back with their applied values through the same dirty-key write (a); for each accepted key `settings_accept(field, value)` (applied values only; the file is not written, so the user's text stays as it is) and `notifySettingChanged(storeKey)` with `from: "settings-file"`, so every window, the owner included, reloads it as it reloads another window's save; `windowMode` goes to `set_window_mode`'s switch without writing the file. Then the note: title 「設定ファイルから変更」, one line per change 「<setting>: <from> → <to>」 (the describers of the agent tools, moved), and one line per refused value 「<setting>: <reason>（前の値のまま）」; 6 seconds, ×, stacked (the agent note's component, renamed). Each goes into this launch's list (the last 10) and the log: `[settings-file] applied <file key>` / `[settings-file] refused <file key>: <English reason>`; URLs and voice names may be in the line, never a key. A key whose name looks like a secret (`apiKey`, `*Key`, `*Token`, `*Secret`, any case) is never read; the note says API keys go on the settings screen
- Every refused reason is said in the UI language: the messages that were English for the agent alone (`path-not-absolute`, `network-path`, `not-readable`, `label-empty`, `builtin`, `unknown-option`, `volume-range`, `no-key`, `local-not-set-up`) get locale keys; the log uses the English text. `server-not-local` and `checkAgentServerUrl` are removed

(f) README.md and the schema. Fixed text in `src-tauri/settings-file/`, written by Rust with `{{SETTINGS}}`, `{{SCHEMA}}`, `{{LOG}}`, `{{VERSION}}` replaced, nothing from the page. The README's first line says the app rewrites it at every launch. A unit test (vitest) reads the schema and checks that its keys are the table's and that its enums equal `AGENTS`, `ICON_SET_IDS`, `CONCIERGE_LOOKS`, `WINDOW_MODES`, the TTS kinds and the providers, so the text can't drift from the code. The same test checks the file the app writes against the schema (a small checker of the schema's `enum`, `type`, `oneOf`, `required`, `properties` / `additionalProperties`, `items`, `minimum` / `maximum`, `minLength`, `propertyNames`, no dependency): the file with nothing saved and the files with a value saved for every store key, built from `FILE_FIELDS` so a key added to the table is checked without touching the test (the test also fails when its saved values miss a store key), and `NULLABLE_FIELDS` equals the keys whose schema accepts `null`. Contents of the README: what the file is; edit one key, save, and the app applies it within a second with a note (it must be running, else at the next launch); left-out keys keep their values; the voice and model lists (`curl <baseUrl>/speakers` for VOICEVOX, `curl <baseUrl>/v1/models` or `<baseUrl>/models` for OpenAI-compatible bases that end in `/v1`); where the result is: `grep '\[settings-file\]' <log>` (the last lines say applied / refused with the reason); API keys aren't in the file; don't touch `id`

(g) The "Settings file" section (replaces "AI agent", `agent` → `settingsFile` in `settings-sections.ts`; a saved `agent` section opens `settingsFile`).
