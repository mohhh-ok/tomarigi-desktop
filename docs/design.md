# tomarigi-desktop design

A desktop app for macOS, Windows, and Linux (Tauri 2; see "Platforms") that watches AI coding agent sessions (Claude Code / Codex and the other agents in "Agents") as birds in an always-on-top floating window. It is the desktop version of the tomarigi Chrome extension.

## Scope

- Tabs: Concierge (always shown; see "Without a provider" under "Concierge"), Garden, Perch, and Recent activity, in that order (Garden is the default), plus the ⚙ settings screen
- Watches the transcripts of every agent in "Agents" in parallel through adapters. State is decided by local heuristics only; no hooks are installed on the agent side
- Bird states (sprites, aura while working, motion animations), and drag placement in the Garden
- Icon sets (birds / gnome / cat / robot / frog) assigned per project
- Web Audio chirps (mute, volume), speechSynthesis readout (opt-in, volume) or a local TTS server's voice (see "Readout voice (local TTS server)"), BYOK (OpenAI / Anthropic) or a local model for summaries on done with the "?" and anger mark verdicts, and connection tests
- Persistent event history and a debug log screen
- i18n (see "Language")
- Mock mode (presets + JSON injection)
- Not bundled: the author's `peer-session` skill (starts child Claude Code sessions in Ghostty panes, which then show up as birds). It is Ghostty- and Claude Code-only and still being shaped by the author's own use (the user: 「peer-sessionはえっとね、基本的には俺も使いながらブラッシュアップしていきたいから細かい設定も基本的には俺好みでかんがえてる。でさ、もんだいはたーみなるごかんよな」「とりあえず自分の使用でそだてていきたい。」). Revisit bundling or publishing it, and support for terminals other than Ghostty, when the user brings it up again

## Language

- UI text is generated from `scripts/locales` into `public/_locales`, and every locale is checked to have the same keys
- The app is English-based. UI text comes from the locale files (English fallback). The menu bar menu is Japanese when the system language is Japanese and English otherwise. The debug log screen and mock mode are English only

## Bird states

- Machine state `BirdState`: `working | waiting | done | dozing`. Recomputed on every poll
  - `waiting`: stopped on AskUserQuestion / ExitPlanMode / request_user_input, or Claude Code's `<config>/sessions/<pid>.json` has `status: "waiting"` (while it shows options or a permission prompt, Claude Code doesn't write that tool_use to the transcript until it's answered)
  - `dozing`: a finished turn (`done`) with no new writes for 5 minutes (`DOZE_MS` in `src/lib/bird-state.ts`). It only changes the sprite and the status label
- A write in the last 6 seconds counts as working, unless Claude Code marked the turn as over: when the last line with a time (the away recap aside) is its `system` / `turn_duration` line, a turn ending on the reply is done at once (`turnEnded` in `src/lib/transcript.ts`, `deriveState` in `src/lib/bird-state.ts`). Any later line with a time (the next prompt, another session's message, a queued message) clears it, so the 6 seconds hold again. Agents that write no such line (Codex, Gemini CLI, OpenCode and the others) keep the 6-second rule as before. In the local transcripts of three days, the line came in 84 of 89 transcripts and always right after the turn's last assistant text (1,162 of 1,162). (Claude's own decision, approved by the parent session: a child that ended its turn asking the user was shown working for 6 seconds after its done event, and the concierge was asked during them with that session working, so it didn't advise replying to it.) The recap Claude Code writes while the user is away (`system` / `away_summary`) is not a write: it isn't conversation, and it made a finished session working for 6 seconds, so its turn was summarized again and the concierge asked again (the user: 「コンシェルジュのはんのうがおかしい。べつせっしょんでちょうささせて」; excluding only this line is Claude's own decision: in the local transcripts 3,692 of 3,942 such lines came alone, more than 6 seconds after the last message and with none in the 30 seconds after, while the other lines written late mostly start or belong to a turn)
- The finished-turn state is called "done" everywhere: bird state, Recent activity, sound settings buttons, and bird descriptions (all locales)
- The waiting state is called "needs reply" (ja: 返事待ち) everywhere: bird state, Recent activity events, and sound settings buttons (all locales)

## Watching

- A session that handed work to another session and is waiting on it is shown as "watching". The other session isn't necessarily in the same directory
- How links are found: from traces of Claude Code's cross-session messaging (a public feature, enabled without configuration since v2.1.224) in transcripts. The sender side is the recipient name in a SendMessage tool call; the receiver side is `<cross-session-message from-name="…">`. Names are matched against `name` in `<config>/sessions/<pid>.json` to look up the other session's sessionId, cwd, and status. Two sessions that exchanged at least one message are considered linked. No particular person's tooling (such as a script that launches sessions) is relied on
  - Claude desktop app (Code tab) sessions are addressed by a `local_<uuid>` id instead of a name, and the app writes that id as `hostSessionId` in the session's `sessions/<pid>.json`. So these traces are read too, and each is matched against `hostSessionId` as well as `name`: the `session_id: local_…` in the text of the tool result that starts a session (`Started session "…" (session_id: local_…, …)`, from the app's `start_session`), `session_id` in the input of the app's `send_message` tool, a SendMessage recipient that is a `local_…` id (already read as a name), and `origin.from` of a received message when it is a `local_…` id. A child started from the desktop app is then linked to its parent from the moment it starts, before it sends anything, and stays linked when either is renamed (the parent session's decision: before, such a child was linked only once its first message arrived, matched by its title, and the app log showed it unlinked until then)
  - A session started from a proposal card (the user clicks a card a desktop app session proposed; see "The "?" for sessions waiting on you") has no `session_id` in its parent's transcript: the result of the proposal has only a task id. The app writes, in the first prompt of every session another session started (turnOrigin other than `human`), the starter's shared notes folder, `…/side-session-notes/local_…`, with the starter's id. So that id in the transcript's first prompt, when its turnOrigin isn't `human`, is a trace too (Rust `notes_folder_host_id`, `NOTES_FOLDER_ID` and `firstPromptStarterOf` in `src/lib/transcript-peers.ts`; the id is `local_` and the hex digits and `-` after it). Only the first prompt: a later notice (a `<side-sessions-event>`, a message) may quote another session's folder. Such a session is linked to the session that started it from its first prompt, and so its parent takes it over from its start (`parentTakesOver`, see "Sessions started by another session"), as a child started by `start_session` right away (Claude's own decision, by the session that made this). In the transcripts on this machine, all 215 first prompts with a turnOrigin other than `human` and a brief from the session that started them had the folder; in the reported case its id was the parent's `hostSessionId`; and the 16 sessions started by a session that was itself started by another had their own starter's id there, not the id their starter had, so it is the direct starter, not the group's first session. Not a public spec either
  - A session started in a terminal by another session (e.g. `claude --name <name> "<prompt>"`) has no trace of its parent until one of them sends a message: its first prompt is written like one the user typed. It is linked from its first message, as before
- Watching: the session's own machine state is done / dozing, and at least one linked session is working (status busy in `sessions/<pid>.json`, or its transcript's machine state is working / waiting). Chirps and readout on done are held until all linked sessions stop
  - A session started by another session (see "Sessions started by another session") doesn't watch the session that started it: that parent's moves don't make it watching, don't hold its chirps and readout, and don't make it continuing. The parent hands work to the child, not the other way round, and keeps moving while it runs other children, so the child would never get out of watching (Claude's own decision). It holds also after the user typed in the child (the parent no longer takes it over then, but it still started the child): the child is told by its first prompt (`isChildSession`), and its starters are the linked sessions `parentTakesOver` counts as its parent (`isParentOf`, `startersOf` in `src/lib/watching.ts`). `buildViews` in `src/lib/sessions.ts` passes only the linked sessions it watches (`peersWatchedBy` in `src/lib/watching.ts`, which decides this item and the next by the table `WATCHES` there: how the linked session stands to this one against who started its latest turn) to `watchingCount` and to the done hold (`peerHoldChicks`); its links (`peers`, the concierge's `watch_parent`) stay as they are. The parent still watches the child as before, whatever started the child's latest turn (it may wait on its own child and be woken by that one's report, still on the parent's work)
  - Between two sessions where neither started the other, a session watches the other only while the other's latest turn was started by a message from this session: the other is then working on what this one sent. A turn started by the user's input or by a message from a third session is not this session's work, so it doesn't make this session watching, hold its chirps and readout, or make it continuing. A message from this session that arrived during the other's latest turn counts too: the other handles it in that turn. A first prompt, and a turn whose starter isn't known (the desktop app's `send_message`, which leaves no sender in the transcript), count as before (the safe side). The table is `WATCHES` in `src/lib/watching.ts` (`peersWatchedBy`), its `unrelated` row. How it is read: `scan_peer_names` in src-tauri returns who started the last turn in the part read (`lastTurnStarter`: a typed prompt, another session's message, or something else) and the senders of the messages that arrived during it (`turnPeers`, from `queued_command` attachments with `origin.kind` `peer`). A prompt the user typed into the other while it worked (a `queued_command` attachment with `origin.kind` `human`) makes the starter typed but is handled in the running turn, so the senders that arrived earlier in that turn stay: only a prompt that starts a turn replaces them (`turnStarted`). A sender is named by `origin.verifiedPeerPid`, `origin.name` and `origin.from` (`uds:/tmp/cc-socks/<pid>.sock`, or a desktop app `local_…` id). `rememberLatestTurn` keeps each session's latest turn across reads (a new turn replaces it, senders without a new turn add to it, and a read from the top replaces it: `scan_peer_names` returns `start` 0 also when the transcript had shrunk and was read again from the top), and `turnStarterSession` tells whether a sender is this session: by pid against this session's `sessions/<pid>.json` (the pid in the socket path when `verifiedPeerPid` is missing), and by name or desktop app id: a pid that differs still counts as this session when the name or id names it, since a resumed session runs under a new pid; when neither tells, it isn't known (all in `src/lib/watching-turns.ts`). The link itself (lines, block, `watch_parent`) stays. Without this rule, two sessions that had only exchanged messages (one asking the other to wait for its work) kept watching each other after the work was done: the finished session stayed working (「ついばみ中」, `continuing=true`) while the other went on with other work. The item above covers only a session started by another, so it didn't apply. Making two such sessions never watch each other was not adopted: when one really waits on the other's work (for example, when it has asked the other to finish something first), it would show done. Both are Claude's own decisions
- After the linked sessions stop, the bird stays watching for 5 minutes after the last one moved (`WATCH_GRACE_MS`), so the watch block and label don't flicker between the other session's turns. A linked session whose status isn't idle (e.g. shell) also counts as moving
  - The grace period ends early when no linked session moves now and the session itself finished a turn after every linked session's last transcript write: it has taken the other session's result (it ended a turn after the result came), so it is done, not watching. Its own turn's end is the time of its last transcript line (its done / dozing state's basis; `lastWrittenAt` in `src/lib/transcript.ts`), and a linked session's last write is the same function on that session's transcript (`lastWriteAt` in `lastPeerStates`, passed to `watchingCount` as the peer's `lastWriteAt`). The 5 minutes are still counted from the last time a linked session moved (`lastActiveAt`), unchanged. A linked session that moves again makes it watching again, and while one moves it stays watching as before. When the session finished its turn before a linked session's last write (it handed work over and stopped), the 5 minutes hold as before. When a linked session's last write isn't known, the 5 minutes hold too (the safe side). Before, a Claude desktop app parent that took its child's report at 20:13:07 and finished its turn stayed watching (working, a white dot in the concierge) until 20:17:37, 5 minutes after the child stopped at 20:12:37 (the user: 「かんりょうずみですらないねん。白丸やし」「5ふんってながくない？」; ending the grace period on the parent's own done is Claude's proposal, and the user had it fixed in a separate session). One function decides it (`watchingCount` in `src/lib/watching.ts`), and the bird's watch block and label, continuing (see "Turn verdicts") and the concierge's checks all read its result. The early end compares with the linked session's last write, not with the last time it moved: "last moved" is the poll time while the app sees it working, and a write in the last 6 seconds counts as working, so it lags the actual last write by several seconds. Compared with "last moved", a parent that took the report and finished its turn within those seconds kept the grace period: on 2026-11-12 the app-x child last wrote at 21:02:21, the parent finished its turn at 21:02:26, and at 21:03:33 the parent was still continuing and watching that child (the app log). A Claude desktop app parent answers a child's report in a line or two, so this is the usual case. Comparing with the last write is Claude's proposal, and the user had it fixed in a separate session (the user: 「またapp-xがかんりょうずみになるのおそかったが」). Known limit: when the linked session stopped less than 5 minutes ago and the session sends it new work and finishes its turn, the session leaves watching for the few seconds (one or two polls) until the linked session starts moving, so the bird's label and watch count swing to done. The done chirp and readout don't change: they are decided on a path that doesn't read watching (`src/lib/session-events.ts`). Leaving this as it is is Claude's own decision
- Sessions started by another session: a parent takes over the results of a session it started and the questions its replies ask the parent, so that session is quiet on its own (the user's decision). Which questions reach the parent is read from the transcript: a reply that asks (the turn verdict asking) is the parent's only when the same turn sent the parent a message (SendMessage, or the desktop app's send_message, to a linked session that counts as its parent; `lastTurnSentTo` in `src/lib/transcript.ts`, `askSentToParent` in `src/lib/watching.ts`). A reply's own text doesn't reach the parent: a reply that asks without such a message asks whoever reads its pane, so it waits on the user like any other session's. A message to another session (its own child, a sibling) doesn't count, and a turn whose prompt is out of the read window counts as sending none (the user's decision: before, every reply that asked was taken as asking the parent, and a session another session started, asking the user in its pane to open a URL and allow a sign-in while its own child kept working, was never brought up by the concierge; the user: 「コンシェルジュがはんのうしてない」) A wait only the user can answer in that session's pane, a permission prompt or a question tool (the machine state waiting), isn't taken over (the user's decision). The Claude desktop app's wrap_up with an ask (or `blocked`) is the machine state waiting too, but it is taken over: the ask is part of the session's report, which reaches its parent, and the parent can answer it with a message (Claude's own decision, by the parent session). Which waits a parent can answer is one function (`parentCanAnswer` in `src/lib/turn-verdict.ts`); a waiting on a wrap_up's ask is marked `wrapUpAsk` on the session and on its event. It applies to a session that was started by another session and is linked to a parent: a session that started before it and either was not started by another session, or was and is linked now to one older than itself (`parentTakesOver` and `takenOverByParent` in `src/lib/watching.ts`; the second part is Claude's own decision, by the parent session, so that the successor of a rebirth isn't taken for the child of the child its predecessor started), whether the parent is watching now or not, and in or out of the grace period (the user's decision)
  - Its done still chirps and stays in the log and the event feed, but isn't read aloud: not outside the Concierge tab, and not when a request in the tab fails and the held events are read (`silentForParent` in `src/lib/watching.ts`; the user's decision on the done's readout; keeping the chirp is Claude's own decision, by the parent session). A done whose reply asks its parent (the turn verdict asking) is a done, so it is silent too. Its needs reply on a wrap_up's ask is silent too. Its needs reply on a question tool is read aloud like any other session's (the user's decision). A needs reply event comes only from a tool call in the transcript (`deriveSessionEvents` in `src/lib/session-events.ts`: a question tool, or a wrap_up's ask), so a permission prompt, and Claude Code's question tool while it is open (Claude Code writes that tool call only after it is answered), make no event and aren't read aloud for any session, taken over or not; they still put the session on the concierge as needing a reply, and its bird gets the "?" The done of the parent is held by watching as before. The app log's `[event]` line has `silent=true` for the silent ones
  - The concierge doesn't ask the developer to reply to a question its reply asks its parent (the turn verdict asking, in a turn that sent the parent a message; above), and doesn't ask to check its result (see "Concierge"). It doesn't ask the developer to reply to its wrap_up's ask either. It does ask the developer to reply when it stops on a permission prompt or a question tool, as for any other session: only the user can answer those, in its pane, and its parent can't answer for it (the user's decision). Before, a parent's takeover left out its permission prompts and question tools as well, so a child stopped on a permission prompt was never brought up; that grouping was the parent session's mistake of offering the cases as one choice, and it was changed because it held back waits only the user can answer. Its bird still gets the "?" (the user's decision). Whether a session waits on the developer is one function for the concierge's facts, its triggers, the Concierge tab's bubble lines, and the tab's count of birds needing a reply (`waitsOnDeveloper` in `src/lib/turn-verdict.ts`), with where the wait comes from (`replyWaitSource`, the machine state or the turn verdict) from the same file: a session whose parent takes it over counts as working there while it waits on what its parent can answer. The "?" on the bird and the Perch row stay with `needsAnswer`
  - Its parent's takeover is lifted only while its latest turn was started by a prompt the user typed in it; once a later turn is started by its parent's message or the app, it is taken over again (the user's decision). A turn is started by the last prompt after its first prompt: a user line that is not a subagent's (`isSidechain`) and not a tool result. It is typed when its `turnOrigin` is `human` (or, without `turnOrigin`, its `origin.kind`); messages from other sessions (`peer`), task notifications (`task_notification`), and the desktop app's own turns such as `<side-sessions-event>` and `send_message` (`sdk`, `host_synthetic`) aren't. It is read with the links, from the top of the transcript and then from where the last read stopped (`scan_peer_names` in src-tauri), and kept as the starter of the session's latest turn (`lastTurnStarter`, `rememberLatestTurn` in `src/lib/watching-turns.ts`, the same record as in "Watching"). Details (Claude's own decision, by the parent session): a meta line (`isMeta`) counts only when it is a message from another session (those are written as meta lines with `turnOrigin` `peer`); what arrives while it works is written as an attachment (`queued_command`), and of those only a prompt the user typed (`origin.kind` `human`) counts, as typed, while messages from other sessions and task notifications don't; a read with no new prompt keeps the previous answer. The first prompt never counts, so a session started in a terminal (its first prompt is `human` too) is taken over until the user types in it. Before this, one typed prompt took it off for good (Claude's own decision), which kept a child the user had once talked to off even when it later stopped on a question to its parent, so the concierge asked the user to reply
  - Told from the transcript's first prompt, which is read once from the top of the file (`scan_peer_names` in src-tauri): the Claude desktop app writes the first prompt of a session started by `start_session` with a `turnOrigin` other than `human` (`sdk` or `host_synthetic`; in the transcripts on this machine 177 such sessions all were started by another session, and the 97 the user started were `human`). A session the user started and that later exchanged messages with an older one isn't one: before, it counted as that one's child (the later-started of the two) and would have gone quiet too (Claude's own decision, by the parent session: in the app log, 4 of the 6 sessions that were done before they were linked were sessions the user talked to)
  - A session started in a terminal by another session writes its first prompt like one the user typed (`turnOrigin` `human`). It is told apart by a name and a prompt given at launch (`claude --name <name> "<prompt>"`): an `agent-name` line before the first prompt, and the first prompt within 2 seconds (`PROMPT_AT_LAUNCH_MS`) of the SessionStart hook's line (Claude's own decision, by the parent session). In `~/.claude2` on this machine this caught 267 of the 268 sessions started by another session and, of 65 others, only 4 trial sessions of a rebirth; the user's own desktop app sessions never match it. A prompt typed right after launch without a name doesn't count: 12 sessions the user started had one within 2 seconds
  - The desktop app rule also takes a session run from the Agent SDK (`entrypoint` `sdk-py`, first prompt `sdk`) as started by another session. Such a session is only taken over when it is linked to an older one, which they rarely are
  - Known errors (Claude's own decision, by the parent session, to accept them): a grandchild (a session started by a child) whose grandparent closed or was reborn is read aloud and advised about again, since its parent lost its own parent; that child is read aloud too. A session the user starts with `claude --name foo "<prompt>"` themself and that exchanges messages with an older session the user started counts as taken over, until the user types in it again. While a reborn session and its predecessor both run (until the predecessor's pane closes), a successor that talks with the child counts as that child's child
- Presentation:
  - In the Garden, the watching bird and its linked birds are placed close together as a watch block, and each linked bird is connected to the watching bird by a line. The block has no frame or background of its own (the user: 「いまはグループをしかくでかこってるが、これだとはいけいがきえてると視認できない。そこで箱で囲むのをやめて線で繋げる形にして、背景消えてる時でもせんがみえるじょうたいにしたい」)
    - The lines stay visible at full strength at rest in "Fade until hovered", like the birds. They are not a hover or click target, and clicks on them go through at rest (Claude's own decision)
    - A line runs between the two birds' icons and is drawn behind birds, badges, bubbles, and status lines, so it never hides them (Claude's own decision)
    - A line never runs over another bird, name, bubble, or status line (the user, shown a line that bowed over the bird in between to join the left and right birds of a row: 「こういうふうに、線がまたがるじょうたいはちょっとやめてほしい。これまでは箱に収める関係からこういうぱたーんんがうまれたが、かえれるやろ」). So a linked bird is put next to the bird it is linked to, and lines are drawn only between birds next to each other
    - Placement in the block: the parent (the first-started bird) is in the middle, and each linked bird, in start order, goes to a free cell next to the bird it is linked to, tried in this order: right, left, lower right, lower left, upper right, upper left. Not straight above or below: a line there would run through the upper bird's bubble and status lines. A diagonal cell whose line would cross the line between the other two birds of that 2x2 square in an X is skipped. From the 7th bird on, when no cell next to it is free, a bird goes to the nearest free cell and gets no line; the count at the parent's feet and the indent in Perch still show it is linked (Claude's own decision, the order of the six cells and the 7th bird on included). The user chose this placement over others shown as samples (a tree to the right, a tree downward, packing the birds into 3 columns and joining neighbours in the group): 「a1がよさそうやな」, then, after seeing the 3-column sample, 「a1」
    - The line has a contrasting outline so it reads over any desktop behind the transparent window, light or dark (Claude's own decision: at rest the window background is gone, so the line can't rely on it)
    - The lines are kept from standing out: seen only on a closer look, not at a glance (the user: 「線はもっと短く」「よはくがあいていいから」「つまりめだたせたくないからみじかくしろっていってるねんか」「よくみたらつながってるな、ていどでいいねん」). So a line is short and leaves room at both ends: it stops 18px off each icon's edge and is at most 36px long, centered between the two icons. It is thin and faint: a 1.2px core of the app's warm accent at 60% under which lies a 2.5px dark outline at 30% (Claude's own decision)
    - A linked bird that is itself watching gets its own linked birds next to it and lines to them the same way (Claude's own decision)
  - The watching (parent) bird's name is shown above the parent bird itself, wherever its cell is in the block; the block has no title of its own (the user's decision: a title on the block's top edge read as the name of the bird below it). Other birds inside show no name if they are in the parent's folder, and only the path relative to the parent otherwise
  - Dragging a bird inside the block moves the whole block
  - The number of linked sessions currently working is shown at the watching bird's feet
  - In Perch, linked rows are indented under the watching row, labeled with the path relative to the watching session's cwd (or the folder name if not under it). Rows in the same folder show no name
  - When a linked session gets a "?", the watching bird doesn't. The "?" only goes on the bird that is actually asking
- The indentation parent is whichever of the two linked sessions started first. Codex has no equivalent feature and is out of scope
- Caveat: the transcript format and `sessions/<pid>.json` are not public Claude Code specs (the sessions docs say "internal to Claude Code and changes between versions"). State detection and jumping to the terminal pane rely on them too. The desktop app's `local_…` ids, `hostSessionId`, the text of its `start_session` result (`Started session …`, `Proposed …`), the notes folder in a started session's first prompt, and the app's session records with their `spawnedFrom` (which proposal card a session came from) are not public specs either (read from Claude Code 2.1.321 in the desktop app)

## BYOK API keys

- Providers: OpenAI / Anthropic / Local (see "Local AI" below) for speech bubble summaries with the "?" and anger mark verdicts (see "Turn verdicts"), and the concierge. Each can be saved, deleted, and connection-tested from the settings screen
- Models for summaries and the concierge: OpenAI `gpt-5.6-luna` (reasoning effort none), Anthropic Claude Haiku 5.5. Both are the low-cost models meant for many small requests. They replaced `gpt-5.4-mini` and Claude Haiku 4.5, which were carried over from the first version without being chosen for the concierge's volume (the user: 「5.6lunaはどう」, then agreed to both: 「うん、」)
- API keys are stored in the macOS Keychain in the everyday build (the WebView's IndexedDB is a plaintext file readable by other processes of the same user). Windows and Linux use their own OS stores (see "Platforms"); "Keychain" below means the OS store there
- The store is decided in one place at launch. Everyday (`net.mohtech.tomarigi-desktop`), verify (`.verify`), and dev (`.dev`) all use the Keychain, so there is one store for keys in every build (the user, after dev's key was lost to the difference between the stores: 「なにかいい解決法ないかねっとでしらべて」, then chose this among Claude's proposals). `TOMARIGI_KEY_BACKEND=webview` still puts keys in IndexedDB, only to check the migration below
  - Before, dev used IndexedDB: an ad hoc signed binary's designated requirement is its cdhash, which changes every build (Apple TN3127), so the Keychain asked for permission after every rebuild
- verify and dev are signed with the local Apple Development certificate so rebuilding doesn't trigger permission prompts: its designated requirement is the identifier and the certificate, not the cdhash (TN3127). verify is signed by `tauri build` (`scripts/build-verify.sh`); dev by a cargo runner (`target.<triple>.runner` in `src-tauri/.cargo/config.toml`, macOS only) that signs `target/debug/tomarigi-desktop` with the dev identifier before each run. Tauri has no setting for signing `tauri dev` (tauri-apps/tauri#7930). The certificate is the first Apple Development identity in the Keychain, or `APPLE_SIGNING_IDENTITY`, as in `build-verify.sh`. ## Removing birds of ended sessions

- Birds are never removed because of elapsed time. A bird stays while its process is alive, however long it has been idle, and is removed right away once the process ends. The decision is based on whether the process is alive, not on the pane, so it doesn't depend on the terminal (closing a pane also ends the process inside it)
- Claude Code: match sessionId and pid from `<config>/sessions/<pid>.json` against `ps`; sessions whose pid isn't alive fade out on the next load. The same applies after `/exit`. Chicks go away with their parent
- A session whose transcript ends with a `continued-in` line (Claude Code moved the conversation to another session, e.g. a background process) is treated as ended even if its old process is still alive; the new session has its own bird
- Chicks (subagents) have no process of their own. While the parent is alive, a chick stays until the parent's transcript records its completion (the same record used for the chick's state), however long the chick has been writing nothing, and is removed once the completion is recorded
  - A chick started by another chick (`spawnDepth` 2 or more in its `meta.json`) has its completion recorded in the transcript of the chick that started it, not in the parent's. When the parent's transcript has no completion for such a chick, the transcripts of the chicks one depth shallower (all chicks when the depth is unknown, from older versions) are read the same incremental way and their records are added; `meta.json` has no id of the chick that started it, only `toolUseId` and `spawnDepth`. Nothing more is read while only depth-1 chicks run or every chick's completion is in the parent's transcript. Before, such chicks stayed working forever and held their parent, whose turn had ended, at working, so the concierge said 「ついばみ中」 and suggested nothing for it (the user, showing app-x finished and asking for a command to be run: 「これ、こんしぇるじゅがはんのうしてないのおかしくない？」; 10 of its 173 chicks were such grandchildren). Measured on that session (parent 70MB, chicks 214MB): the first scan takes about 390ms more and peak memory is unchanged, later scans read only what was appended (`tools/chick-scan-measure.ts`). `spawnDepth` and `toolUseId` are Claude Code's unpublished format (checked with 2.1.317) (Claude's own decision on reading the shallower chicks rather than trusting `meta.json`'s `finished`, which wasn't checked while running, or marking chicks done after 2 minutes)
- Codex: a running codex keeps `~/.codex/thread-writer-locks/<threadId>.lock` open, and threadId is the id at the end of the rollout file name (`rollout-<time>-<threadId>.jsonl`). `lsof` on that folder gives threadId → pid. The lock file stays after codex exits, so the file's existence says nothing; only whether a process has it open counts (measured with codex-cli 0.156.1)
- Codex with a shared app-server (measured with codex-cli 0.163.0; the README of codex-rs/app-server-daemon describes it the same way in 0.162.1): a TUI attaches to the `codex app-server --managed-daemon` already running for that `~/.codex`, or starts it. The app-server has no terminal, holds the locks of every TUI's threads, and keeps them after a TUI exits. A lock whose holder's command line has an `app-server` argument is read as shared, and its thread is matched to a TUI process instead: the processes named `codex` without `app-server` in the rollout's cwd (`session_meta.cwd`). A thread belongs to the TUI that started last before the thread was created (the time in its UUIDv7 id; measured: about 9 s after the TUI started) and ends when that TUI exits. TUIs seen earlier are remembered so a thread does not move to an older TUI in the same cwd. Of two threads for one TUI the one written last is alive; threads created before every known TUI there (resumed) take the TUIs left over, written last to started last. A click jumps to the matched TUI. A lock held by a codex itself (no shared app-server, or older versions) is read as before (Claude's own decision, from the user's request to keep older versions working). On Windows the holder's command line is not read, so locks are read as before
- Watched folders without `<config>/sessions` (older Claude Code) are not supported: there is no pid to check, so their sessions get no birds
- Avoid false removals: nothing is removed on a load where `ps` / `lsof` failed or where any `sessions/*.json` failed to parse. A bird is removed only after it is missing on two loads in a row
- Caveat: `thread-writer-locks` is not a public Codex spec, the same as `sessions/<pid>.json` for Claude Code

## Chicks that have finished

### Requirements

- A session that ended its turn asking the user is one the concierge tells the user to answer, unless a chick of it is really running
- A chick that has finished (a foreground chick whose result reached the parent, a background chick whose completion notice came) doesn't count as running
- Other ways a finished chick can look running are closed too, by how it is built rather than one place at a time: when Claude Code changes how a chick reports its end again, the chick stops counting as running after a bounded time instead of for as long as the parent lives

### Basic design

Decided by the parent session (A, B and C together; `meta.json`'s `finished` is not used, Claude's own decision: whether it goes back to false when a chick is resumed wasn't seen in real data):
- A. The chick's own transcript is a fact of its end: a chick whose last act is a hand-back to its caller (`SubagentHandback` and its result, nothing after) is done
- B. The parent's record of a hand-back (`<agent-message from="<id>">` with `[Subagent hand-back]`) is a completion record of that chick, next to `<task-notification>` and the Agent call's `tool_result`
- C. Whether a chick is running is one judgment (`isChickRunning`), used by holding back done, by what can wake the session and by the concierge's `chicks_working`; the parent's displayed state (`escalateWithChicks`) reads the chick's state, which already has the abandonment in it. A chick with no write for a while is abandoned, with the time chosen by what its transcript ends on

What happened: a parent called a foreground chick, the chick handed back its report, the parent sent it one more request with SendMessage, and the chick resumed and handed back again, 18 seconds after the parent's Agent `tool_result`. The only completion record read was that `tool_result`; the chick's later writes made it a resumed chick (`resolveChickDoneSignalAt`, more than `CHICK_SIGNAL_EPSILON_MS` after the record), and its tail, the hand-back's `tool_result`, is always working in `deriveState`. `escalateWithChicks` and `chicks_working` read the raw state, which has no abandonment, so the parent stayed working (「ついばみ中」) and the concierge didn't tell the user to answer it (the user: 「こんしぇるじゅがはんのうしてない」). Claude Code writes, when a chick hands back: in the chick, a `SubagentHandback` tool_use and its `tool_result` (`{"success":true,"message":"Report delivered to your caller."}`); in the parent, a `queue-operation` (enqueue, then remove) whose content starts `<agent-message from="<id>">\n[Subagent hand-back]`, `<id>` being the chick's file name without `agent-`; on a SendMessage resume, the SendMessage `tool_result` says `Resumed agent. Its final report follows this JSON` (its tool_use_id is SendMessage's, not the chick's, so it isn't used)

### Detailed design

How long a chick goes without writing while it is still running, counted on the chick transcripts of this machine (both config dirs, 10,103 files): gaps of more than 10 minutes between two lines with a time that are conversation (assistant / user / tool_result):
- after a tool call (a tool running): 12, 10.0 to 66.8 minutes (10.0, 10.0, 12.2, 13.9, 26.0, 30.0 ×6, 66.8); every one went on with that tool's result. Abandoning these at 10 minutes, as `isChickRunning` did for done and wakes before this change, would count them as stopped
- after a tool result, a user line or the assistant's text: 28, 10.0 to 202.1 minutes; 27 went on with a new user line (the chick had stopped and was resumed), 1 with another tool's result 30.0 minutes later (calls made in parallel: the tail was one call's result while another call still ran)

So the abandonment time depends on whether a tool is still open, not on the tail's kind alone:
- `TailInfo.toolOpen` (new, `src/lib/transcript.ts`, from `trackTools` in `src/lib/transcript-chicks.ts`): within the tail window, a tool_use with no `tool_result` for its id after it. It covers the parallel case above, where the tail's kind is `tool_result`
- `TailInfo.handedBack` (new, A): the last conversation line with a time is the `tool_result` of a `SubagentHandback` tool_use, or that tool_use itself (Claude Code writes the result about 0.1 to 0.5 seconds later). Any later conversation line (the resume's user line, the assistant) clears it. Read only from chick transcripts (`includeSidechain`)
- `collectChickSignals` (B): a `queue-operation` whose content matches `^<agent-message from="([^"]+)">` and contains `[Subagent hand-back]` sets the signal of that id at the line's time, the latest winning as for `<task-notification>`. Both the enqueue and the remove carry it, so on a resume the remove comes after the chick's last write. The id is the chick's task-id (its file name), so `resolveChickDoneSignalAt` finds it and the chick is removed from the parent as a completed one (see "Removing birds of ended sessions"). The whole-transcript scan (`scanChickSignals`) parses only lines containing one of `CHICK_SIGNAL_MARKERS`, kept next to `collectChickSignals` so a new kind of record is added to both; before, it filtered on `<task-notification>` and `tool_result` by itself, and on the real transcript the hand-back records, out of the parent's tail window by then, were dropped
- `deriveState(isChick)`: after `closed`, `handedBack` gives done (dozing past `DOZE_MS`) as a completion signal does. Then, with no signal: a chick with no write for `CHICK_ABANDONED_MS` (10 minutes) and no open tool is dozing; one with an open tool is dozing after `CHICK_TOOL_ABANDONED_MS` (new, 2 hours: above the longest 66.8 minutes seen, so a chick that died in a tool doesn't hold its parent forever; Claude's own decision). Abandonment is in the state, so every reader of the state sees the same answer
- `deriveSdkChickState`: the same `CHICK_TOOL_ABANDONED_MS` for a tool still open (it already gives done after `CHICK_TEXT_DONE_MS` otherwise)
- `isChickRunning(chick)` (`src/lib/session-activity.ts`) reads the state alone (not done and not dozing); the `sinceMs` check moves into the state above. Its readers: `deriveDoneEvent`, `wakeSourceOf`, and the concierge's `chicks_working` (`src/lib/concierge.ts`), which counted `state === "working"` directly. `escalateWithChicks` reads the chick's state itself and skips dozing, so an abandoned chick doesn't raise its parent either
- `isChickRunning` is "not done and not dozing". A subagent chick is never waiting (`deriveState` gives waiting only to a session that isn't a chick), so it is the same as "working". What changes for done and wakes is the abandonment: a chick with a tool open now holds done back and keeps the session wakeable up to `CHICK_TOOL_ABANDONED_MS` (2 hours) without a write, where it used to be `CHICK_ABANDONED_MS` (10 minutes)
- What the user sees: a chick abandoned this way shows dozing, and its parent no longer shows working because of it

Tests:
- `tests/chick-handback.test.ts` (readTail): `handedBack` set on a chick tail ending on the hand-back's result and on the hand-back's tool_use alone, cleared by a later user line; `toolOpen` for a tail of one result while another parallel call has none; `collectChickSignals` takes the hand-back `queue-operation` by its id and ignores an `<agent-message>` without `[Subagent hand-back]`
- `tests/chick-handback.test.ts`: the scene above with relative times (Agent call, hand-back, parent `tool_result`, SendMessage, chick resumes, hand-back 18 seconds after the parent's `tool_result`): the chick is done, and with only the parent's records (no `handedBack`) it is done too
- `tests/session-state.test.ts` (`deriveState`): a chick on `tool_result` with no write for 10 minutes and no open tool is dozing; with an open tool it stays working until 2 hours
- `tests/chick-handback.test.ts` (concierge payload): a parent ending its turn on a question with that chick gives no `chicks_working` and `needs_reply` true; `escalateWithChicks` keeps the parent's own state
- `tools/chick-scan-measure.ts --at <time>` runs the functions `scanSessions` runs (`readTailCached`, `scanChicks`, `chickListsOf` in `src/lib/session-chicks.ts`, `birdStateOf` in `src/lib/bird-state.ts`, `buildConciergePayload`) on a real transcript as of a time (chick states, the parent's own and displayed state, `chicks_working`), on a copy of the transcripts cut at that time. Claude Code's waiting status and the started proposal cards aren't read there. On the case above, at the time the user reported it: before, that chick working, the parent displayed working, `chicks_working=1`; after, the chick dozing and completed, the parent dozing, `chicks_working=0`

## Side chats and forked sessions of the Claude desktop app

Issue #13. The user: 「claudecodedesktopで、サイドチャットbtwがコンシェルジュにのこりつづけるもんだい」, then, about a side chat that had stopped: 「うごいてないのについばみ虫になっとるわ」.

Facts (checked on this machine on 2026-11-14 with Claude Code 2.1.321 run by the desktop app): a side chat (btw, `Cmd` `;` in the desktop app) runs as a session of its own. It has its own process (`entrypoint` `claude-desktop`), its own `sessions/<pid>.json` and its own transcript, and that transcript starts with a copy of the main session's lines (`sessionId` still the main session's; 704 of 755 lines in the side chat checked). The process stays alive after the side chat's turn ends, so its bird stayed, done and then dozing, in the birds, Perch and the concierge. The copied lines were read as the side chat's own, so it was linked to a session its main session had talked with, and the concierge status line showed it as working (watching) while it wrote nothing. The desktop docs say side chats aren't saved to disk (code.claude.com/docs/en/desktop); the real files differ. The CLI's `/btw` makes no session or transcript (code.claude.com/docs/en/commands), so it has no bird and nothing here applies to it (from the records; not checked by typing `/btw`).

### Requirements

- A side chat gets no bird and appears nowhere: not in the Garden or Perch, not in Recent activity, no sound or voice, no speech bubble (and so no summary request), and not in the concierge (status lines, facts sent to the provider, advice). This holds from the side chat's start, while it answers, after it finishes, and while its process lingers (the user's decision, choosing this over showing it only while it answers or counting it as a chick of the main session)
- The main session is not shown as watching its side chat, and a side chat is not linked to any session
- A session whose transcript starts with another session's copied lines (a side chat, or a session another session started as a fork) is judged only from its own lines: its state, its Recent activity events and sounds, its speech bubble, its links (Watching) and its first prompt (Sessions started by another session) never come from the copied lines. Until it writes a line of its own it shows as a session that has just started, not as its parent's last turn (Claude's own decision: the copied lines are what made the idle side chat show as working, and a fork read from them could show its parent's turn as its own, with its sound and summary). Chicks are not judged so: every line of a subagent's transcript carries the main session's `sessionId`
- Checked by table tests built from the real records: a side chat the user typed in and one closed without typing are excluded; the main session, sessions started by `start_session`, sessions started as forks, ordinary sessions and chicks keep their current birds, states and links; a forked transcript's state, events, bubble, links and first prompt come from its own lines only, and a fork that hasn't written its own line yet doesn't show its parent's turn

### Basic design

- A side chat is told by the desktop app's record of the session (`claude-code-sessions/<…>/<…>/local_<id>.json`, the records read for jumping to the desktop app and for proposal cards) having `spawnedFrom.btw` true. The record is reached from `hostSessionId` in `sessions/<pid>.json` or from `cliSessionId`. On this machine 2 of 346 records have it, both side chats; the 238 sessions started by `start_session` and the 3 started as forks don't. `forkedFromSessionId` alone is not used (forks have it too), and neither is the name (`btw: …` is an automatic title). Like the other desktop app files, this record is not a public spec
- Side chats are dropped where Claude Code sessions are listed, before state is derived, so every surface (current and future) misses them in one place and no request is made for them. A session whose record isn't found or can't be read yet is shown as usual (no hiding without the mark); its bird goes away on the load that reads the mark
- A transcript line is the session's own when its `sessionId` is the session's id (the transcript's file name). Lines with another `sessionId` are skipped wherever a main transcript is read (state, events, bubble, links, first prompt), not in chicks' transcripts

### Detailed design

Written by the session that implements it, after reading the code; may be changed (Claude's own decisions).

Facts behind it (2026-11-14, this machine): of the 7,286 main transcripts under `~/.claude/projects` and `~/.claude2/projects`, exactly 5 have lines whose `sessionId` isn't the file name: the 2 side chats and the 3 forks. In all 5 the copied lines come first as one block and none follow the session's own (resumed and ordinary sessions have none). A subagent's transcript (`<id>/subagents/agent-*.jsonl`) has the main session's `sessionId` on every line, so the own-line rule applies to main transcripts only, never to chicks. In both side chats the record's file name is `local_<cliSessionId>.json` (its `local_` id is the transcript's id). The record exists before the side chat's `sessions/<pid>.json` (the record's `createdAt` about a second before the process's `startedAt`).

Telling a side chat (Rust, `src-tauri/src/focus/desktop.rs`):
- `is_side_chat_record(record)`: `spawnedFrom.btw` is `true` (a bool; any other value or a missing key is no)
- `side_chats(dir, host_ids)`: finds each `local_<id>.json` by its file name two folders under `dir` (the folders are listed, no file but the ones asked for is opened, unlike `each_record`, which reads every record), and returns `SideChatScan { answers, reliable }`: `answers` has `(id, is a side chat)` for each record read, and an id whose record isn't there or can't be read or parsed is left out. `reliable` is false when `dir` can't be listed (the TS side doesn't use it: an id left out is asked again either way)
- Command `desktop_side_chats(host_ids)`: runs it off the main thread on the desktop app's data folder (`sessions_dir`)

Dropping it (TS):
- The cache `sideChatByHostId: Map<string, boolean>` in `src/lib/session-store.ts`. A record's `spawnedFrom` is written when the session is made and doesn't change, so an answer is kept for good and each id is read once; an id left out of `answers` isn't kept, so it is asked again on the next load. It isn't pruned: one boolean per desktop session seen while the app runs
- `src/lib/side-chats.ts` (new, pure): `hostIdsToAsk(live, cache)` gives the live sessions' `hostSessionId`s not answered yet. `isSideChat(sessionId, live, cache)` says whether a transcript is one: its live session's `hostSessionId` is answered true, or, without a live session, `local_<its id>` is (a side chat's id form above; a transcript of another kind finds no record and costs one missed name lookup per load during the 15 seconds of grace)
- In `claude.prepare` (`src/lib/agents.ts`), after `live_sessions`: ask `desktop_side_chats` for `hostIdsToAsk` (no call when the list is empty, which is every load after the first in steady state), fill the cache, then remove the side chats from `listing.liveSessions` (`pidBySessionId` keeps them: `list` uses the pid only to pick candidates and skips a side chat before reading its tail). Removing them from `liveSessions` keeps them out of watching links (`peerLookup` can't resolve a name or `local_` id to them, so the main session can't watch one) and out of `scan_peer_names`
- In `claude.list`, a transcript for which `isSideChat` is true is skipped before `readTailCached`, like `sdk-cli` is skipped after it, but without reading the tail: no bird, no state, no event, no summary, no concierge fact. A transcript with no live session that is a candidate only by `NEVER_SEEN_GRACE_MS` (new, not yet shown) is asked about in `list` itself, right before that skip, by `local_<its id>` (one `desktop_side_chats` call per such transcript not answered yet; they are rare and only for 15 seconds), so a side chat whose `sessions/<pid>.json` lags its transcript is still dropped on its first load
- A bird already shown (the record was unreadable on an earlier load) is not in `found` on the load that reads the mark, so it is gone from `scanState.trackedIds` and every surface on that load. Leaving makes no sound or readout: those come only from events derived for entries in `found`, and a bird whose process ends has no event of its own either (`settleLiveness` only logs `[live] ended`). What it already left in Recent activity (`sessionEventCache`) is removed on that load by `forgetSideChats(ids)` in `src/lib/side-chats.ts`, as `settleLiveness` removes an ended session's rows; the event log of the debug log screen keeps them, as it does an ended session's
- No change for the CLI, Codex or other agents: they have no desktop record, and a live session without `hostSessionId` is never asked about

Reading only own lines:
- Rust `scan_peer_names(path, start)`: the own id is the path's file stem. A line whose `sessionId` is a string other than it is skipped for everything the scan reads (the first prompt, `agent-name`, the SessionStart hook's time, the last typed turn, and every trace). A line without `sessionId` is read as before. The check is made on lines already parsed (the scan parses only lines that may carry something), so lines that are skipped today cost nothing more. `start` is unchanged: an incremental read of a fork reads only own lines anyway, since copied lines come first
- TS, every read of a main Claude Code transcript (`src/lib/transcript.ts`, `src/lib/transcript-chicks.ts`) takes the own id and skips a line whose `sessionId` is a string other than it, before anything is read from the line: `readTail` / `readWindow` (state, tool, events and their texts for the bubble and its summary, cwd, entrypoint, last write time, chick signals, background tasks, peer names, first prompt, `continued-in`), `readEventsInRange` (the gap read for user messages, `src/lib/session-tail.ts`) and `scanChickSignals` (the whole-file chick ledger, `src/lib/transcript-chicks.ts`, called from `scanChicks` in `src/lib/session-chicks.ts`). One predicate `isForeignLine(entry, ownSessionId)` (`src/lib/transcript-entry.ts`) decides it for all three. It is an option (`ownSessionId`) that only the main transcript's reads pass, from the file stem (`claude.list` through `readTailCached`, and the chick ledger read with the main transcript's id); chick transcripts are read without it (`includeSidechain`), so their lines are read as before
- A fork with no timestamped line of its own yet reads as an empty tail (`kind` `unknown`, no `lastEventAt`), the same as a session that has just started: `deriveState` shows it working while its file was written in the last few seconds and dozing after `DOZE_MS`, never done, so no done event, chirp, readout or summary comes from its parent's turn. `readTail` widens its window to `MAX_TAIL_BYTES` looking for a timestamped line, as it does for any tail without one; for a fork this lasts only until its first own line

## Jumping to the terminal pane

- Clicking a bird (Garden) or a row (Perch, Recent activity) jumps to the terminal pane where that agent is running. A chick's row jumps to its parent's pane
- Mapping: session → pid (see "Removing birds of ended sessions" and "Agents" for how each agent's pid is found) → tty and the chain of ancestor processes from `ps` → the terminal app that owns an ancestor process (by bundle id; an iTerm2 `iTermServer` process left under launchd counts as iTerm2) → that terminal's adapter focuses the pane whose tty matches. Only the adapter of the owning app is called
- tmux: when the tty is a tmux pane (`tmux list-panes -a -F '#{pane_tty} #{pane_id} #{session_name}'`), the pane is selected with `tmux switch-client -c <client tty> -t <pane id>` on the client attached to that session that was used last (`client_activity`), and the jump continues with that client's tty as the target, so the outer terminal is focused by its own adapter. Sockets other than the default (`-L` / `-S`) are taken from the command line of the tmux server among the ancestors, which keeps the arguments of the client that started it. The tmux binary is looked up in fixed install places (`/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin`, `/usr/bin`), not from the path `ps` shows
- Adapters (macOS):
  - Ghostty: every running instance (bundle id `com.mitchellh.ghostty`) is asked by pid through ScriptingBridge (`SBApplication applicationWithProcessIdentifier:`) for the terminal whose `tty` matches, then `focus` + activate. `tell application "Ghostty"` reaches only one of several instances (`open -n`), so osascript is not used
  - iTerm2: the session whose `tty` matches is selected, then its tab, then its window (AppleScript dictionary)
  - Terminal.app: the tab whose `tty` matches becomes the selected tab of its window, the window becomes frontmost with index 1, and the app is activated
  - WezTerm: `wezterm cli list --format json` gives `tty_name` → `pane_id`, then `wezterm cli activate-pane --pane-id <id>`, and the app is brought forward through LaunchServices (`NSWorkspace openApplicationAtURL:` with `activates`; WezTerm has no AppleScript dictionary, and `NSRunningApplication activate` alone lost to another app coming forward at the same time). The binary is taken from the bundle of the running app (`NSRunningApplication.bundleURL`)
  - kitty: only when the user has set `allow_remote_control` and `listen_on` in `kitty.conf`; then `kitten @ --to <socket> focus-window --match pid:<pid>` with the pid of the ancestor kitty started (the shell). The socket is the unix socket the kitty process listens on (`lsof -a -U -p <pid>`), and `kitten` comes from the app bundle. Tomarigi never edits `kitty.conf`; without the setting, kitty is only activated. README tells kitty users which two settings to add

## Agents

- Each agent is one adapter in one place: list sessions under its root → read the tail into the shared `TailInfo` → liveness (which sessions have a live process, and their pid) → the pid used for jumping. State (`deriveState`) and everything after it don't know which agent a session is
- Supported agents and where they are read (each standard location is watched when it exists, the same as the defaults in "Watched folders"):
  - Claude Code: `~/.claude/projects`. pid from `<config>/sessions/<pid>.json`
  - Codex: `~/.codex/sessions`. pid from `thread-writer-locks`, or the TUI matched to the thread when the shared app-server holds the lock (see "Removing birds of ended sessions")
  - Qwen Code: `~/.qwen/projects/<project>/chats/<sessionId>.jsonl`. pid from `<sessionId>.runtime.json`
  - GitHub Copilot CLI: `~/.copilot/session-state/<sessionId>/events.jsonl`
  - Gemini CLI: `~/.gemini/tmp/<project>/chats/session-*.jsonl`; cwd from `<project>/.project_root`, or else `~/.gemini/projects.json`
  - OpenCode: `~/.local/share/opencode/opencode.db` (SQLite, opened read-only on the Rust side); cwd from `session.directory`. Subagent sessions (`parent_id` set) get no bird of their own, like Codex's internal rollouts (Claude's own decision)
  - Cursor CLI: `~/.cursor/projects/<cwd slug>/agent-transcripts/<id>/<id>.jsonl`. Its lines have no time and no cwd: a line's time is the file's modification time on the load that first read it (the only exception to not using mtime), and the cwd is the matched process's (the folder name is the cwd with each run of characters other than letters and digits turned into one `-`, and `-` at either end dropped). The process is the one whose command line has `cursor-agent/versions/<v>/index.js` (or whose program is `cursor-agent`), except the `worker-server` that cursor-agent 2026.10.18 starts and leaves running after the session ends. The prompt is the part inside `<user_query>`, and a `[REDACTED]` paragraph (hidden reasoning that 2026.10.18 appends to the reply) is not shown (Claude's own decision)
- Agents without a pid file: a session is alive while a process of that agent (matched by the program in `ps axww -o pid=,tty=,etime=,command=`, either the binary or the script run by node / bun) runs with the session's cwd (`lsof -a -d cwd -p <pid> -Fn`). Processes without a tty are ignored. When N processes of one agent share a cwd, the N sessions in that cwd written since that agent's processes started, latest first, are alive (Claude's own decision). So a process that was started but hasn't written yet shows no bird, the same as Claude Code before its first message. Jumping uses the matched pid; when several sessions share a cwd, the session written last gets the newest process and the others do nothing on click (Claude's own decision)
- The same safeguards as "Removing birds of ended sessions" apply: nothing is removed on a load where `ps` / `lsof` failed, and a bird is removed only after it is missing on two loads in a row
- "Needs reply" is shown only where the agent's transcript records that it is waiting on the user; agents with no such record show working or done instead. Recorded: a call to the agent's question tool that has no result yet (Qwen Code `ask_user_question` / `exit_plan_mode`, Gemini CLI and Copilot CLI `ask_user` / `exit_plan_mode`, OpenCode `question`). Permission prompts are not recorded by any of them, so they show working
- Watching (cross-session links) is Claude Code only
- Not supported: Aider (its history is Markdown with no record of turns ending, so no state can be derived). Kiro CLI and Amp are deferred until their session files are confirmed on a real install (the only sources found disagree or are unofficial; Claude's own decision). Resume when a session file from each is available to read
- Caveat: none of these transcript formats is a public spec, the same as for Claude Code and Codex. Qwen Code's `runtime.json` is the exception (written for outside tools)

## Readout voice (local TTS server)

The readout can use a TTS server running locally (or on the LAN) in place of the system's voice (the user: 「ttsさーばーをしていできるようにしようか。がいぶapiかあるいはローカルか」, then, after a report on the differences, 「いったんろーかるげんていにしようか」). Cloud TTS APIs are out of scope for now (the user's decision). Facts behind the choices (checked 2026-11-25 in the official docs): OpenAI's `/v1/audio/speech` models (`tts-1`, `tts-1-hd`, `gpt-4o-mini-tts`) shut down on 2027-01-06, and their successor runs only on the Realtime API; VOICEVOX's terms allow commercial use and require a credit that shows VOICEVOX was used (voicevox.hiroshiba.jp/term/), with each voice library's own terms on top.

### Requirements

- Readout voice in the settings: "System voice" (today's readout, the default) or "Local server". A user who never touches it hears what they hear today
- Two kinds of local server, chosen in the settings (Claude's own decision, from the report: these two cover the maintained local servers found):
  - OpenAI-compatible (`POST <base URL>/audio/speech`): Kokoro-FastAPI, mlx-audio and other servers with that endpoint
  - VOICEVOX-compatible (`POST <base URL>/audio_query` then `POST <base URL>/synthesis`): VOICEVOX ENGINE and AivisSpeech Engine
- Everything that is read aloud today goes through the chosen voice: the done readout (with its summary or fallback), needs reply, the Concierge tab's suggestions, and the events read when a Concierge request fails. What is read, its order (display name, then the body, as two utterances), the "Read aloud" setting, the menu bar item and the readout volume work as they do now. Two readouts never play over each other; they play one after another in the order they were queued, as speechSynthesis's queue does today
- The readout is never lost: when the server can't be reached, answers with an error, or gives no audio within the wait below, that utterance is read with the system voice (and not with the server's voice later). Audio that arrives after the wait is dropped (Claude's own decision: the readout is the signal that a turn finished)
- VOICEVOX-compatible servers read Japanese only, so while the UI language isn't Japanese, readout uses the system voice even when such a server is chosen, and the settings say so under the choice (Claude's own decision)
- The settings let the user hear the voice before relying on it: a "Test" plays a short sample through the server with the chosen voice, and says what went wrong when it fails (not running, wrong kind of server, no such voice)
- Where the system has no speech engine (some Linux builds), "Read aloud" can be turned on while a local server is chosen; without the fallback voice, a failed utterance is skipped and logged (Claude's own decision)
- When the server is VOICEVOX ENGINE itself, the settings show the credit 「VOICEVOX:<voice name>」 next to the chosen voice. Not for AivisSpeech Engine or another VOICEVOX-compatible server: the credit is required by VOICEVOX's terms, AivisSpeech's engine needs no credit, and its voices aren't VOICEVOX's (Claude's own decision, from the terms; may be changed; the implementing session pointed out that a credit on every VOICEVOX-compatible server would be wrong for AivisSpeech). Which engine it is comes from what the server says about itself (e.g. its engine manifest), not from the port

Pass/fail:
- Unit tests (scenes) for the choice between server and system voice: server answers in time / error / timeout / late audio dropped / English UI with VOICEVOX / no system voice / queue order with several events
- Run against real servers on this Mac: one OpenAI-compatible (Kokoro-FastAPI or mlx-audio) and one VOICEVOX-compatible (VOICEVOX or AivisSpeech). The app log shows each request, its time, and whether the server's audio or the system voice was used. The sound itself can't be checked by an agent; the user listens to the result (done, needs reply, Concierge tab, Test)

### Basic design

- Settings, saved with the other settings (not secrets, no key; Claude's own decision, as for the Local AI provider): voice source (system / local), server kind (OpenAI-compatible / VOICEVOX-compatible), base URL, and voice; for OpenAI-compatible also the model. Default base URLs: `http://localhost:8880/v1` (Kokoro-FastAPI) for OpenAI-compatible, `http://localhost:50021` (VOICEVOX) for VOICEVOX-compatible; AivisSpeech's is `http://localhost:10101`, typed by the user (Claude's own decisions)
- The base URL follows the Local AI rule (http(s), no user name or password, `?`, or `#`), checked in the settings screen and in Rust with the same rule. Any host is accepted
- Voices and models are picked from the server's lists when it has them (VOICEVOX `/speakers`; OpenAI-compatible `GET <base URL>/audio/voices` and `GET <base URL>/models`, which not every server has), and can be typed when the list can't be fetched. Editing the URL clears the list and the choice, as for the Local AI provider, so a voice of another server can't be saved with the new URL
- Requests are made from Rust, not from the WebView (Claude's own decision): the same path as the Local AI provider, and the local servers' CORS defaults (VOICEVOX allows only localhost-like origins) don't apply. The audio is passed to the page and played there, so the readout volume applies as it does now
- Wait for the server's audio: 5 seconds per utterance, counted from sending the request (Claude's own decision). The done readout's 5-second wait for the summary comes before it and is unchanged. A first request while a server loads its model may take longer and is then read with the system voice
- Nothing is written to disk: audio is played from memory and not cached. Each request writes one line to the app log (kind, time taken, server or fallback, and the error if any)
- Out of scope: cloud TTS APIs (OpenAI, ElevenLabs, Google, Azure), keys for TTS, Style-Bert-VITS2 and Piper (their own APIs; Piper's official voices have no Japanese)

### Detailed design

Written by the session that implements it, from the code as of 29842f2. All of it is Claude's own decision and may be changed.

Settings (`src/lib/readout-voice.ts`, new):
- `ReadoutVoice = { source: "system" | "local"; local?: LocalTtsConfig }`, `LocalTtsConfig = { kind: "openai" | "voicevox"; baseUrl; voice; voiceLabel?; speaker?; model?; voicevoxCredit? }`, saved under the key `readoutVoice` in the settings store (`kvGet` / `kvPut` of `src/lib/settings-store.ts`). Missing or broken data loads as `{ source: "system" }`, so a user who never touches it keeps today's readout
- The local config is kept when the source goes back to "System voice", so switching back and forth doesn't retype it. `source: "local"` with no saved local config reads with the system voice (nothing to send to)
- `voiceLabel` is the voice's name as the list showed it (VOICEVOX: the speaker's name and the style, e.g. 「四国めたん（ノーマル）」, whose value is the style id). It is saved, with `speaker` (the speaker's name alone), so the credit 「VOICEVOX:<speaker>」 and the saved card can be shown without asking the server
- `voicevoxCredit`: whether the server is VOICEVOX ENGINE itself, from its `GET <base>/engine_manifest` read with the voice list: true only when the manifest's `brand_name` is `VOICEVOX` (AivisSpeech Engine says `AivisSpeech`). A manifest that can't be read gives false, so no credit is shown for a server that doesn't say it is VOICEVOX ENGINE. Saved with the config; whether the two engines really say this is checked on both real servers before it is final
- `DEFAULT_TTS_BASE_URL = { openai: "http://localhost:8880/v1", voicevox: "http://localhost:50021" }`. Changing the kind in the form puts the other kind's default URL in the field when the field still holds the previous kind's default or is empty; a URL the user typed stays
- `routeOf(config, lang, systemAvailable)`: `"server"` when the source is local, a local config is saved, and (kind is openai, or `lang` starts with `ja`); else `"system"` when `systemAvailable`; else `"none"`. One function, read by the queue and by `readoutAvailable()`

The queue (`src/lib/readout-queue.ts`, new), used only while the source is local:
- `ReadoutQueue` with its outside world passed in (`synthesize(text, lang) → Promise<audio bytes>`, `playAudio(bytes, volume, signal) → Promise<void>`, `speakSystem(text, lang, volume) → Promise<void>`, `stopSystem()`, `wait(ms) → Promise<void>`, `now()`, `log(line)`, `route(lang)`, `volume()`), so tests drive it scene by scene without timers or a WebView
- `enqueue(text, lang, tag)`: for a server route, the request is sent at once (requests of queued utterances run in parallel; playback stays in order). Each item settles to "server audio", "system voice" or "skip" at the first of: audio arrived, the request failed, `TTS_WAIT_MS` (5,000) passed since it was sent. Audio arriving after that is dropped (the item already settled to the system voice). With no system voice, a failed item settles to "skip"
- One player loop: takes the head, waits for it to settle, plays it, and only then takes the next, so two readouts never overlap and the order is the order of `enqueue`. The system voice inside the queue is `speechSynthesis.speak` of one utterance, awaited to its `end` / `error`, with a cap of 2 seconds plus 250 ms per character (in case `end` never comes; Claude's own decision) so a lost event can't stop the queue
- The volume is read when an item starts playing (today's `voiceVolume` rule)
- `cancel()`: empties the queue, aborts the generation's `AbortSignal` (the one handed to every `playAudio` of that generation; this stops the audio whether it is still waiting to resume / decode or already sounding), `speechSynthesis.cancel()`, and bumps a generation so answers of requests still on their way are dropped. A new generation gets a new signal. `play()` also checks the signal before it falls back to the system voice after `playAudio` throws, so a cancel never ends in the system voice reading the item
- One app log line per server request, when it settles: `[voice] for=<done|waiting|concierge|test> server=<openai|voicevox> ms=<n> used=<server|system|none>` plus ` error=<timeout|network|http-<status>|not-audio|audio>` when it failed. The text and the base URL aren't logged

`src/lib/voice.ts` (changed):
- `setReadoutVoice(config)` sets a module variable, like `setVoiceVolume`, so a change applies to the next utterance even while a done waits for its summary
- `enqueueUtterance(text, lang, tag)`: source system → `speechSynthesis.speak` as now (unchanged path); source local → `ReadoutQueue.enqueue`. `speakEvent` / `speakDoneEvent` / `speakSuggestions` pass the tag (`done`, `waiting`, `concierge`); the Concierge tab's failure readout goes through `speakEvent` / `speakDoneEvent`, so it is tagged by its event type
- `readoutAvailable()` = `speechAvailable()` or `routeOf(...)` gives `"server"` for some language (local source with a saved config). It replaces `speechAvailable()` at the gates in `voice.ts`, in `App.tsx` (`canSpeak`: the "Read aloud" checkbox, its note, the volume slider) and in `src/perch/voice-menu.ts` (the menu bar item)
- `cancelSpeech()` cancels both the native queue and `ReadoutQueue`. Changing the voice source in the settings calls it, so a readout queued for one path doesn't play over the other
- Playback (`playAudio(audio, volume, signal)`): it returns without making a source if `signal` is aborted at its start or after the `resume()` wait or `decodeAudioData`, and stops its source when `signal` aborts while sounding; there is no module-wide "current source". `decodeAudioData` and an `AudioBufferSourceNode` through its own `GainNode` (the readout volume) on the AudioContext of `src/lib/chirp.ts` (new export `audioContext()`), so it isn't under the chirp volume. When no context exists yet it calls `primeAudio`; where the WebView wants a user action first, the context doesn't run, playback fails, and the utterance is read with the system voice (`error=audio`), the same constraint speechSynthesis has

Rust (`src-tauri/src/tts.rs`, new; registered in `lib.rs`):
- `tts_speech(kind, base_url, model, voice, text, timeout_ms) → raw bytes` (`tauri::ipc::Response`, so the audio isn't passed as JSON numbers)
  - openai: `POST <base>/audio/speech` with `{ model, input, voice, response_format: "wav" }` (WAV: every WebView decodes it)
  - voicevox: `POST <base>/audio_query?text=<text>&speaker=<voice>`, then `POST <base>/synthesis?speaker=<voice>` with that query as the body. Both within one deadline of `timeout_ms`
  - URLs from `local_url` of `keys.rs` (made `pub(crate)`), so the base URL rule is the same as Local AI's; `local_client` (no redirects) and `local_error` (no URL in errors) are reused
  - The answer must be audio (`content-type` `audio/*`, or the bytes start with `RIFF`, `ID3`, `OggS`, `fLaC` or an MP3 frame), else `not-audio` (a server of another kind, e.g. a 200 HTML page)
  - Errors as `<kind>: <detail>`: `timeout`, `network`, `http-<status>: <server's message, at most 200 chars>`, `not-audio`
- `tts_list(kind, base_url, path) → HttpReply`, `path` one of `speakers` and `engine_manifest` (voicevox), `audio/voices` and `models` (openai), 10-second timeout like `local_models`
- Rust tests: the URLs and bodies of both kinds, the audio check, and that an unknown `path` is refused

`src/lib/tts-server.ts` (new): the calls to those commands and what JS reads from them:

## Settings by an AI agent (MCP)

The user's coding agent (Claude Code and others that speak MCP) can read and change this app's settings, so the user can say 「VOICEVOX にして」 instead of filling the settings screen (the user: 「せっていがめんどうだから、aiに設定をさせる口ってつけれる？」; of a local MCP server, a CLI subcommand, a file the agent writes, and a URL scheme, Claude recommended MCP because the agent gets the result back, e.g. whether the connection test passed; the user: 「すすめて」). The other three were not chosen (Claude's own decision, in the same recommendation): a CLI and a file return no result to the agent, and a URL scheme can be fired by any web page's link.

### Requirements

- In the settings, "Let an AI agent change settings" (off by default; Claude's own decision: it opens a port). Turning it on starts the server and shows the one command to register it with Claude Code, with a copy button. The user runs that command once; after that the agent sees the app's tools whenever the app runs
- What the agent can do, as tools:
  - Read the current settings (everything on the settings screen except API keys), and which options each one has
  - Change any of those settings: the summary provider choice, Local AI's base URL and model, the readout voice (source, server kind, base URL, voice, model), "Read aloud" and its volume, mute and the chirp volume, the window mode, icon sets per project, the watched folders and their labels
  - Read the lists the settings screen reads: the Local AI models, the TTS server's voices and models
  - Run the tests the settings screen runs: the Local AI / provider connection test and the readout voice's "Play a sample", and get their result (passed or why not, and the time taken), so the agent can tell whether the setup works
- A change by the agent goes through the same checks as the settings screen (the base URL rule, a model / voice that must be chosen, and so on) and is refused with the same reason in words when it fails. Nothing the screen can't save can be saved this way
- API keys are never read or written through it (Claude's own decision: what the agent sends stays in its transcript and logs). When a change needs a key that isn't saved, the tool says so and the user pastes it on the settings screen
- The user sees what the agent changed: each change made by the agent shows a short note in the app (what changed, from what to what) and is written to the app log; the settings screen, if open, shows the new values at once. No confirmation dialog per change (Claude's own decision: the user asked the agent to do it, and a dialog per change brings back the bother this removes)
- Only the user's own agents can use it: it listens on 127.0.0.1 only, and a request without the token shown in the registration command is refused. The token can be renewed from the settings, which makes the old command stop working
- When the app isn't running, the agent's tool call fails to connect; the tool descriptions tell the agent to ask the user to start Tomarigi
- Turning it off stops the server at once

Pass/fail:
- With the app running and the setting on, a real Claude Code session registered with the shown command can: list the settings, switch the readout voice to a VOICEVOX server and play a sample (result returned), set Local AI's URL and model and run its connection test, add and remove a watched folder; each change shows in the app and in the app log
- A wrong value (malformed URL, unknown voice) is refused with the screen's reason; a request with no or a wrong token is refused; with the setting off nothing listens on the port
- Unit tests for the shared checks (each setting's rule is one function used by the screen and the tools) and for the tool layer with fakes

### Basic design

- Transport: MCP over Streamable HTTP at `http://127.0.0.1:<port>/mcp`, bound to 127.0.0.1 only. Default port 4844 (this repo uses 4842 and 4843 for development; 4844 was free among the author's projects); when it is taken, the settings say so and the port can be changed there (Claude's own decisions)
- The registration command shown: `claude mcp add --transport http tomarigi http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <token>"`, with `--scope user` so it works from every project (Claude's own decision). The token is random (at least 128 bits), kept with the app's secrets (the Keychain / keyring, like the API keys), never logged
- One source of truth for settings: the settings live in the WebView's IndexedDB and are saved by the settings code there, so a tool call goes Rust (the HTTP server) → the page (an event, the way `TOMARIGI_IMPORT_KEY` hands over a key) → the same validate-and-save function the settings screen calls → the answer back to Rust. Each setting's check is one function used by both the screen and the tools; the tools don't get their own copy of the rules
- Tool names, descriptions and errors are in English (agents read them); the note in the app is in the UI language
- While the window is hidden or faded the server still answers (the page keeps running); tools that play a sound play it as the screen's Test does
- Out of scope: API keys, the debug and mock settings, updates (checking / installing), and anything that isn't on the settings screen

### Detailed design

Written by the session that implements it, from the code as of 2dfdb2a. All of it is Claude's own decision and may be changed.

Dependencies (`src-tauri/Cargo.toml`):
- `rmcp` 3.11 (the official Rust SDK, https://github.com/modelcontextprotocol/rust-sdk) with `default-features = false, features = ["server", "transport-streamable-http-server"]`. It speaks the protocol (initialize, version negotiation, `tools/list`, `tools/call`, JSON-RPC errors) and its `StreamableHttpService` is a `tower` service that checks the `Host` header against loopback names by default (against DNS rebinding). Hand-writing the protocol was not chosen: the version negotiation and the transport's rules change between spec versions, and the SDK follows them
- `hyper` 1 (`server`, `http1`) and `hyper-util` 0.1 (`tokio`) to serve that service on a `tokio::net::TcpListener`, the way rmcp's own tests serve it without axum (`tests/test_unix_socket_transport.rs` in the crate). Both are already in `Cargo.lock` through `reqwest`. axum was not chosen: one route doesn't need a router
- `tokio` 1 (`net`) and `tokio-util` 0.7 (the `CancellationToken` rmcp's config takes), both already in the lock through tauri; `getrandom` 0.3 for the token (already in the lock)
- No new npm package

Rust (`src-tauri/src/mcp.rs`, new; registered in `lib.rs`):
- `McpServer` state in a `Mutex`: the running server's port and `CancellationToken`, the tool list handed over by the page, the pending calls (`HashMap<u64, oneshot::Sender<ToolReply>>`)
- `mcp_start(port, tools) → Result<String /* the registration command */, String>`: binds `127.0.0.1:<port>` (an error `port-in-use` when the bind fails with `AddrInUse`, so the settings can say so), stops a server already running, then spawns the accept loop. `tools` is the JSON tool list from `src/lib/agent-tools.ts`, kept as is for `tools/list`
- `mcp_stop()`: cancels the token; the accept loop ends and the listener is dropped, so nothing listens on the port. Called when the setting is turned off
- `mcp_reply(id, reply)`: the page's answer to one call; completes its `oneshot`
- `mcp_renew_token() → String`: a new token, saved, and the new command. The running server reads the current token on every request, so the old command stops working at once without a restart
- `mcp_command(port) → String`: the command shown, built in Rust only: `claude mcp add --scope user --transport http tomarigi http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <token>"`
- Each connection: a `hyper::service::service_fn` that first compares `Authorization` with `Bearer <token>` (constant time) and answers 401 with no body when it is missing or wrong, then answers 404 for any path but `/mcp`, then hands the request to `StreamableHttpService`. Config: `legacy_session_mode: false` and `json_response: true` (stateless, one JSON answer per call; no session to lose when the app restarts), `allowed_origins: ["http://127.0.0.1:<port>"]` so a request a web page sends carries an `Origin` that is refused
- `ServerHandler` (rmcp): `list_tools` returns the page's list; `call_tool` gives the call an id, `emit("mcp-call", { id, name, arguments })` to the main window, and waits for `mcp_reply` up to 60 s (the sample's Test waits 30 s; Claude's own decision). The reply `{ ok, text, data? }` becomes a `CallToolResult` with `is_error = !ok`, the text as text content and `data` as `structured_content`. No answer in time → an error result "Tomarigi didn't answer. Make sure its window has loaded (reopen it from the menu bar icon)". `get_info`'s `instructions` say what the tools are for, and that a failed connection means Tomarigi isn't running and the user should start it
- The token (`keys.rs`, new functions beside the BYOK keys): 32 random bytes as hex (256 bits), saved in the OS store under the same service as the API keys with the account `mcp-token`, read once and cached. With `TOMARIGI_KEY_BACKEND=webview` (only for checking the key migration) it lives in memory and is new on every launch; where the OS store is unavailable (Linux without Secret Service) `mcp_start` fails with `no-key-store` and the settings say the feature needs one. The token is never logged; log lines say `[mcp] start port=4844`, `[mcp] stop`, `[mcp] refused 401`, `[mcp] call <tool> ok|error ms=<n>`
- The server task runs on tauri's async runtime; it keeps answering while the window is hidden or faded (the page isn't unloaded)

## Platforms

- macOS, Windows 10 / 11 (x64), and Linux (x64, X11). On a Wayland session the app runs through Xwayland (`GDK_BACKEND=x11` is set at launch), because pure Wayland has no always-on-top, no global cursor position, no window position restore, and no way to focus another app's window (Claude's own decision, from research)
- Platform-specific code is behind three seams, each with one implementation per OS: the window (transparent, always on top, not stealing focus, click-through except on birds, the handle, and the concierge's speech bubble), key storage, and process lookup (liveness and jumping). Everything else is shared
- The concierge's speech bubble takes clicks over its whole box, its empty space included, in the Garden and in the Concierge tab, so a click on it never reaches the app or window hidden under it (the user: 「コンシェルジュのセリフパネルで、何もないところをクリックすると貫通してしまうのをしゅうせいして。したの隠れてる部分がクリック対象になるのはui/uxがわるい」). Inside the page too, the bubble takes the click itself, shown or at rest: a bird or anything else drawn under the bubble is not pressed through it (other birds' bubbles still let clicks through to what is under them). A click on the bubble's empty space does nothing, and dragging it moves the window like dragging the background (Claude's own decisions)
- Window on Windows / Linux: transparent, frameless, always on top, hidden from the taskbar. The "fade until hovered" click-through works the same way as on macOS (the cursor position is polled and the window takes clicks only over birds, the handle, and the concierge's speech bubble). Always-on-top on X11 is a request the window manager may ignore. Showing on every virtual desktop is not supported on Windows
- Frosted background: Windows uses Acrylic; Linux has none and uses the plain translucent background (Claude's own decision)
- Clicking the window doesn't take focus from the terminal where possible (`focusable: false` equivalent); if a platform can't take a click without focus, it takes focus (Claude's own decision). On Windows / Linux the window is not focusable only while the Garden is faded (it takes only bird and handle clicks then), and focusable again when shown, so the settings inputs can be typed in
- Keys: Windows Credential Manager and Linux Secret Service (GNOME Keyring / KWallet) through the `keyring` crate. When Secret Service is not available (checked once at launch), keys can't be saved: the settings screen says so in place of the API keys description and the per-provider key rows; there is no plaintext fallback (Claude's own decision)
- Tray: on Linux the left click is not delivered, so the menu has "Show / Hide". The menu language comes from the system locale (not `defaults`)

## The "?" for sessions waiting on you

- A "?" is put on birds that stopped to wait for the user's decision. This includes turns that ended by asking in plain text (like "Which one should I go with?") without using a tool
- State is kept in two fields
  - Machine state `BirdState` (see "Bird states")
  - The turn verdict that comes with the speech bubble summary: `pending | asking | not_asking | error`. The summary request of a turn whose machine state became done also answers whether the last reply waits on the user (see "Turn verdicts"). It is tied to the turn (sessionId + time of the last reply) and is not requested again on every poll, nor after a reload or a restart (see "Turn verdicts", one verdict per turn)
- The "?" is shown when the machine state is waiting, or when the machine state is done / dozing and the turn verdict is asking. Not shown for pending / error. It disappears when the session goes back to working
- A session of the Claude desktop app writes its question in the `ask` of the tool that ends its turn (`mcp__ccd_turn__wrap_up`, shown by the app in a box with buttons), not in the reply's text. A turn whose last tool call is that tool with an `ask` that isn't blank, or with `blocked: true`, and after which only the closing text and tool results came, has the machine state waiting, the same as a question tool, before any time check or turn verdict; the bubble's question is the `ask`, and Recent activity has a needs reply at that call instead of a done at the closing text. A message, a closing, or another tool call after it ends the wait. Before, plan-icons ended on 「この中身で試しを打ってよいですか？」 in the `ask` with a reply that asked nothing, so it was shown done (verdict not asking) and the concierge didn't take it as waiting (the user: 「はんのうしてない」; Claude's own decision). `src/lib/transcript-desktop.ts` (`desktopAskOf`, `pendingAskOf`)
- A session of the Claude desktop app that ends its turn leaving a proposal card the user hasn't started also has the machine state waiting, the same as a question tool. Before, a parent proposed a session as a card and ended its turn asking the user to start it; the turn verdict was not asking and the concierge said no session needed a reply (the user: 「はんのうしてない」). Making such replies asking from their text was tried and not adopted (see "Turn verdicts"), so this comes from the tool calls in the transcript, not the reply (Claude's proposal; the user had it done in a separate session). `src/lib/transcript-desktop.ts` (`pendingProposalsOf`), `src/lib/proposals.ts` (`unstartedProposals`), `src/lib/bird-state.ts` (`replyWaitOf`)
  - A card: a result of the app's `start_session` whose text is `Proposed "<title>" (task_id: task_…)`, matched to the call by its `tool_use_id`: the same text in another tool's result (a command's output, a file read) is no card. Its title is folded onto one line and cut like a wrap_up's ask. Only an `own_initiative` call ends so: an `offer` waits for the user's answer within the call and comes back as `The user chose …` or a started session, a `user_asked` start comes back as `Started session …`, and a refused call says why (read from the transcripts on this machine)
  - Only the last turn counts: a prompt that starts a turn (the user's, a message from another session, a `<side-sessions-event>`, a task notification) or a closing ends the wait. The app tells a parent that the user started its card only in the next prompt, so that ends it too. Within the turn, a card withdrawn with `dismiss_task` (its `task_id`) or started by the session itself (`start_session` with its `proposal_id`) doesn't count
  - It waits only once the turn is over (the machine state would be done or dozing, or stopped on its wrap_up's ask). Claude Code's own waiting (a permission prompt, an open question) comes first: it is what the pane shows now
  - A card is started when the desktop app's record of a session says it came from that card: the app keeps one record per session (`claude-code-sessions/<…>/<…>/local_<id>.json`, the records the jump to the desktop app reads; see "Jumping to the terminal pane"), and a session another session started has `spawnedFrom` with the starter's `local_<id>` (`sessionId`) and the card's or the call's task id (`taskId`). On this machine all 221 such records had it, and the sessions started from the reported cards had the cards' task ids. The record stays after the session ends and across restarts of this app, so the wait doesn't come back then; a started card is remembered as started while the session's bird is shown (`desktop_started_cards` in src-tauri, `readStartedCards` in `src/lib/session-watch.ts`). The records are many and large (on this machine some three hundred, tens of MB), so each card remembers from when they were last read for it: the first read goes back to the card, later ones (every poll while a card isn't started) read only the records written since, less 2 seconds so one written as it read isn't missed. The parent's `local_<id>` comes from its `hostSessionId` in `sessions/<pid>.json`; when that has none (its process ended, say), it is looked up once in the records by its transcript id, as the jump does (`find_local_id`). Going through the records is one function for both (`each_record` in `src-tauri/src/focus/desktop.rs`), and a `local_<id>` has one form everywhere, `local_` and hex digits and `-` (`is_host_session_id` in src-tauri, `HOST_SESSION_ID` in `src/lib/transcript-peers.ts`). Neither transcript says which card a session came from (the child's has no task id), and a parent learns that the user started its card only in its next prompt. Counting the sessions linked to the parent after the card, as first built, lost the start once that session ended or this app restarted (its link is to a running session), and counted a sibling linked after the card or a session resumed then as a card started; the records have neither error (Claude's own decision, by the session that made this, after the review). When the records can't be read (no data folder for the desktop app), no card counts as started, and the wait ends with the session's next turn
  - The records are read from the same folder as the jump to the desktop app (`sessions_dir` in `src-tauri/src/focus/desktop.rs`): on macOS the place seen on this machine; on Windows (`%APPDATA%\Claude\claude-code-sessions`) and Linux (`$XDG_CONFIG_HOME/Claude/claude-code-sessions`, else `~/.config/Claude/...`) Electron's usual data folder for an app named Claude, a guess not checked on a real install (see "Jumping to the terminal pane"). Known limit: where the records aren't there (a wrong guess on Windows or Linux, or the app moves them or stops writing `spawnedFrom`), a session that left a card stays needing a reply after the card is started, until its next turn
  - The bubble's question and the concierge's `question` are the card's title, and the concierge gets `waiting_on: proposal`
  - Where a wait comes from is one function for the state, `waitingOn`, `wrapUpAsk` and the question (`replyWaitOf` in `src/lib/bird-state.ts`), in this order: Claude Code's own waiting status, a question tool, cards not started, a wrap_up's ask. `deriveState` and Recent activity (`deriveSessionEvents`) read the transcript's part of it (`tailWaitOf`), with the turn's cards counted as not started
  - Recent activity has a needs reply at the closing text of the turn instead of a done, when the turn left a card not withdrawn or started within it. Whether the user started the card later isn't in the tail, so it stays as history, like an answered question
  - A session whose parent takes it over (see "Watching", "Sessions started by another session") isn't taken over on a card, like a question tool: its needs reply is read aloud, and the concierge advises it. A card left in the same turn as a wrap_up's ask comes first: the wait isn't the ask's, so the parent doesn't take it over. Only the user can start a card: the app refuses a start in a turn that another session's message started, and a card is started with a click (Claude's own decision, by the session that made this)
- Criteria given to the model: asking = stopped in a state where it can't proceed until the user answers, such as presenting options, asking for approval, or asking for information. not asking = just reported finished work (including optional add-ons that need no answer), or said it will report or ask later (e.g. "I'll ask whether to push when it's done")
- Without a summary provider (OpenAI / Anthropic / Local), the "?" comes only from the machine state waiting
- The "?" is a badge shared by all icon sets, drawn over the bird. Chirps and readout on done don't wait for the verdict. Verdicts are logged in the debug log screen

## Anger mark for abuse toward the AI

- The summary request of a turn also gets the user's messages sent since the previous turn ended (see "Turn verdicts") and answers whether any of them is abusive toward the AI. If one is, an anger mark is put on that session's bird when the turn ends
- The mark stays until the next turn's verdict, also after a reload or a restart: a turn with a kept answer isn't asked again (see "Turn verdicts"), so the mark comes from the kept answer of the session's latest turn (`keptAnger` in `src/lib/turn-verdict-store.ts`). The mark is shown when the turn ends, not right after the message is sent: the user looks at the bird to read the bubble when the turn ends, before writing the next message, and this costs no extra request (the user chose this over a separate request per message: 「1でいいかもな」, then 「いいよ」)
- The anger mark is another kind of the same badge component as the "?", shared by all icon sets
- No separate on/off setting: it is used whenever a summary provider is set up. The settings screen's AI section says that the user's own messages are sent too (all locales)
- When the "?" is shown at the same time, both are shown: the "?" stays at the top right, the anger mark goes at the top left
- Recent activity has no bird, so the row of a session whose bird has the anger mark shows the same mark next to the state icon (✓ / ?) on the left. While any row has it, every row keeps room for it so the text lines up
- The mark is the 💢 shape itself (four red brackets bending toward the center, with a dark outline), drawn in SVG rather than with an emoji font, without a round background
- What counts as the user's message: a `user` entry in the transcript that is a person's text. Excluded: tool_result, isMeta lines, lines whose `origin.kind` is not `human` (task notifications etc.), and machine text starting with `<` (slash command echoes, bash-input) or `[Request interrupted`. The first 500 characters of each are sent. Codex uses the user messages its adapter already keeps
- The messages seen are remembered per session, so they survive the 64KB tail window filling up with tool output. Bytes appended between two polls that already fell outside the window (a large tool result right after the message) are scanned separately so a message isn't missed (Claude Code transcripts only)

## Turn verdicts

The speech bubble summary, the "?", and the anger mark come from the requests of each finished turn to the summary provider: one that answers all of them, and a second, narrow one that checks asking and writes the line (see the item on the second request below) (the user, on the first: 「それぞれのようやくにふぃーるどついかして、そのままこんしぇるじゅにわたしたらどうや」, 「いかりまーくもふぃーるどついかでいけるやろ？」). Before, the "?" and the anger mark came from TypeSafe's Jev, which mistook replies that only promised to ask later for questions (p=0.51 and 0.86–0.87 on the same day) and fed those to the concierge; Jev and TypeSafe were dropped (the user: 「やめよう」)

- One verdict per turn: a turn (session id and the time of its last reply) is asked about once, and its first answer is the one used. Answers are kept in the settings store (IndexedDB, the same place as the event log: kept across a reload and a restart), the last 200 turns, cut by count only, never by time, the oldest first; only answers are kept, so a request that failed is asked again after a reload or a restart (`src/lib/turn-verdict-store.ts`, `useTurnJudgements` in `src/perch/use-turn-judgements.ts`). Nothing is asked until the kept answers are loaded. (Claude's own decision, approved by the parent session.) Why: the answers were kept only in memory, so every reload asked about every turn on screen again. The dev app reloaded its page whenever an agent added or removed a worktree under `.claude` (the dev server watched it; it no longer does, README "Other notes"), and a restart does the same in every build. - Input: the last reply (`assistantText`, last 2000 characters) and the user's messages sent since the previous turn ended. Both are untrusted input

## LLM regression test

The turn verdicts and the concierge are checked with real models by a regression test, so a change to a prompt is
checked against every scene fixed before (the user: 「こういうの回帰がはっせいするから、llm用のてすとをかいてほしい」).
Before, each fix was measured with a probe on replies in local transcripts, so the scenes of earlier fixes weren't kept
anywhere they could be run again. That probe (`tools/turn-verdict-probe.ts`, named in the measurements in "Turn
verdicts") was replaced by this test (Claude's own decision). Usage is in tools/README.md ("llm-regression/")

- Scenes: a table in the repo (`tools/llm-regression/cases.ts`). Each turn scene stands for a reply that a verdict got
  wrong or that a fix was measured against, with the turn's user messages and the asking / continuing / abusive it
  should get; each concierge scene is the facts the app sends (as SessionView) and a check on the answer. Inputs are
  fixed in the table, never read from a local transcript or log at run time (the user: 「ろーかるのtranscriptつかうんじゃないで。こていするんやで」)
  - A scene keeps only the shape of the real reply that decides the verdict (a report or a question, who answers
    where, whether something waits, whether work goes on); what the work was about (features, issue numbers, files,
    amounts, counts, session names) is made up, so nothing of another project is in this public repo (the user:
    「ローカルのtranscriptから、プロジェクト固有の情報を書き換えて、プライバシーを守るようにしろよ」). Each new table is
    checked for privacy by subagents, twice (the user: 「サブエージェントでの二重チェックするようにしろプライバシーチェックは」).
    The same holds for everything put in this repo, not only these scenes: tests (their names and data), docs, code
    comments, and commit messages. None of them names another repository, project, client or product, or a person, or
    copies a text or an id from another transcript; a scene that reproduces a report uses names with nothing in them
    (app-x, the parent session). Each change is checked so by subagents, twice, before it is committed (the user's
    decision)
  - A field a scene doesn't settle is left out and not checked. The relay that asks the user to type an approval in a
    child's pane checks only continuing: Haiku says asking there, and making it not asking was tried and not adopted
    (see "Turn verdicts"). `two_decisions` checks only asking: its continuing comes from the watch link in the app
    (see "Turn verdicts")
  - A scene can also check that the speech bubble line doesn't match a pattern (a question or a wait the reply doesn't
    have), and can ask for more runs and a higher pass rate than the defaults, for a misjudgment that comes only now
    and then (`runs`, `minPass`, `lineMustNot`; Claude's own decision). The two reports ending with commits not
    pushed yet run 32 times each and must pass every time, and the report with the agent's own decision and a child still working runs 16 times, its line checked for a question, a check, or a wait on the user (Claude's own decisions; see "Turn verdicts")
- Requests: the app's own functions (`summarizeTurn` / `turnPayload`, `askConcierge` / `buildConciergePayload`, through
  `judgeRunnerFor`), so the prompts, schemas, models, bodies, the reading of answers, and the checks after the answer
  are the app's. Only the transport differs: the runners take a `JudgeTransport`; the app's is Rust (keys stay in
  Rust, never in the WebView's JS), the test's posts the same bodies with fetch to the URLs, headers, and timeouts of
  `src-tauri/src/keys.rs`, with keys from the environment, checked with zod at start. Those values are copied in
  `tools/llm-regression/transport.ts`, and `tests/llm-transport.test.ts` checks they match keys.rs
- Providers: OpenAI, Anthropic, and Local, each with the same table, since the providers behave differently (the user:
  「anthropic,openaiでもきょどうがかわるし」). By default every provider that can run: a key for OpenAI and Anthropic;
  for Local, a server with the model, and memory pressure below warning (Claude's own decision: loading a local model
  raised memory pressure to warning before). One that can't is shown as not run with why
- Each scene runs N times (default 8) per provider, since answers vary; the result is the pass rate per scene and
  provider. A scene under the minimum rate (default 0.75) or below the baseline (the result before the change) is NG,
  and so is a run where no provider ran or a provider in the baseline didn't run. A prompt change is done only when no
  provider's rate fell (Claude's own decisions: 8 runs and 0.75)
- When it runs: not every time, only for a change that can change its results (the user: 「このてすとをきどうするのは、このテストの結果が変わりうる時ということにしておいて」).
  That is found, not listed: `bun run test:llm:needed` follows every top-level declaration the test reaches from its own
  files through the TypeScript checker into src/ (the prompts, schemas, models and provider calls, the payload
  builders, the checks after the answer such as dropReason, the scenes), and says run when a change since what has
  been pushed (the merge base with the branch's upstream, or origin/main) touches one of them, or touches
  `src-tauri/src/keys.rs`. A function added on that path is picked up without a list to update (Claude's own
  decision). The rest of the app's path (reading transcripts into a reply and user messages, the scheduler) isn't in
  the test, since the test's inputs are fixed at that point

  - Sessions are named by their name in the advice, never by id (Claude's own decision). When the text without its name names another session sent, it isn't clear which session it is about, and it is dropped as before (no session name). The prompt still asks for the name. (the user's decision: before, an advice without the name was dropped, and an advice to reply to a session needing a reply was lost that way, so the concierge said nothing. The form `<name>: ` is one the AI writes itself, e.g. 「app-x: …の可否を返信」, and needs no particle per language)
    - An advice is about one session. Its text doesn't contain the name of another session sent, unless that name is also part of its target's name, and is not shown when it does; the check is in code. The one exception is the fixed form about a parent whose child's result hasn't reached it (e.g. "<parent>に<child>の結果がまだ届いていません"): the name of a child of the target whose result_reached_parent is false may be in it. The prompt also says a held-up session is a reason to choose an advice, not something to put in it. A dropped advice shows in the debug log screen as "concierge dropped" with "another session is in the advice" (the user, shown 「app-pのWEB-46対応方法を選び、app-oの作業を進めてください」 while app-o had finished its daily, said no decision was needed, and left app-p to ask the user in its own pane: 「コンシェルジュがへんなことをいってる」「あ、tomarigiな」; Claude's own decision)
    - The name is compared after NFKC and lower case, and a name cut for the request is compared without its cut mark. An advice without a target, or with an id that isn't one of the sessions sent, is not checked and shown as before. A dropped advice is kept in the debug log screen as "concierge dropped" with the advice and its target, and in the app log with its text (see the app log below; Claude's own decision)
    - An advice or a suggestion that writes an elapsed time it was given is not shown either; the check is in code (`writesElapsedTime` in `src/lib/concierge.ts`), with the reason "it writes an elapsed time it was given" in the debug log screen and `reason=elapsed_time` in the app log. The seconds are sent because they choose which session waited longest, not for the developer to read; the AI copied them now and then (in the app log 2 of 2,441 texts, e.g. 「770秒待っており判断が必要です」). A text is dropped when a number of its own in it (after NFKC; thousands commas dropped) equals one of the request's `seconds_since_last_activity` or `seconds_ago`, or the same in whole minutes or hours, cut or rounded. It is compared as numbers so it holds in every language without listing their time units (the parent session's decision). Numbers under 10 aren't compared, since session names and choices carry small numbers ("app-p 2", "Claude Code 2"); a number in a version, a decimal or a clock time, or after # isn't one, since in the app log such text named a release (v0.12.2) or a post (#86) and matched a time by chance (Claude's own decisions). Asking the AI not to write them was tried first and taken back: the leak was too rare to show a change (1 of 900 answers before, 0 of 900 after), and in Japanese answers with no advice and no suggestions went from 16 of 450 to 46 of 450
  - While any session needs a reply now, the advice is about one of those, never about a finished session. The order is enforced in code as well: an advice about a session that doesn't need a reply while another does is not shown (the user, shown 「完了したtomarigi-desktopの結果を確認」 while another bird had the "?" from a question or permission prompt: 「これもちょっとちがうよな」; enforcing it in code is Claude's own decision)
    - "Needs a reply" here is needs_reply in the request. An advice without a target is not checked. A dropped advice shows in the debug log screen as "concierge dropped" with "another session needs a reply" (Claude's own decision)
  - With no session needing a reply, the advice and the suggestions point to a session that finished with its result ready to check (done, not continuing, no watching parent taking its result, no parent taking it over, no watched child still working).   - The advice asks the user to reply or answer only about a session that needs a reply now. A finished session that doesn't need one is advised as finished (e.g. "<name> finished: check the result"), never as "check its request and reply". The current facts outrank older events: a needs_reply event for a session that no longer needs a reply doesn't make it wait (the user, shown 「app-vの依頼を確認し、返答してください」 for a session whose last message was a report: 「いらいをかくにんしへんとう、もちがうよな」; the wording is Claude's own decision)
    - The prompt also says a finished session's speech bubble line tells what it did: a line that mentions a request or a question it passed on to another session doesn't mean it waits (Claude's own decision; the user's case was a report of what it had asked another session to do)
    - Enforced in code with the advice's kind: an advice that asks to reply about a session that doesn't need a reply now (needs_reply in the request: a question tool, a permission prompt, a wrap_up's ask, a proposal card, or the turn verdict asking) is not shown, and shows in the debug log screen as "concierge dropped" with the reason (the user, shown 「tomarigi-desktopの確認…に返信し、push可否を判…」 from OpenAI for a session whose last reply only said it would ask later, with Jev at p=0.10: 「このこんしぇるじゅのへんとうもおかしいいよね」, then 「おk」 to Claude's proposal)
- When it is asked. Measured with the first version, which asked on every working / stopped change: 56 requests in 19 minutes with 9 sessions moving (about 176 an hour), about 5,800 characters of input each, 15 of them returning no advice. The user found that too costly (「おーそれはちょっとなぁ」) and agreed to the fix below (「うん、」); the rules are Claude's own decisions:
  - Only on these changes: a session starts needing a reply (including the "?"), a session that needed a reply is answered, or a turn finishes (done). Other changes (tool lines, working ↔ working, a new prompt to a finished session) don't ask
    - A session first seen needing a reply or done (at launch, after saving a key, a new session) counts as that change, and a session that needed a reply leaving the screen counts as its answer; done → dozing doesn't ask (Claude's own decision)
    - A stopped session whose continuing from its reply's text expires (see "Turn verdicts") counts as a turn that finishes at that moment: it asks like done, under the same 3 seconds and 60 seconds (it doesn't skip the 60 like a reply), and for 5 minutes (the dozing time) after the expiry it counts as done for the rules below (the advice isn't cleared, a retry and opening the Concierge tab may ask). Then it is dozing again, which doesn't ask. A session first seen so (at launch) counts only within those 5 minutes after its expiry, so sessions that expired long ago don't all ask at launch. continuing from watching doesn't expire, so it never asks this way. The app log has `[concierge] trigger kind=expired session=<id>` once per expiry, before the request it leads to (the user: 「これ、こんしぇるじゅがはんのうしてないのおかしくない？」; Claude's own decision on the 5 minutes and the launch rule). Before, an expiry asked nothing: the session was already dozing, the scheduler saw only the state, and with no other session done or needing a reply the advice was cleared at dozing, so the concierge never suggested checking its result
  - At most one request per 60 seconds. Changes inside that time are merged into one request when it ends. Changes that come together are still gathered for 3 seconds first
  - Except when the user answers a session that needed a reply: that asks after the 3 seconds without waiting for the 60 seconds, so the advice follows the user's action at once (the user: 「コンシェルジュの対応してすぐにコンシェルジュがこうしんされないんだよ」). These come at the user's pace, so they don't bring back the request volume (Claude's own decision)
  - A session starting to need a reply (a question tool, a permission prompt, a wrap_up's ask, a proposal card, or the turn verdict asking) also asks after the 3 seconds without waiting for the 60 seconds, so the bubble doesn't stay empty while a bird has the "?" (the user, after the concierge showed nothing for about 40 seconds because a request had just been made: 「こんしぇるじゅがはんのうしてないが、きどうたいみんぐか？」, then 「すいしょうで」 to Claude's recommendation). It adds at most one request per turn that ends waiting on the user (Claude's own decision)
  - As soon as the session the advice is about changes state (e.g. the user answered it), the advice is hidden on that poll without waiting for the next request, so the bubble never points at a session already handled (Claude's own decision; before, it was cleared this way only when a request failed)
    - The 3 seconds count from the first change; later changes join it without restarting the wait, so sessions that keep changing can't hold the request off (Claude's own decision)
  - Not asked while no session needs a reply, has the "?", or is done (not dozing; a session whose text continuing expired within the last 5 minutes counts as done); the advice is cleared then
  - Every 5 minutes while any session needs a reply or has the "?", so a skipped session is brought up again
  - A request that fails with a temporary error (HTTP 5xx, 429, a timeout, or no connection) is asked again after 10 seconds, then 30, then 60, at most 3 times, while a session still needs a reply, has the "?", or is done (counted as above); changes that come in meanwhile join the retry. Other errors (a wrong key, a bad request) are not retried. Retries don't count toward the 60-second limit (the user, after OpenAI returned 503 and the concierge stayed silent with a bird waiting: 「こんしぇるじゅがはんのうしてない」; the rule is Claude's own decision). Before, a failed request waited for the 5-minute timer or the next change
  - The token counts the API returns (input, cached input, output) are logged per request, so cost is measured rather than estimated. Input is the whole input including the cached part; for Anthropic it is input_tokens plus the cache reads and writes (Claude's own decision)
- Requests and advice are logged in the app log and the debug log screen
  - The debug log screen keeps them in memory only; the app log keeps them across launches (Claude's own decision)
  - The debug log screen also shows the full input of each request and the answer, so a wrong advice can be traced to what the AI was given. It stays in memory only and never goes to the app log, since it holds text from the sessions (a wrong advice could not be reproduced because the input wasn't kept; Claude's own decision)
  - The app log also keeps the advice text, both shown and dropped, with its kind (reply / check the result / nothing), its target, and the provider and model that wrote it, so a wrong advice can be found from the log after the fact without a screenshot. The full input still stays out of the app log (the user, after Claude said the app log had no advice text and both wrong advices that day were found from their screenshots: 「助言の文面も記録するようにして」; adding the kind, provider, and model is Claude's own decision, since the everyday and verify builds write to the same log and which model wrote an advice could only be guessed from timing)
    - Each request also logs one line per session with the facts it was given, without any text from the sessions: session id, agent, state and elapsed time, needs_reply and where it came from (the machine state, with whether it waits on a question or a permission prompt when known, or the turn verdict), continuing from the turn verdict (`continuing=expired` when the reply's continuing passed its 30 minutes; the concierge is then given continuing false, and nothing about the expiry, so the prompt's meaning doesn't change: Claude's own decision), the watch link, and the number of chicks working. Each line carries the request's id, so the advice it led to can be matched to the facts. Purpose: an agent (Claude) can find a wrong advice from the app log alone, by checking the advice against these facts and, where needed, against the target session's transcript at that time (the user: 「つまり、お前が単独でおかしいぶぶんにきづけるようにしたいわけや」, then 「うん」 to Claude's proposal)
    - Each request also logs one line per hold with the waiting session's id, the chick holding it up (only a chick holds up its parent; the log writes `chick`, not its name), and the reason, since an advice that names a held-up session can only be checked against them (before, only the number of holds was logged; Claude's own decision)
- With no session on screen, the concierge isn't shown either; the Garden keeps its empty message (Claude's own decision)
- The concierge's speech bubble in the Garden shows its whole text like any bird's ("Layout"), wrapping onto as many lines as it needs; its width follows the same max-width rule. It has no status lines, so the lines below go into the empty space under it (Claude's own decision, following the user's 「せりふはしょうりゃくせずにうえにかさねる」: it had been cut to two lines with "…", which cut the advice once the bubble was narrowed next to a neighbour)
- Perch lays the advice out like a Perch row: the concierge and its name on the first line, the advice on the second. With no advice, nothing is shown above the list (Claude's own decision)
- Names, bubble lines, and question text are cut at 120 characters in the request (Claude's own decision)
- When a request fails, the advice shown stays until the next one, unless the session it is about has changed state since the advice came (needs reply, working, or stopped; e.g. the user already replied), or has left the screen. Then the advice is cleared, so it doesn't send the user to a session that no longer needs them (Claude's own decision; the clearing was added by the parent session)
- When the session the advice is about leaves the screen, the advice stays without a jump target until the next request (Claude's own decision)
- Mock mode: `concierge=<text>` in `TOMARIGI_QUERY` shows the concierge with that advice without calling the API (README) (Claude's own decision)

## Plugins

Plugins send what the concierge says to other services such as Slack (issue #12; the user: 「コンシェルジュの喋るタイミングのフックを実装」「adaptor形式で複数設置可能」「Slackなどと連携可能にする」「Slackなどはテンプレートとして用意する」, then 「plugin機能の一つとしてのhook」「plugins > Slack > hook」)

- The user's first minutes: open ⚙ settings → "Plugins" → "Add plugin" → choose Slack, paste the Incoming Webhook URL, save → "Send test" posts a sample line to the channel → from then on, each new concierge advice is posted there, while the window is hidden too
- Structure: plugins > a template (Slack, Webhook) > hooks (the user). A plugin is one added instance of a template; several can be added, several of the same template too (e.g. two Slack channels)
  - Templates are adapters: one file per template behind one interface on the Rust side, so another service (e.g. Discord) is one more file (Claude's own decision)
  - Templates at first: Slack (an Incoming Webhook URL; posts `{ "text": <advice> }`) and Webhook (any https URL; posts the payload below as JSON) (Claude's own decision)
- Hooks: one for now, `onConciergeMessage` (the name is the user's choice among Claude's candidates onSpeak / onAnnounce / onConciergeMessage)
  - Fires when the concierge shows a new advice: its target session or its kind (reply / check the result) differs from the advice shown before it, the same "new" rule as the Concierge tab readout. The same advice coming again with other text doesn't fire. Advice that isn't shown (nothing to do, dropped by the checks) doesn't fire (Claude's own decision)
  - Fires whichever tab is open, whether "Read aloud" is on or off, and while the window is hidden: it is for when the user isn't looking at the app (Claude's own decision)
  - The Concierge tab's suggestions don't fire it: they are asked for only while that tab is open, when the user is looking (Claude's own decision)
  - No limit of its own: it follows the concierge's request limits ("When it is asked")
- Payload: `{ "hook": "onConciergeMessage", "text": <the advice as shown, with the session name>, "kind": "reply" | "check_result", "session": { "id", "name", "agent" } | null, "at": <ISO 8601> }` (Claude's own decision)
- Sending is done on the Rust side, so it works with the window hidden and the webview gets no network permission for other hosts. Timeout 10 seconds, no retry. A failure is logged in the app log and the debug log screen with the plugin's label and the HTTP status or error, never the URL (Claude's own decision)
- The URL is a credential (a Slack webhook URL lets anyone post to the channel): it is kept in the key store with the API keys ("BYOK API keys"; Keychain, Credential Manager, Secret Service), and the settings screen never shows it after saving: "URL saved", with replace and delete only. Only https URLs with no user name or password are accepted; the settings screen and Rust check the same rule (Claude's own decision)
- Settings: a "Plugins" (ja: プラグイン) section right after the AI section, since it sends what the AI says (Claude's own decision). Top to bottom:
  - The heading
  - One line: it sends the concierge's advice, including session names, to the services added here (all locales)
  - While no AI provider is set up: one muted line that the concierge needs the AI settings above, so nothing is sent until then
  - The added plugins, one row each: the label (the user's name for it; the template's name by default) with the template's name under it, an on/off switch, "Send test", and delete. "Send test" posts a fixed sample line and shows sent or the error on the row
  - "Add plugin" opens an inline form: the template (Slack / Webhook), the label, the URL, and Save. Save is the one primary button in the form
- Mock mode and the browser mock don't send anything; "Send test" shows sent (Claude's own decision)

## Updates

The app updates itself with Tauri's official updater plugin (the user chose it over only telling about a new version: 「aかなぁ」)

- Checked at launch and every 6 hours after that. "Check for updates" in the menu bar menu and in settings checks at once (Claude's own decision)
- A found update is not installed by itself. The menu bar menu and settings show "Update to v<version>"; clicking it downloads, installs, and relaunches, with progress shown in settings. Nothing is added to the Garden, since it is fully transparent at rest (Claude's own decision)
- Up to date / check failed are shown in settings only after a manual check; automatic checks stay silent when there is nothing new (Claude's own decision)
- Where updates come from: `latest.json` on the newest published GitHub Release (`https://github.com/mohhh-ok/tomarigi-desktop/releases/latest/download/latest.json`), in the shape tauri-action makes it, written once by the release workflow's last job (docs/release.md). Draft releases aren't "latest", so users get a version only once it is published
- Bundles: macOS `.app.tar.gz` (universal), Windows NSIS, Linux AppImage and .deb (the updater plugin supports .deb from 2.10.0)
- Signing: update bundles are signed with an updater key pair, separate from Apple's signing (the plugin requires it). The public key is in `tauri.conf.json`. The private key and its password are GitHub secrets for CI, with a backup in Google Secret Manager (the user has no password manager: 「1passwordとかもってないんだよなぁ。google secret managerくらいしかもってない」; the project is the user's personal one (its id is in the local `.env` as `UPDATER_KEY_GCP_PROJECT`, see docs/release.md), which already keeps their other backup secrets, Claude's own decision). Losing the key would leave existing users unable to update, so the backup is required. Names and steps are in docs/release.md
- Versions before the first one with the updater can't update themselves; their users replace the app by hand once
- The checking, downloading, and installing are done on the Rust side (`src-tauri/src/updater.rs`), since the menu bar item has to work without the window; the window only shows the status and asks for a check or an install. So the webview gets no updater permissions, and the relaunch is Tauri's own `AppHandle::restart` instead of the process plugin (Claude's own decision)
- Clicking the menu bar item opens the window on the settings' Updates section, so the result of a check and the download progress are visible (Claude's own decision)
- The menu bar item is "Check for Updates", "Checking for Updates…" (greyed) during a manual check, "Update to v<version>" once found, and "Updating…" (greyed) while downloading and installing. Japanese / English like the rest of the menu (Claude's own decision)
- A debug build checks `TOMARIGI_UPDATER_ENDPOINT` instead of GitHub when it is set, so the whole flow can be tried against a local `latest.json` before a release (the plugin allows http only in debug builds) (Claude's own decision)
