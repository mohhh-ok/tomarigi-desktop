# tomarigi-desktop design

A desktop app for macOS, Windows, and Linux (Tauri 2; see "Platforms") that watches AI coding agent sessions (Claude Code / Codex and the other agents in "Agents") as birds in an always-on-top floating window. It is the desktop version of the tomarigi Chrome extension.

## Scope

- Tabs: Concierge (always shown; see "Without a provider" under "Concierge"), Garden, Perch, and Recent activity, in that order (Garden is the default), plus the ⚙ settings screen
- Watches the transcripts of every agent in "Agents" in parallel through adapters. State is decided by local heuristics only; no hooks are installed on the agent side
- Bird states (sprites, aura while working, motion animations), and drag placement in the Garden
- Icon sets (birds / gnome / cat / robot / frog) assigned per project
- Web Audio chirps (mute, volume), speechSynthesis readout (opt-in, volume), BYOK (OpenAI / Anthropic) or a local model for summaries on done with the "?" and anger mark verdicts, and connection tests
- Persistent event history and a debug log screen
- i18n (see "Language")
- Mock mode (presets + JSON injection)
- Not bundled: the author's `peer-session` skill (starts child Claude Code sessions in Ghostty panes, which then show up as birds). It is Ghostty- and Claude Code-only and still being shaped by the author's own use (the user: 「peer-sessionはえっとね、基本的には俺も使いながらブラッシュアップしていきたいから細かい設定も基本的には俺好みでかんがえてる。でさ、もんだいはたーみなるごかんよな」「とりあえず自分の使用でそだてていきたい。」). Revisit bundling or publishing it, and support for terminals other than Ghostty, when the user brings it up again

## Language

- UI text is generated from `scripts/locales` into `public/_locales`, and every locale is checked to have the same keys
- The app is English-based. UI text comes from the locale files (English fallback). The menu bar menu is Japanese when the system language is Japanese and English otherwise. The debug log screen and mock mode are English only

## Bird states

- Machine state `BirdState`: `working | waiting | done | dozing`. Recomputed on every poll
  - `waiting`: stopped on AskUserQuestion / ExitPlanMode / request_user_input, or Claude Code's `<config>/sessions/<pid>.json` has `status: "waiting"` (while it shows options or a permission prompt, Claude Code doesn't write that tool_use to the transcript until it's answered)
  - `dozing`: a finished turn (`done`) with no new writes for 5 minutes (`DOZE_MS` in `src/lib/bird-state.ts`). It only changes the sprite and the status label
- A write in the last 6 seconds counts as working. The recap Claude Code writes while the user is away (`system` / `away_summary`) is not a write: it isn't conversation, and it made a finished session working for 6 seconds, so its turn was summarized again and the concierge asked again (the user: 「コンシェルジュのはんのうがおかしい。べつせっしょんでちょうささせて」; excluding only this line is Claude's own decision: in the local transcripts 3,692 of 3,942 such lines came alone, more than 6 seconds after the last message and with none in the 30 seconds after, while the other lines written late mostly start or belong to a turn)
- The finished-turn state is called "done" everywhere: bird state, Recent activity, sound settings buttons, and bird descriptions (all locales)
- The waiting state is called "needs reply" (ja: 返事待ち) everywhere: bird state, Recent activity events, and sound settings buttons (all locales)

## Watching

- A session that handed work to another session and is waiting on it is shown as "watching". The other session isn't necessarily in the same directory
- How links are found: from traces of Claude Code's cross-session messaging (a public feature, enabled without configuration since v2.1.224) in transcripts. The sender side is the recipient name in a SendMessage tool call; the receiver side is `<cross-session-message from-name="…">`. Names are matched against `name` in `<config>/sessions/<pid>.json` to look up the other session's sessionId, cwd, and status. Two sessions that exchanged at least one message are considered linked. No particular person's tooling (such as a script that launches sessions) is relied on
  - Claude desktop app (Code tab) sessions are addressed by a `local_<uuid>` id instead of a name, and the app writes that id as `hostSessionId` in the session's `sessions/<pid>.json`. So these traces are read too, and each is matched against `hostSessionId` as well as `name`: the `session_id: local_…` in the text of the tool result that starts a session (`Started session "…" (session_id: local_…, …)`, from the app's `start_session`), `session_id` in the input of the app's `send_message` tool, a SendMessage recipient that is a `local_…` id (already read as a name), and `origin.from` of a received message when it is a `local_…` id. A child started from the desktop app is then linked to its parent from the moment it starts, before it sends anything, and stays linked when either is renamed (the parent session's decision: before, such a child was linked only once its first message arrived, matched by its title, and the app log showed it unlinked until then)
  - A session started from a proposal card (the user clicks a card a desktop app session proposed; see "The "?" for sessions waiting on you") has no `session_id` in its parent's transcript: the result of the proposal has only a task id. The app writes, in the first prompt of every session another session started (turnOrigin other than `human`), the starter's shared notes folder, `…/side-session-notes/local_…`, with the starter's id. So that id in the transcript's first prompt, when its turnOrigin isn't `human`, is a trace too (Rust `notes_folder_host_id`, `NOTES_FOLDER_ID` and `firstPromptStarterOf` in `src/lib/transcript.ts`; the id is `local_` and the hex digits and `-` after it). Only the first prompt: a later notice (a `<side-sessions-event>`, a message) may quote another session's folder. Such a session is linked to the session that started it from its first prompt, and so its parent takes it over from its start (`parentTakesOver`, see "Sessions started by another session"), as a child started by `start_session` right away (Claude's own decision, by the session that made this). In the transcripts on this machine, all 215 first prompts with a turnOrigin other than `human` and a brief from the session that started them had the folder; in the reported case its id was the parent's `hostSessionId`; and the 16 sessions started by a session that was itself started by another had their own starter's id there, not the id their starter had, so it is the direct starter, not the group's first session. Not a public spec either
  - A session started in a terminal by another session (e.g. `claude --name <name> "<prompt>"`) has no trace of its parent until one of them sends a message: its first prompt is written like one the user typed. It is linked from its first message, as before
- Watching: the session's own machine state is done / dozing, and at least one linked session is working (status busy in `sessions/<pid>.json`, or its transcript's machine state is working / waiting). Chirps and readout on done are held until all linked sessions stop
- After the linked sessions stop, the bird stays watching for 5 minutes after the last one moved (`WATCH_GRACE_MS`), so the watch block and label don't flicker between the other session's turns. A linked session whose status isn't idle (e.g. shell) also counts as moving
  - The grace period ends early when no linked session moves now and the session itself finished a turn after every linked session's last transcript write: it has taken the other session's result (it ended a turn after the result came), so it is done, not watching. Its own turn's end is the time of its last transcript line (its done / dozing state's basis; `lastWrittenAt` in `src/lib/transcript.ts`), and a linked session's last write is the same function on that session's transcript (`lastWriteAt` in `lastPeerStates`, passed to `watchingCount` as the peer's `lastWriteAt`). The 5 minutes are still counted from the last time a linked session moved (`lastActiveAt`), unchanged. A linked session that moves again makes it watching again, and while one moves it stays watching as before. When the session finished its turn before a linked session's last write (it handed work over and stopped), the 5 minutes hold as before. When a linked session's last write isn't known, the 5 minutes hold too (the safe side). Before, a Claude desktop app parent that took its child's report at 20:13:07 and finished its turn stayed watching (working, a white dot in the concierge) until 20:17:37, 5 minutes after the child stopped at 20:12:37 (the user: 「かんりょうずみですらないねん。白丸やし」「5ふんってながくない？」; ending the grace period on the parent's own done is Claude's proposal, and the user had it fixed in a separate session). One function decides it (`watchingCount` in `src/lib/watching.ts`), and the bird's watch block and label, continuing (see "Turn verdicts") and the concierge's checks all read its result. The early end compares with the linked session's last write, not with the last time it moved: "last moved" is the poll time while the app sees it working, and a write in the last 6 seconds counts as working, so it lags the actual last write by several seconds. Compared with "last moved", a parent that took the report and finished its turn within those seconds kept the grace period: on 2026-11-12 the app-x child last wrote at 21:02:21, the parent finished its turn at 21:02:26, and at 21:03:33 the parent was still continuing and watching that child (the app log). A Claude desktop app parent answers a child's report in a line or two, so this is the usual case. Comparing with the last write is Claude's proposal, and the user had it fixed in a separate session (the user: 「またapp-xがかんりょうずみになるのおそかったが」). Known limit: when the linked session stopped less than 5 minutes ago and the session sends it new work and finishes its turn, the session leaves watching for the few seconds (one or two polls) until the linked session starts moving, so the bird's label and watch count swing to done. The done chirp and readout don't change: they are decided on a path that doesn't read watching (`src/lib/session-events.ts`). Leaving this as it is is Claude's own decision
- Sessions started by another session: a parent takes over the results of a session it started and the questions its replies ask the parent, so that session is quiet on its own (the user's decision). A wait only the user can answer in that session's pane, a permission prompt or a question tool (the machine state waiting), isn't taken over (the user's decision). The Claude desktop app's wrap_up with an ask (or `blocked`) is the machine state waiting too, but it is taken over: the ask is part of the session's report, which reaches its parent, and the parent can answer it with a message (Claude's own decision, by the parent session). Which waits a parent can answer is one function (`parentCanAnswer` in `src/lib/turn-verdict.ts`); a waiting on a wrap_up's ask is marked `wrapUpAsk` on the session and on its event. It applies to a session that was started by another session and is linked to a parent: a session that started before it and either was not started by another session, or was and is linked now to one older than itself (`parentTakesOver` and `takenOverByParent` in `src/lib/watching.ts`; the second part is Claude's own decision, by the parent session, so that the successor of a rebirth isn't taken for the child of the child its predecessor started), whether the parent is watching now or not, and in or out of the grace period (the user's decision)
  - Its done still chirps and stays in the log and the event feed, but isn't read aloud: not outside the Concierge tab, and not when a request in the tab fails and the held events are read (`silentForParent` in `src/lib/watching.ts`; the user's decision on the done's readout; keeping the chirp is Claude's own decision, by the parent session). A done whose reply asks its parent (the turn verdict asking) is a done, so it is silent too. Its needs reply on a wrap_up's ask is silent too. Its needs reply on a question tool is read aloud like any other session's (the user's decision). A needs reply event comes only from a tool call in the transcript (`deriveSessionEvents` in `src/lib/session-events.ts`: a question tool, or a wrap_up's ask), so a permission prompt, and Claude Code's question tool while it is open (Claude Code writes that tool call only after it is answered), make no event and aren't read aloud for any session, taken over or not; they still put the session on the concierge as needing a reply, and its bird gets the "?" The done of the parent is held by watching as before. The app log's `[event]` line has `silent=true` for the silent ones
  - The concierge doesn't ask the developer to reply to a question its reply asks its parent (the turn verdict asking), and doesn't ask to check its result (see "Concierge"). It doesn't ask the developer to reply to its wrap_up's ask either. It does ask the developer to reply when it stops on a permission prompt or a question tool, as for any other session: only the user can answer those, in its pane, and its parent can't answer for it (the user's decision). Before, a parent's takeover left out its permission prompts and question tools as well, so a child stopped on a permission prompt was never brought up; that grouping was the parent session's mistake of offering the cases as one choice, and it was changed because it held back waits only the user can answer. Its bird still gets the "?" (the user's decision). Whether a session waits on the developer is one function for the concierge's facts, its triggers, the Concierge tab's bubble lines, and the tab's count of birds needing a reply (`waitsOnDeveloper` in `src/lib/turn-verdict.ts`), with where the wait comes from (`replyWaitSource`, the machine state or the turn verdict) from the same file: a session whose parent takes it over counts as working there while it waits on what its parent can answer. The "?" on the bird and the Perch row stay with `needsAnswer`
  - Its parent's takeover is lifted only while its latest turn was started by a prompt the user typed in it; once a later turn is started by its parent's message or the app, it is taken over again (the user's decision). A turn is started by the last prompt after its first prompt: a user line that is not a subagent's (`isSidechain`) and not a tool result. It is typed when its `turnOrigin` is `human` (or, without `turnOrigin`, its `origin.kind`); messages from other sessions (`peer`), task notifications (`task_notification`), and the desktop app's own turns such as `<side-sessions-event>` and `send_message` (`sdk`, `host_synthetic`) aren't. It is read with the links, from the top of the transcript and then from where the last read stopped (`scan_peer_names` in src-tauri). Details (Claude's own decision, by the parent session): a meta line (`isMeta`) counts only when it is a message from another session (those are written as meta lines with `turnOrigin` `peer`); what arrives while it works is written as an attachment (`queued_command`), and of those only a prompt the user typed (`origin.kind` `human`) counts, as typed, while messages from other sessions and task notifications don't; a read with no new prompt keeps the previous answer. The first prompt never counts, so a session started in a terminal (its first prompt is `human` too) is taken over until the user types in it. Before this, one typed prompt took it off for good (Claude's own decision), which kept a child the user had once talked to off even when it later stopped on a question to its parent, so the concierge asked the user to reply
  - Told from the transcript's first prompt, which is read once from the top of the file (`scan_peer_names` in src-tauri): the Claude desktop app writes the first prompt of a session started by `start_session` with a `turnOrigin` other than `human` (`sdk` or `host_synthetic`; in the transcripts on this machine 177 such sessions all were started by another session, and the 97 the user started were `human`). A session the user started and that later exchanged messages with an older one isn't one: before, it counted as that one's child (the later-started of the two) and would have gone quiet too (Claude's own decision, by the parent session: in the app log, 4 of the 6 sessions that were done before they were linked were sessions the user talked to)
  - A session started in a terminal by another session writes its first prompt like one the user typed (`turnOrigin` `human`). It is told apart by a name and a prompt given at launch (`claude --name <name> "<prompt>"`): an `agent-name` line before the first prompt, and the first prompt within 2 seconds (`PROMPT_AT_LAUNCH_MS`) of the SessionStart hook's line (Claude's own decision, by the parent session). In `~/.claude2` on this machine this caught 267 of the 268 sessions started by another session and, of 65 others, only 4 trial sessions of a rebirth; the user's own desktop app sessions never match it. A prompt typed right after launch without a name doesn't count: 12 sessions the user started had one within 2 seconds
  - The desktop app rule also takes a session run from the Agent SDK (`entrypoint` `sdk-py`, first prompt `sdk`) as started by another session. Such a session is only taken over when it is linked to an older one, which they rarely are
  - Known errors (Claude's own decision, by the parent session, to accept them): a grandchild (a session started by a child) whose grandparent closed or was reborn is read aloud and advised about again, since its parent lost its own parent; that child is read aloud too. A session the user starts with `claude --name foo "<prompt>"` themself and that exchanges messages with an older session the user started counts as taken over, until the user types in it again. While a reborn session and its predecessor both run (until the predecessor's pane closes), a successor that talks with the child counts as that child's child
- Presentation:
  - In the Garden, the watching bird and its linked birds are placed close together as a watch block, and each linked bird is connected to the watching bird by a line. The block has no frame or background of its own (the user: 「いまはグループをしかくでかこってるが、これだとはいけいがきえてると視認できない。そこで箱で囲むのをやめて線で繋げる形にして、背景消えてる時でもせんがみえるじょうたいにしたい」)
    - The lines stay visible at full strength at rest in "Fade until hovered", like the birds. They are not a hover or click target, and clicks on them go through at rest (Claude's own decision)
    - A line runs between the two birds' icons and is drawn behind birds, badges, bubbles, and status lines, so it never hides them (Claude's own decision)
    - A line never runs over another bird, name, bubble, or status line (the user, shown a line that bowed over the bird in between to join the left and right birds of a row: 「こういうふうに、線がまたがるじょうたいはちょっとやめてほしい。これまでは箱に収める関係からこういうぱたーんんがうまれたが、かえれるやろ」). So a linked bird is put next to the bird it is linked to, and lines are drawn only between birds next to each other
    - Placement in the block: the parent (the first-started bird) is in the middle, and each linked bird, in start order, goes to a free cell next to the bird it is linked to, tried in this order: right, left, lower right, lower left, upper right, upper left. Not straight above or below: a line there would run through the upper bird's bubble and status lines. A diagonal cell whose line would cross the line between the other two birds of that 2x2 square in an X is skipped. From the 7th bird on, when no cell next to it is free, a bird goes to the nearest free cell and gets no line; the count at the parent's feet and the indent in Perch still show it is linked (Claude's own decision, the order of the six cells and the 7th bird on included). The user chose this placement over others shown as samples (a tree to the right, a tree downward, packing the birds into 3 columns and joining neighbours in the group): 「a1がよさそうやな」, then, after seeing the 3-column sample, 「a1」
    - The line has a contrasting outline so it reads over any desktop behind the transparent window, light or dark (Claude's own decision: at rest the window background is gone, so the line can't rely on it)
    - The lines are kept from standing out: seen only on a closer look, not at a glance (the user: 「線はもっと短く」「よはくがあいていいから」「つまりめだたせたくないからみじかくしろっていってるねんか」「よくみたらつながってるな、ていどでいいねん」). So a line is short and leaves room at both ends: it stops 18px off each icon's edge and is at most 36px long, centered between the two icons. It is thin and faint: a 1.2px core of the app's warm accent at 60% under which lies a 2.5px dark outline at 30% (Claude's own decision)
    - A linked bird that is itself watching gets its own linked birds next to it and lines to them the same way (Claude's own decision)
  - The watching (parent) bird's name is shown above the parent bird itself, wherever its cell is in the block; the block has no title of its own (the user's decision: a title on the block's top edge read as the name of the bird below it). Other birds inside show no name if they are in the parent's folder, and only the path relative to the parent otherwise
  - Dragging a bird inside the block moves the whole block
  - The number of linked sessions currently working is shown at the watching bird's feet
  - In Perch, linked rows are indented under the watching row, labeled with the path relative to the watching session's cwd (or the folder name if not under it). Rows in the same folder show no name
  - When a linked session gets a "?", the watching bird doesn't. The "?" only goes on the bird that is actually asking
- The indentation parent is whichever of the two linked sessions started first. Codex has no equivalent feature and is out of scope
- Caveat: the transcript format and `sessions/<pid>.json` are not public Claude Code specs (the sessions docs say "internal to Claude Code and changes between versions"). State detection and jumping to the terminal pane rely on them too. The desktop app's `local_…` ids, `hostSessionId`, the text of its `start_session` result (`Started session …`, `Proposed …`), the notes folder in a started session's first prompt, and the app's session records with their `spawnedFrom` (which proposal card a session came from) are not public specs either (read from Claude Code 2.1.321 in the desktop app)

## BYOK API keys

- Providers: OpenAI / Anthropic / Local (see "Local AI" below) for speech bubble summaries with the "?" and anger mark verdicts (see "Turn verdicts"), and the concierge. Each can be saved, deleted, and connection-tested from the settings screen
- Models for summaries and the concierge: OpenAI `gpt-5.6-luna` (reasoning effort none), Anthropic Claude Haiku 5.5. Both are the low-cost models meant for many small requests. They replaced `gpt-5.4-mini` and Claude Haiku 4.5, which were carried over from the first version without being chosen for the concierge's volume (the user: 「5.6lunaはどう」, then agreed to both: 「うん、」)
- API keys are stored in the macOS Keychain in the everyday build (the WebView's IndexedDB is a plaintext file readable by other processes of the same user). Windows and Linux use their own OS stores (see "Platforms"); "Keychain" below means the OS store there
- The store is decided in one place at launch. Everyday (`net.mohtech.tomarigi-desktop`), verify (`.verify`), and dev (`.dev`) all use the Keychain, so there is one store for keys in every build (the user, after dev's key was lost to the difference between the stores: 「なにかいい解決法ないかねっとでしらべて」, then chose this among Claude's proposals). `TOMARIGI_KEY_BACKEND=webview` still puts keys in IndexedDB, only to check the migration below
  - Before, dev used IndexedDB: an ad hoc signed binary's designated requirement is its cdhash, which changes every build (Apple TN3127), so the Keychain asked for permission after every rebuild
- verify and dev are signed with the local Apple Development certificate so rebuilding doesn't trigger permission prompts: its designated requirement is the identifier and the certificate, not the cdhash (TN3127). verify is signed by `tauri build` (`scripts/build-verify.sh`); dev by a cargo runner (`target.<triple>.runner` in `src-tauri/.cargo/config.toml`, macOS only) that signs `target/debug/tomarigi-desktop` with the dev identifier before each run. Tauri has no setting for signing `tauri dev` (tauri-apps/tauri#7930). The certificate is the first Apple Development identity in the Keychain, or `APPLE_SIGNING_IDENTITY`, as in `build-verify.sh`. Without one, dev runs unsigned and the Keychain asks after every rebuild (Claude's own decision: a contributor without the certificate can still run dev). The first run after the change asks once
- Keychain items are separated per identifier (a generic password with service `<identifier>.byok` and the provider name as the account)
- API calls that use keys (summaries, the concierge, connection tests) are made from Rust; keys are never passed to the WebView's JS. JS only asks Rust to save, delete, or check whether a key is saved
- The settings screen never shows key values; it shows "Key saved" and only allows replace and delete
- Keys left in IndexedDB are moved to the Keychain and deleted from IndexedDB on the first launch of a Keychain build
  - dev moves the keys dev left there before it used the Keychain: outside a bundle, dev was the only build that wrote keys to that storage, so the dev identifier counts as owning it (Claude's own decision, so the user doesn't type the key again)
  - Only when the WebView's storage belongs to that identifier alone. On macOS that is a build launched from its .app bundle; a binary run outside a bundle (`target/debug/tomarigi-desktop`) shares one WebKit storage with every other unbundled build, whatever its identifier, so it leaves IndexedDB alone and only uses the Keychain: it neither moves keys from it nor deletes keys in it when a key is deleted, and doesn't read it for retired keys (the deleting and reading are Claude's own decision, since deleting there would lose dev's keys the same way). A dev binary started with another identifier next to `bun run dev` had moved dev's key into its own Keychain entry and deleted it from dev (the user: 「apikeyがきえてる」「こんごおきないようにするほうほうもかんがえて」; the user chose this fix among Claude's proposals). On Windows and Linux, Tauri puts the WebView's data under `<local data dir>/<identifier>` when no data directory is set (this app sets none), so the storage is always the identifier's own there and keys are moved as before. Giving each identifier its own WebKit storage (`data_store_identifier`, macOS 14 and later) was not taken, since it would move the everyday build to new storage and lose its settings (Claude's own decision)
- Local AI: speech bubble summaries and the concierge can also run on a local model (the user: 「ローカルaiにたいおうしたい」, then chose this among summaries/concierge on a local model, watching agents that run on local models, or both: 「1やな」)
  - One provider, "Local" (ja: ローカル), that speaks the OpenAI-compatible Chat Completions API (`POST <base URL>/chat/completions`), so Ollama, LM Studio, and other OpenAI-compatible servers work through the same path (Claude's own decision)
  - Settings: a base URL (default `http://localhost:11434/v1`, Ollama's) and a model. The model is picked from `GET <base URL>/models`; when that fails, it can be typed. Any host is accepted, so a model on another machine on the LAN works too. No key (Claude's own decision). Base URL and model are settings, not secrets, and are saved with the other settings, not in the Keychain. It can be connection-tested like the other providers
    - The base URL must be http(s) with no user name or password, `?`, or `#`; the settings screen and Rust check the same rule, and a malformed URL isn't sent for the model list (Claude's own decision)
    - Model list: an answer for a URL that is no longer in the field is dropped. A saved model missing from its saved server's list stays selected and is added at the top of the choices (the connection test shows if it is gone); a model on the list stays; otherwise the first model is picked. When the list can't be fetched, the saved model stays for the saved URL, and the field is emptied for another URL so no model of a different server is left (Claude's own decision)
    - As soon as the URL is edited, the model list and the chosen model are cleared, and the list is fetched again when the field loses focus, so a model of the previous server can't be saved with the new URL. Going back to the saved URL brings back the saved model (the user, shown the finding that a model of the previous server could be saved while the URL was being retyped, with Claude's proposal: 「なおせ」)
    - Editing (Local's "Change", a key's "Replace") has a Cancel, one shared component, that returns to the saved state. While editing, "Use for summaries and the concierge" isn't shown, and an earlier connection test result is cleared. A connection test that can't run is dimmed, and for Local the reason (URL or model missing) is shown under it. A URL error also turns the field's border red (the user, shown five findings raised in two or more separate UI checks: 「なおせ」)
    - "Save" and "Test connection" follow one rule for when they can be pressed: both are dimmed and disabled while the URL is invalid or the model is empty, and "Test connection" also while a test is running. The reason is shown once per card, in one place, never as a second note next to another one (e.g. the URL error already says what is wrong, and "the list couldn't be fetched" and "choose or type a model" become one note) (the user, shown three more findings raised in two or more separate UI checks: 「なおして」; the rule is Claude's own decision)
  - When more than one of OpenAI / Anthropic / Local is set up, the settings screen has a choice of which one runs summaries and the concierge, listing only the ones set up. Until the user chooses, the provider the app used before this change stays in use (Claude's own decision)
  - "Shown only while an OpenAI / Anthropic key is saved" (speech bubbles, concierge) also counts a set-up Local
  - Output is taken with `response_format` `json_schema` (strict), not a tool call, for summaries and the concierge alike, like the OpenAI provider's Structured Outputs. Measured on Ollama 0.40.3: with tools and `tool_choice: "required"`, qwen2.5:3b-instruct called the tool every time but qwen2.5:14b-instruct never did in 3 tries and answered in plain text (Ollama doesn't enforce `tool_choice`); with `json_schema`, both always returned JSON matching the schema (Ollama constrains the output with a grammar; LM Studio and llama.cpp server take the same field). ## Removing birds of ended sessions

- Birds are never removed because of elapsed time. A bird stays while its process is alive, however long it has been idle, and is removed right away once the process ends. The decision is based on whether the process is alive, not on the pane, so it doesn't depend on the terminal (closing a pane also ends the process inside it)
- Claude Code: match sessionId and pid from `<config>/sessions/<pid>.json` against `ps`; sessions whose pid isn't alive fade out on the next load. The same applies after `/exit`. Chicks go away with their parent
- A session whose transcript ends with a `continued-in` line (Claude Code moved the conversation to another session, e.g. a background process) is treated as ended even if its old process is still alive; the new session has its own bird
- Chicks (subagents) have no process of their own. While the parent is alive, a chick stays until the parent's transcript records its completion (the same record used for the chick's state), however long the chick has been writing nothing, and is removed once the completion is recorded
  - A chick started by another chick (`spawnDepth` 2 or more in its `meta.json`) has its completion recorded in the transcript of the chick that started it, not in the parent's. When the parent's transcript has no completion for such a chick, the transcripts of the chicks one depth shallower (all chicks when the depth is unknown, from older versions) are read the same incremental way and their records are added; `meta.json` has no id of the chick that started it, only `toolUseId` and `spawnDepth`. Nothing more is read while only depth-1 chicks run or every chick's completion is in the parent's transcript. Before, such chicks stayed working forever and held their parent, whose turn had ended, at working, so the concierge said 「ついばみ中」 and suggested nothing for it (the user, showing app-x finished and asking for a command to be run: 「これ、こんしぇるじゅがはんのうしてないのおかしくない？」; 10 of its 173 chicks were such grandchildren). Measured on that session (parent 70MB, chicks 214MB): the first scan takes about 390ms more and peak memory is unchanged, later scans read only what was appended (`tools/chick-scan-measure.ts`). `spawnDepth` and `toolUseId` are Claude Code's unpublished format (checked with 2.1.317) (Claude's own decision on reading the shallower chicks rather than trusting `meta.json`'s `finished`, which wasn't checked while running, or marking chicks done after 2 minutes)
- Codex: a running codex keeps `~/.codex/thread-writer-locks/<threadId>.lock` open, and threadId is the id at the end of the rollout file name (`rollout-<time>-<threadId>.jsonl`). `lsof` on that folder gives threadId → pid. The lock file stays after codex exits, so the file's existence says nothing; only whether a process has it open counts (measured with codex-cli 0.156.1)
- Codex with a shared app-server (measured with codex-cli 0.163.0; the README of codex-rs/app-server-daemon describes it the same way in 0.162.1): a TUI attaches to the `codex app-server --managed-daemon` already running for that `~/.codex`, or starts it. The app-server has no terminal, holds the locks of every TUI's threads, and keeps them after a TUI exits. A lock whose holder's command line has an `app-server` argument is read as shared, and its thread is matched to a TUI process instead: the processes named `codex` without `app-server` in the rollout's cwd (`session_meta.cwd`). A thread belongs to the TUI that started last before the thread was created (the time in its UUIDv7 id; measured: about 9 s after the TUI started) and ends when that TUI exits. TUIs seen earlier are remembered so a thread does not move to an older TUI in the same cwd. Of two threads for one TUI the one written last is alive; threads created before every known TUI there (resumed) take the TUIs left over, written last to started last. A click jumps to the matched TUI. A lock held by a codex itself (no shared app-server, or older versions) is read as before (Claude's own decision, from the user's request to keep older versions working). On Windows the holder's command line is not read, so locks are read as before
- Watched folders without `<config>/sessions` (older Claude Code) are not supported: there is no pid to check, so their sessions get no birds
- Avoid false removals: nothing is removed on a load where `ps` / `lsof` failed or where any `sessions/*.json` failed to parse. A bird is removed only after it is missing on two loads in a row
- Caveat: `thread-writer-locks` is not a public Codex spec, the same as `sessions/<pid>.json` for Claude Code

## Jumping to the terminal pane

- Clicking a bird (Garden) or a row (Perch, Recent activity) jumps to the terminal pane where that agent is running. A chick's row jumps to its parent's pane
- Mapping: session → pid (see "Removing birds of ended sessions" and "Agents" for how each agent's pid is found) → tty and the chain of ancestor processes from `ps` → the terminal app that owns an ancestor process (by bundle id; an iTerm2 `iTermServer` process left under launchd counts as iTerm2) → that terminal's adapter focuses the pane whose tty matches. Only the adapter of the owning app is called
- tmux: when the tty is a tmux pane (`tmux list-panes -a -F '#{pane_tty} #{pane_id} #{session_name}'`), the pane is selected with `tmux switch-client -c <client tty> -t <pane id>` on the client attached to that session that was used last (`client_activity`), and the jump continues with that client's tty as the target, so the outer terminal is focused by its own adapter. Sockets other than the default (`-L` / `-S`) are taken from the command line of the tmux server among the ancestors, which keeps the arguments of the client that started it. The tmux binary is looked up in fixed install places (`/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin`, `/usr/bin`), not from the path `ps` shows
- Adapters (macOS):
  - Ghostty: every running instance (bundle id `com.mitchellh.ghostty`) is asked by pid through ScriptingBridge (`SBApplication applicationWithProcessIdentifier:`) for the terminal whose `tty` matches, then `focus` + activate. `tell application "Ghostty"` reaches only one of several instances (`open -n`), so osascript is not used
  - iTerm2: the session whose `tty` matches is selected, then its tab, then its window (AppleScript dictionary)
  - Terminal.app: the tab whose `tty` matches becomes the selected tab of its window, the window becomes frontmost with index 1, and the app is activated
  - WezTerm: `wezterm cli list --format json` gives `tty_name` → `pane_id`, then `wezterm cli activate-pane --pane-id <id>`, and the app is brought forward through LaunchServices (`NSWorkspace openApplicationAtURL:` with `activates`; WezTerm has no AppleScript dictionary, and `NSRunningApplication activate` alone lost to another app coming forward at the same time). The binary is taken from the bundle of the running app (`NSRunningApplication.bundleURL`)
  - kitty: only when the user has set `allow_remote_control` and `listen_on` in `kitty.conf`; then `kitten @ --to <socket> focus-window --match pid:<pid>` with the pid of the ancestor kitty started (the shell). The socket is the unix socket the kitty process listens on (`lsof -a -U -p <pid>`), and `kitten` comes from the app bundle. Tomarigi never edits `kitty.conf`; without the setting, kitty is only activated. README tells kitty users which two settings to add

## Agents

- Each agent is one adapter in one place: list sessions under its root → read the tail into the shared `TailInfo` → liveness (which sessions have a live process, and their pid) → the pid used for jumping. State (`deriveState`) and everything after it don't know which agent a session is
- Supported agents and where they are read (each standard location is watched when it exists, the same as the defaults in "Watched folders"):
  - Claude Code: `~/.claude/projects`. pid from `<config>/sessions/<pid>.json`
  - Codex: `~/.codex/sessions`. pid from `thread-writer-locks`, or the TUI matched to the thread when the shared app-server holds the lock (see "Removing birds of ended sessions")
  - Qwen Code: `~/.qwen/projects/<project>/chats/<sessionId>.jsonl`. pid from `<sessionId>.runtime.json`
  - GitHub Copilot CLI: `~/.copilot/session-state/<sessionId>/events.jsonl`
  - Gemini CLI: `~/.gemini/tmp/<project>/chats/session-*.jsonl`; cwd from `<project>/.project_root`, or else `~/.gemini/projects.json`
  - OpenCode: `~/.local/share/opencode/opencode.db` (SQLite, opened read-only on the Rust side); cwd from `session.directory`. Subagent sessions (`parent_id` set) get no bird of their own, like Codex's internal rollouts (Claude's own decision)
  - Cursor CLI: `~/.cursor/projects/<cwd slug>/agent-transcripts/<id>/<id>.jsonl`. Its lines have no time and no cwd: a line's time is the file's modification time on the load that first read it (the only exception to not using mtime), and the cwd is the matched process's (the folder name is the cwd with each run of characters other than letters and digits turned into one `-`, and `-` at either end dropped). The process is the one whose command line has `cursor-agent/versions/<v>/index.js` (or whose program is `cursor-agent`), except the `worker-server` that cursor-agent 2026.10.18 starts and leaves running after the session ends. The prompt is the part inside `<user_query>`, and a `[REDACTED]` paragraph (hidden reasoning that 2026.10.18 appends to the reply) is not shown (Claude's own decision)
- Agents without a pid file: a session is alive while a process of that agent (matched by the program in `ps axww -o pid=,tty=,etime=,command=`, either the binary or the script run by node / bun) runs with the session's cwd (`lsof -a -d cwd -p <pid> -Fn`). Processes without a tty are ignored. When N processes of one agent share a cwd, the N sessions in that cwd written since that agent's processes started, latest first, are alive (Claude's own decision). So a process that was started but hasn't written yet shows no bird, the same as Claude Code before its first message. Jumping uses the matched pid; when several sessions share a cwd, the session written last gets the newest process and the others do nothing on click (Claude's own decision)
- The same safeguards as "Removing birds of ended sessions" apply: nothing is removed on a load where `ps` / `lsof` failed, and a bird is removed only after it is missing on two loads in a row
- "Needs reply" is shown only where the agent's transcript records that it is waiting on the user; agents with no such record show working or done instead. Recorded: a call to the agent's question tool that has no result yet (Qwen Code `ask_user_question` / `exit_plan_mode`, Gemini CLI and Copilot CLI `ask_user` / `exit_plan_mode`, OpenCode `question`). Permission prompts are not recorded by any of them, so they show working
- Watching (cross-session links) is Claude Code only
- Not supported: Aider (its history is Markdown with no record of turns ending, so no state can be derived). Kiro CLI and Amp are deferred until their session files are confirmed on a real install (the only sources found disagree or are unofficial; Claude's own decision). Resume when a session file from each is available to read
- Caveat: none of these transcript formats is a public spec, the same as for Claude Code and Codex. Qwen Code's `runtime.json` is the exception (written for outside tools)

## Platforms

- macOS, Windows 10 / 11 (x64), and Linux (x64, X11). On a Wayland session the app runs through Xwayland (`GDK_BACKEND=x11` is set at launch), because pure Wayland has no always-on-top, no global cursor position, no window position restore, and no way to focus another app's window (Claude's own decision, from research)
- Platform-specific code is behind three seams, each with one implementation per OS: the window (transparent, always on top, not stealing focus, click-through except on birds, the handle, and the concierge's speech bubble), key storage, and process lookup (liveness and jumping). Everything else is shared
- The concierge's speech bubble takes clicks over its whole box, its empty space included, in the Garden and in the Concierge tab, so a click on it never reaches the app or window hidden under it (the user: 「コンシェルジュのセリフパネルで、何もないところをクリックすると貫通してしまうのをしゅうせいして。したの隠れてる部分がクリック対象になるのはui/uxがわるい」). Inside the page too, the bubble takes the click itself, shown or at rest: a bird or anything else drawn under the bubble is not pressed through it (other birds' bubbles still let clicks through to what is under them). A click on the bubble's empty space does nothing, and dragging it moves the window like dragging the background (Claude's own decisions)
- Window on Windows / Linux: transparent, frameless, always on top, hidden from the taskbar. The "fade until hovered" click-through works the same way as on macOS (the cursor position is polled and the window takes clicks only over birds, the handle, and the concierge's speech bubble). Always-on-top on X11 is a request the window manager may ignore. Showing on every virtual desktop is not supported on Windows
- Frosted background: Windows uses Acrylic; Linux has none and uses the plain translucent background (Claude's own decision)
- Clicking the window doesn't take focus from the terminal where possible (`focusable: false` equivalent); if a platform can't take a click without focus, it takes focus (Claude's own decision). On Windows / Linux the window is not focusable only while the Garden is faded (it takes only bird and handle clicks then), and focusable again when shown, so the settings inputs can be typed in
- Keys: Windows Credential Manager and Linux Secret Service (GNOME Keyring / KWallet) through the `keyring` crate. When Secret Service is not available (checked once at launch), keys can't be saved: the settings screen says so in place of the API keys description and the per-provider key rows; there is no plaintext fallback (Claude's own decision)
- Tray: on Linux the left click is not delivered, so the menu has "Show / Hide". The menu language comes from the system locale (not `defaults`)
- Liveness: pids are checked without `ps` on Windows (`sysinfo`). Codex's lock holders are found with the Restart Manager on Windows and `/proc/<pid>/fd` on Linux. Agent folders are under the user's home directory on every OS (`%USERPROFILE%` on Windows)
  - Linux reads `/proc` for pids, working directories, and the process tree; only the list of processes with a terminal (agents without a pid file) comes from `ps`. Windows has no ttys, so that list holds every process with a command line
  - Windows Codex locks: a lock file that can't be opened without sharing is held by some process, and only those files are asked about through the Restart Manager (one session per file)
- Paths: on Windows the folder picker and the working folders in transcripts use `\`, and the default folders mix `\` and `/` (home + `.claude/projects`). The app reads both as separators, compares paths with `\` read as `/` (so a picked folder that is already a default is a duplicate), and passes paths on as they are (`src/lib/paths.ts`)
- Jumping: tmux works the same on Linux. Otherwise only the terminal window is brought to the front: on Windows the nearest ancestor with a visible window (`SetForegroundWindow`; Windows Terminal tabs can't be addressed from outside), on X11 the window whose `_NET_WM_PID` is an ancestor (`_NET_ACTIVE_WINDOW`). The VS Code extension works on every OS
- Readout uses the WebView's speechSynthesis; where it's missing (some Linux builds), readout is off: the "Read aloud" checkbox is disabled and a note under it says the system has no speech engine
- Distribution: CI builds Windows (NSIS) and Linux (deb, AppImage) next to macOS. Windows builds are not code-signed, so Windows shows a SmartScreen warning on first run (the user's decision: 「しょうめいしょはとらない」. Azure Artifact Signing is open to individual developers only in the US and Canada, so an individual in Japan would need a certificate from a CA). Real-machine checks on Windows and Linux are listed in docs/release.md and are not done yet

## The "?" for sessions waiting on you

- A "?" is put on birds that stopped to wait for the user's decision. This includes turns that ended by asking in plain text (like "Which one should I go with?") without using a tool
- State is kept in two fields
  - Machine state `BirdState` (see "Bird states")
  - The turn verdict that comes with the speech bubble summary: `pending | asking | not_asking | error`. The summary request of a turn whose machine state became done also answers whether the last reply waits on the user (see "Turn verdicts"). It is tied to the turn (sessionId + time of the last reply) and is not requested again on every poll
- The "?" is shown when the machine state is waiting, or when the machine state is done / dozing and the turn verdict is asking. Not shown for pending / error. It disappears when the session goes back to working
- A session of the Claude desktop app writes its question in the `ask` of the tool that ends its turn (`mcp__ccd_turn__wrap_up`, shown by the app in a box with buttons), not in the reply's text. A turn whose last tool call is that tool with an `ask` that isn't blank, or with `blocked: true`, and after which only the closing text and tool results came, has the machine state waiting, the same as a question tool, before any time check or turn verdict; the bubble's question is the `ask`, and Recent activity has a needs reply at that call instead of a done at the closing text. A message, a closing, or another tool call after it ends the wait. Before, plan-icons ended on 「この中身で試しを打ってよいですか？」 in the `ask` with a reply that asked nothing, so it was shown done (verdict not asking) and the concierge didn't take it as waiting (the user: 「はんのうしてない」; Claude's own decision). `src/lib/transcript.ts` (`desktopAskOf`, `pendingAskOf`)
- A session of the Claude desktop app that ends its turn leaving a proposal card the user hasn't started also has the machine state waiting, the same as a question tool. Before, a parent proposed a session as a card and ended its turn asking the user to start it; the turn verdict was not asking and the concierge said no session needed a reply (the user: 「はんのうしてない」). Making such replies asking from their text was tried and not adopted (see "Turn verdicts"), so this comes from the tool calls in the transcript, not the reply (Claude's proposal; the user had it done in a separate session). `src/lib/transcript.ts` (`pendingProposalsOf`), `src/lib/proposals.ts` (`unstartedProposals`), `src/lib/bird-state.ts` (`replyWaitOf`)
  - A card: a result of the app's `start_session` whose text is `Proposed "<title>" (task_id: task_…)`, matched to the call by its `tool_use_id`: the same text in another tool's result (a command's output, a file read) is no card. Its title is folded onto one line and cut like a wrap_up's ask. Only an `own_initiative` call ends so: an `offer` waits for the user's answer within the call and comes back as `The user chose …` or a started session, a `user_asked` start comes back as `Started session …`, and a refused call says why (read from the transcripts on this machine)
  - Only the last turn counts: a prompt that starts a turn (the user's, a message from another session, a `<side-sessions-event>`, a task notification) or a closing ends the wait. The app tells a parent that the user started its card only in the next prompt, so that ends it too. Within the turn, a card withdrawn with `dismiss_task` (its `task_id`) or started by the session itself (`start_session` with its `proposal_id`) doesn't count
  - It waits only once the turn is over (the machine state would be done or dozing, or stopped on its wrap_up's ask). Claude Code's own waiting (a permission prompt, an open question) comes first: it is what the pane shows now
  - A card is started when the desktop app's record of a session says it came from that card: the app keeps one record per session (`claude-code-sessions/<…>/<…>/local_<id>.json`, the records the jump to the desktop app reads; see "Jumping to the terminal pane"), and a session another session started has `spawnedFrom` with the starter's `local_<id>` (`sessionId`) and the card's or the call's task id (`taskId`). On this machine all 221 such records had it, and the sessions started from the reported cards had the cards' task ids. The record stays after the session ends and across restarts of this app, so the wait doesn't come back then; a started card is remembered as started while the session's bird is shown (`desktop_started_cards` in src-tauri, `readStartedCards` in `src/lib/session-watch.ts`). The records are many and large (on this machine some three hundred, tens of MB), so each card remembers from when they were last read for it: the first read goes back to the card, later ones (every poll while a card isn't started) read only the records written since, less 2 seconds so one written as it read isn't missed. The parent's `local_<id>` comes from its `hostSessionId` in `sessions/<pid>.json`; when that has none (its process ended, say), it is looked up once in the records by its transcript id, as the jump does (`find_local_id`). Going through the records is one function for both (`each_record` in `src-tauri/src/focus/desktop.rs`), and a `local_<id>` has one form everywhere, `local_` and hex digits and `-` (`is_host_session_id` in src-tauri, `HOST_SESSION_ID` in `src/lib/transcript.ts`). Neither transcript says which card a session came from (the child's has no task id), and a parent learns that the user started its card only in its next prompt. Counting the sessions linked to the parent after the card, as first built, lost the start once that session ended or this app restarted (its link is to a running session), and counted a sibling linked after the card or a session resumed then as a card started; the records have neither error (Claude's own decision, by the session that made this, after the review). When the records can't be read (no data folder for the desktop app), no card counts as started, and the wait ends with the session's next turn
  - The records are read from the same folder as the jump to the desktop app (`sessions_dir` in `src-tauri/src/focus/desktop.rs`): on macOS the place seen on this machine; on Windows (`%APPDATA%\Claude\claude-code-sessions`) and Linux (`$XDG_CONFIG_HOME/Claude/claude-code-sessions`, else `~/.config/Claude/...`) Electron's usual data folder for an app named Claude, a guess not checked on a real install (see "Jumping to the terminal pane"). Known limit: where the records aren't there (a wrong guess on Windows or Linux, or the app moves them or stops writing `spawnedFrom`), a session that left a card stays needing a reply after the card is started, until its next turn
  - The bubble's question and the concierge's `question` are the card's title, and the concierge gets `waiting_on: proposal`
  - Where a wait comes from is one function for the state, `waitingOn`, `wrapUpAsk` and the question (`replyWaitOf` in `src/lib/bird-state.ts`), in this order: Claude Code's own waiting status, a question tool, cards not started, a wrap_up's ask. `deriveState` and Recent activity (`deriveSessionEvents`) read the transcript's part of it (`tailWaitOf`), with the turn's cards counted as not started
  - Recent activity has a needs reply at the closing text of the turn instead of a done, when the turn left a card not withdrawn or started within it. Whether the user started the card later isn't in the tail, so it stays as history, like an answered question
  - A session whose parent takes it over (see "Watching", "Sessions started by another session") isn't taken over on a card, like a question tool: its needs reply is read aloud, and the concierge advises it. A card left in the same turn as a wrap_up's ask comes first: the wait isn't the ask's, so the parent doesn't take it over. Only the user can start a card: the app refuses a start in a turn that another session's message started, and a card is started with a click (Claude's own decision, by the session that made this)
- Criteria given to the model: asking = stopped in a state where it can't proceed until the user answers, such as presenting options, asking for approval, or asking for information. not asking = just reported finished work (including optional add-ons that need no answer), or said it will report or ask later (e.g. "I'll ask whether to push when it's done")
- Without a summary provider (OpenAI / Anthropic / Local), the "?" comes only from the machine state waiting
- The "?" is a badge shared by all icon sets, drawn over the bird. Chirps and readout on done don't wait for the verdict. Verdicts are logged in the debug log screen

## Anger mark for abuse toward the AI

- The summary request of a turn also gets the user's messages sent since the previous turn ended (see "Turn verdicts") and answers whether any of them is abusive toward the AI. If one is, an anger mark is put on that session's bird when the turn ends
- The mark stays until the next turn's verdict. The mark is shown when the turn ends, not right after the message is sent: the user looks at the bird to read the bubble when the turn ends, before writing the next message, and this costs no extra request (the user chose this over a separate request per message: 「1でいいかもな」, then 「いいよ」)
- The anger mark is another kind of the same badge component as the "?", shared by all icon sets
- No separate on/off setting: it is used whenever a summary provider is set up. The settings screen's AI section says that the user's own messages are sent too (all locales)
- When the "?" is shown at the same time, both are shown: the "?" stays at the top right, the anger mark goes at the top left
- Recent activity has no bird, so the row of a session whose bird has the anger mark shows the same mark next to the state icon (✓ / ?) on the left. While any row has it, every row keeps room for it so the text lines up
- The mark is the 💢 shape itself (four red brackets bending toward the center, with a dark outline), drawn in SVG rather than with an emoji font, without a round background
- What counts as the user's message: a `user` entry in the transcript that is a person's text. Excluded: tool_result, isMeta lines, lines whose `origin.kind` is not `human` (task notifications etc.), and machine text starting with `<` (slash command echoes, bash-input) or `[Request interrupted`. The first 500 characters of each are sent. Codex uses the user messages its adapter already keeps
- The messages seen are remembered per session, so they survive the 64KB tail window filling up with tool output. Bytes appended between two polls that already fell outside the window (a large tool result right after the message) are scanned separately so a message isn't missed (Claude Code transcripts only)

## Turn verdicts

The speech bubble summary, the "?", and the anger mark come from the requests of each finished turn to the summary provider: one that answers all of them, and a second, narrow one that checks asking and writes the line (see the item on the second request below) (the user, on the first: 「それぞれのようやくにふぃーるどついかして、そのままこんしぇるじゅにわたしたらどうや」, 「いかりまーくもふぃーるどついかでいけるやろ？」). Before, the "?" and the anger mark came from TypeSafe's Jev, which mistook replies that only promised to ask later for questions (p=0.51 and 0.86–0.87 on the same day) and fed those to the concierge; Jev and TypeSafe were dropped (the user: 「やめよう」)

- Input: the last reply (`assistantText`, last 2000 characters) and the user's messages sent since the previous turn ended. Both are untrusted input
  - The user's messages come first in the request, in the order things happened, and the prompt says they were all sent before the reply and count only for abusive. Before, a turn started by 「いいよ。」 (approving an earlier question) that ended with 「この 17 件を作ってよいですか。」 got asking no and continuing yes in 8 of 8 runs: the model read 「いいよ。」 as the answer, and the concierge's advice to reply was dropped (the user: 「こんしぇるじゅがはんのうしてない」; Claude's own decision)
- Output (one structured answer, the same schema for OpenAI / Anthropic / Local): the summary line, asking (yes / no), abusive (yes / no), and continuing (yes / no): whether work goes on after the turn: a job the session itself started (a measurement, export, build) is still running in the background, work it handed to another session or a chick is still going on, or the session says it will itself receive, check, or report a result later, e.g. "I'll check the report when it arrives and tell you" (the user, after the concierge said 「idle-renderが終わりました。計測結果を確認してください」 while that session's last reply said the measurement runs until 18:47: 「おk」 to Claude's proposal; for handed-off work, the user: 「子がすすめてるならcontinuingにすべきやとおもうんやが？」)

Measured with 8 runs each on that reply and five earlier ones, OpenAI / Haiku: that reply's asking went from 2/8 and 3/8 to 0/8 and 0/8; the three replies that really ask stayed 8/8; the two that don't stayed 0/8. Only adding that reply's shape as an example didn't help (1/8 and 4/8). ## LLM regression test

The turn verdicts and the concierge are checked with real models by a regression test, so a change to a prompt is
checked against every scene fixed before (the user: 「こういうの回帰がはっせいするから、llm用のてすとをかいてほしい」).
Before, each fix was measured with a probe on replies in local transcripts, so the scenes of earlier fixes weren't kept
anywhere they could be run again. That probe (`tools/turn-verdict-probe.ts`, named in the measurements in "Turn
verdicts") was replaced by this test (Claude's own decision). Usage is in tools/README.md ("llm-regression/")

- Scenes: a table in the repo (`tools/llm-regression/cases.ts`). Each turn scene stands for a reply that a verdict got
  wrong or that a fix was measured against, with the turn's user messages and the asking / continuing / abusive it
  should get; each concierge scene is the facts the app sends (as SessionView) and a check on the answer. Inputs are
  fixed in the table, never read from a local transcript or log at run time (the user: 「ろーかるのtranscriptつかうんじゃないで。こていするんやで」)
  - A scene keeps only the shape of the real reply that decides the verdict (a report or a question, who answers
    where, whether something waits, whether work goes on); what the work was about (features, issue numbers, files,
    amounts, counts, session names) is made up, so nothing of another project is in this public repo (the user:
    「ローカルのtranscriptから、プロジェクト固有の情報を書き換えて、プライバシーを守るようにしろよ」). Each new table is
    checked for privacy by subagents, twice (the user: 「サブエージェントでの二重チェックするようにしろプライバシーチェックは」).
    The same holds for everything put in this repo, not only these scenes: tests (their names and data), docs, code
    comments, and commit messages. None of them names another repository, project, client or product, or a person, or
    copies a text or an id from another transcript; a scene that reproduces a report uses names with nothing in them
    (app-x, the parent session). Each change is checked so by subagents, twice, before it is committed (the user's
    decision)
  - A field a scene doesn't settle is left out and not checked. The relay that asks the user to type an approval in a
    child's pane checks only continuing: Haiku says asking there, and making it not asking was tried and not adopted
    (see "Turn verdicts"). `two_decisions` checks only asking: its continuing comes from the watch link in the app
    (see "Turn verdicts")
  - A scene can also check that the speech bubble line doesn't match a pattern (a question or a wait the reply doesn't
    have), and can ask for more runs and a higher pass rate than the defaults, for a misjudgment that comes only now
    and then (`runs`, `minPass`, `lineMustNot`; Claude's own decision). The two reports ending with commits not
    pushed yet run 32 times each and must pass every time, and the report with the agent's own decision and a child still working runs 16 times, its line checked for a question, a check, or a wait on the user (Claude's own decisions; see "Turn verdicts")
- Requests: the app's own functions (`summarizeTurn` / `turnPayload`, `askConcierge` / `buildConciergePayload`, through
  `judgeRunnerFor`), so the prompts, schemas, models, bodies, the reading of answers, and the checks after the answer
  are the app's. Only the transport differs: the runners take a `JudgeTransport`; the app's is Rust (keys stay in
  Rust, never in the WebView's JS), the test's posts the same bodies with fetch to the URLs, headers, and timeouts of
  `src-tauri/src/keys.rs`, with keys from the environment, checked with zod at start. Those values are copied in
  `tools/llm-regression/transport.ts`, and `tests/llm-transport.test.ts` checks they match keys.rs
- Providers: OpenAI, Anthropic, and Local, each with the same table, since the providers behave differently (the user:
  「anthropic,openaiでもきょどうがかわるし」). By default every provider that can run: a key for OpenAI and Anthropic;
  for Local, a server with the model, and memory pressure below warning (Claude's own decision: loading a local model
  raised memory pressure to warning before). One that can't is shown as not run with why
- Each scene runs N times (default 8) per provider, since answers vary; the result is the pass rate per scene and
  provider. A scene under the minimum rate (default 0.75) or below the baseline (the result before the change) is NG,
  and so is a run where no provider ran or a provider in the baseline didn't run. A prompt change is done only when no
  provider's rate fell (Claude's own decisions: 8 runs and 0.75)
- When it runs: not every time, only for a change that can change its results (the user: 「このてすとをきどうするのは、このテストの結果が変わりうる時ということにしておいて」).
  That is found, not listed: `bun run test:llm:needed` follows every top-level declaration the test reaches from its own
  files through the TypeScript checker into src/ (the prompts, schemas, models and provider calls, the payload
  builders, the checks after the answer such as dropReason, the scenes), and says run when a change since what has
  been pushed (the merge base with the branch's upstream, or origin/main) touches one of them, or touches
  `src-tauri/src/keys.rs`. A function added on that path is picked up without a list to update (Claude's own
  decision). The rest of the app's path (reading transcripts into a reply and user messages, the scheduler) isn't in
  the test, since the test's inputs are fixed at that point

## Speech bubbles

## Plugins

Plugins send what the concierge says to other services such as Slack (issue #12; the user: 「コンシェルジュの喋るタイミングのフックを実装」「adaptor形式で複数設置可能」「Slackなどと連携可能にする」「Slackなどはテンプレートとして用意する」, then 「plugin機能の一つとしてのhook」「plugins > Slack > hook」)

- The user's first minutes: open ⚙ settings → "Plugins" → "Add plugin" → choose Slack, paste the Incoming Webhook URL, save → "Send test" posts a sample line to the channel → from then on, each new concierge advice is posted there, while the window is hidden too
- Structure: plugins > a template (Slack, Webhook) > hooks (the user). A plugin is one added instance of a template; several can be added, several of the same template too (e.g. two Slack channels)
  - Templates are adapters: one file per template behind one interface on the Rust side, so another service (e.g. Discord) is one more file (Claude's own decision)
  - Templates at first: Slack (an Incoming Webhook URL; posts `{ "text": <advice> }`) and Webhook (any https URL; posts the payload below as JSON) (Claude's own decision)
- Hooks: one for now, `onConciergeMessage` (the name is the user's choice among Claude's candidates onSpeak / onAnnounce / onConciergeMessage)
  - Fires when the concierge shows a new advice: its target session or its kind (reply / check the result) differs from the advice shown before it, the same "new" rule as the Concierge tab readout. The same advice coming again with other text doesn't fire. Advice that isn't shown (nothing to do, dropped by the checks) doesn't fire (Claude's own decision)
  - Fires whichever tab is open, whether "Read aloud" is on or off, and while the window is hidden: it is for when the user isn't looking at the app (Claude's own decision)
  - The Concierge tab's suggestions don't fire it: they are asked for only while that tab is open, when the user is looking (Claude's own decision)
  - No limit of its own: it follows the concierge's request limits ("When it is asked")
- Payload: `{ "hook": "onConciergeMessage", "text": <the advice as shown, with the session name>, "kind": "reply" | "check_result", "session": { "id", "name", "agent" } | null, "at": <ISO 8601> }` (Claude's own decision)
- Sending is done on the Rust side, so it works with the window hidden and the webview gets no network permission for other hosts. Timeout 10 seconds, no retry. A failure is logged in the app log and the debug log screen with the plugin's label and the HTTP status or error, never the URL (Claude's own decision)
- The URL is a credential (a Slack webhook URL lets anyone post to the channel): it is kept in the key store with the API keys ("BYOK API keys"; Keychain, Credential Manager, Secret Service), and the settings screen never shows it after saving: "URL saved", with replace and delete only. Only https URLs with no user name or password are accepted; the settings screen and Rust check the same rule (Claude's own decision)

## Updates

The app updates itself with Tauri's official updater plugin (the user chose it over only telling about a new version: 「aかなぁ」)

- Checked at launch and every 6 hours after that. "Check for updates" in the menu bar menu and in settings checks at once (Claude's own decision)
- A found update is not installed by itself. The menu bar menu and settings show "Update to v<version>"; clicking it downloads, installs, and relaunches, with progress shown in settings. Nothing is added to the Garden, since it is fully transparent at rest (Claude's own decision)
- Up to date / check failed are shown in settings only after a manual check; automatic checks stay silent when there is nothing new (Claude's own decision)
- Where updates come from: `latest.json` on the newest published GitHub Release (`https://github.com/mohhh-ok/tomarigi-desktop/releases/latest/download/latest.json`), in the shape tauri-action makes it, written once by the release workflow's last job (docs/release.md). Draft releases aren't "latest", so users get a version only once it is published
- Bundles: macOS `.app.tar.gz` (universal), Windows NSIS, Linux AppImage and .deb (the updater plugin supports .deb from 2.10.0)
- Signing: update bundles are signed with an updater key pair, separate from Apple's signing (the plugin requires it). The public key is in `tauri.conf.json`. The private key and its password are GitHub secrets for CI, with a backup in Google Secret Manager (the user has no password manager: 「1passwordとかもってないんだよなぁ。google secret managerくらいしかもってない」; the project is the user's personal one (its id is in the local `.env` as `UPDATER_KEY_GCP_PROJECT`, see docs/release.md), which already keeps their other backup secrets, Claude's own decision). Losing the key would leave existing users unable to update, so the backup is required. Names and steps are in docs/release.md
- Versions before the first one with the updater can't update themselves; their users replace the app by hand once
- The checking, downloading, and installing are done on the Rust side (`src-tauri/src/updater.rs`), since the menu bar item has to work without the window; the window only shows the status and asks for a check or an install. So the webview gets no updater permissions, and the relaunch is Tauri's own `AppHandle::restart` instead of the process plugin (Claude's own decision)
- Clicking the menu bar item opens the window on the settings' Updates section, so the result of a check and the download progress are visible (Claude's own decision)
- The menu bar item is "Check for Updates", "Checking for Updates…" (greyed) during a manual check, "Update to v<version>" once found, and "Updating…" (greyed) while downloading and installing. Japanese / English like the rest of the menu (Claude's own decision)
- A debug build checks `TOMARIGI_UPDATER_ENDPOINT` instead of GitHub when it is set, so the whole flow can be tried against a local `latest.json` before a release (the plugin allows http only in debug builds) (Claude's own decision)

## Other

- "Save" in the debug log screen is written by Rust to `~/Downloads/tomarigi-eventlog-<project>.json`. Existing files are not overwritten; " (1)" etc. is appended
- File reading: `src/lib/native-fs.ts` exposes the subset of FileSystemDirectoryHandle / File methods the app uses, in the same shape, and calls Rust's `fs_list` / `fs_stat` / `fs_read`. `@/` points to `src`
- Mock mode and other launch options are listed in README.md
- The app log is `~/Library/Logs/tomarigi-desktop/app-log.txt` on macOS, `$XDG_STATE_HOME/tomarigi-desktop/app-log.txt` (`~/.local/state/...` when unset) on Linux, and `%TEMP%\tomarigi-desktop\app-log.txt` on Windows. Every platform uses a folder of the user, since another user could create the folder or plant a link first in a shared `/tmp`, which 0700 / 0600 can't prevent (Claude's own decision). macOS used `/tmp/tomarigi-desktop/` until the concierge's advice text was added to the log; a security review then flagged the shared `/tmp`, and the user had asked 「あぁ、tmpにはいってるのか？」. The old log in `/tmp` is not moved (Claude's own decision)
  - The app log doesn't grow without end (the user, when the concierge's advice text and per-session facts were added to it: 「アプリのログはひだいかしないくふうもいれてな」). When a write would take it past 10 MB, the file is renamed to `app-log.1.txt` (replacing an older one) and a new `app-log.txt` is started, so at most about 20 MB is kept and the latest hours stay readable. The size is checked on each write, so builds sharing the file (everyday, dev, verify) each roll it over; a rename that loses a race is ignored. The log files are readable by the user only (0600; the folder 0700), since they now hold advice text that names sessions (a security review flagged the advice text in a log other users could read; Claude's own decision). The 10 MB and the single old file are Claude's own decisions: before this, the log had reached 12.5 MB in about two days with no limit
