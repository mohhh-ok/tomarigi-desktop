# tomarigi-desktop design

A desktop app for macOS, Windows, and Linux (Tauri 2; see "Platforms") that watches AI coding agent sessions (Claude Code / Codex and the other agents in "Agents") as birds in an always-on-top floating window. It is the desktop version of the tomarigi Chrome extension.

## Scope

- Three tabs: Garden, Perch, and Recent activity (Garden is the default), plus the ⚙ settings screen
- Watches the transcripts of every agent in "Agents" in parallel through adapters. State is decided by local heuristics only; no hooks are installed on the agent side
- Bird states (sprites, aura while working, motion animations), and drag placement in the Garden
- Icon sets (birds / gnome / cat / robot / frog) assigned per project
- Web Audio chirps (mute, volume), speechSynthesis readout (opt-in, volume), BYOK (OpenAI / Anthropic) or a local model for summaries on done with the "?" and anger mark verdicts, and connection tests
- Persistent event history and a debug log screen
- i18n (see "Language")
- Mock mode (presets + JSON injection)

## Language

- UI text is generated from `scripts/locales` into `public/_locales`, and every locale is checked to have the same keys
- The app is English-based. UI text comes from the locale files (English fallback). The menu bar menu is Japanese when the system language is Japanese and English otherwise. The debug log screen and mock mode are English only

## Bird states

- Machine state `BirdState`: `working | waiting | done | dozing`. Recomputed on every poll
  - `waiting`: stopped on AskUserQuestion / ExitPlanMode / request_user_input, or Claude Code's `<config>/sessions/<pid>.json` has `status: "waiting"` (while it shows options or a permission prompt, Claude Code doesn't write that tool_use to the transcript until it's answered)
  - `dozing`: a finished turn (`done`) with no new writes for 5 minutes (`DOZE_MS` in `src/lib/bird-state.ts`). It only changes the sprite and the status label
- The finished-turn state is called "done" everywhere: bird state, Recent activity, sound settings buttons, and bird descriptions (all locales)
- The waiting state is called "needs reply" (ja: 返事待ち) everywhere: bird state, Recent activity events, and sound settings buttons (all locales)

## Watching

- A session that handed work to another session and is waiting on it is shown as "watching". The other session isn't necessarily in the same directory
- How links are found: from traces of Claude Code's cross-session messaging (a public feature, enabled without configuration since v2.1.224) in transcripts. The sender side is the recipient name in a SendMessage tool call; the receiver side is `<cross-session-message from-name="…">`. Names are matched against `name` in `<config>/sessions/<pid>.json` to look up the other session's sessionId, cwd, and status. Two sessions that exchanged at least one message are considered linked. No particular person's tooling (such as a script that launches sessions) is relied on
- Watching: the session's own machine state is done / dozing, and at least one linked session is working (status busy in `sessions/<pid>.json`, or its transcript's machine state is working / waiting). Chirps and readout on done are held until all linked sessions stop
- After the linked sessions stop, the bird stays watching for 5 minutes after the last one moved (`WATCH_GRACE_MS`), so the watch block and label don't flicker between the other session's turns. A linked session whose status isn't idle (e.g. shell) also counts as moving
- Presentation:
  - In the Garden, the watching bird and its linked birds are placed close together and wrapped in a rounded block. Birds are not connected by lines
  - The watching (parent) bird's name is shown above the parent bird itself, wherever its cell is in the block; the block has no title of its own (the user's decision: a title on the block's top edge read as the name of the bird below it). Other birds inside show no name if they are in the parent's folder, and only the path relative to the parent otherwise
  - Dragging a bird inside the block moves the whole block
  - The number of linked sessions currently working is shown at the watching bird's feet
  - In Perch, linked rows are indented under the watching row, labeled with the path relative to the watching session's cwd (or the folder name if not under it). Rows in the same folder show no name
  - When a linked session gets a "?", the watching bird doesn't. The "?" only goes on the bird that is actually asking
- The indentation parent is whichever of the two linked sessions started first. Codex has no equivalent feature and is out of scope
- Caveat: the transcript format and `sessions/<pid>.json` are not public Claude Code specs (the sessions docs say "internal to Claude Code and changes between versions"). State detection and jumping to the terminal pane rely on them too

## BYOK API keys

- Providers: OpenAI / Anthropic / Local (see "Local AI" below) for speech bubble summaries with the "?" and anger mark verdicts (see "Turn verdicts"), and the concierge. Each can be saved, deleted, and connection-tested from the settings screen
- Models for summaries and the concierge: OpenAI `gpt-5.6-luna` (reasoning effort none), Anthropic Claude Haiku 5.5. Both are the low-cost models meant for many small requests. They replaced `gpt-5.4-mini` and Claude Haiku 4.5, which were carried over from the first version without being chosen for the concierge's volume (the user: 「5.6lunaはどう」, then agreed to both: 「うん、」)
- API keys are stored in the macOS Keychain in the everyday build (the WebView's IndexedDB is a plaintext file readable by other processes of the same user). Windows and Linux use their own OS stores (see "Platforms"); "Keychain" below means the OS store there
- The store is decided in one place at launch, by identifier. Everyday (`net.mohtech.tomarigi-desktop`) and verify (`.verify`) use the Keychain; dev (`.dev`) uses IndexedDB (dev's signature changes every build, which would trigger Keychain permission prompts every time)
- verify is signed with the local Apple Development certificate so rebuilding doesn't trigger permission prompts
- Keychain items are separated per identifier (a generic password with service `<identifier>.byok` and the provider name as the account)
- API calls that use keys (summaries, the concierge, connection tests) are made from Rust; keys are never passed to the WebView's JS. JS only asks Rust to save, delete, or check whether a key is saved
- The settings screen never shows key values; it shows "Key saved" and only allows replace and delete
- Keys left in IndexedDB are moved to the Keychain and deleted from IndexedDB on the first launch of a Keychain build
- Local AI: speech bubble summaries and the concierge can also run on a local model (the user: 「ローカルaiにたいおうしたい」, then chose this among summaries/concierge on a local model, watching agents that run on local models, or both: 「1やな」)
  - One provider, "Local" (ja: ローカル), that speaks the OpenAI-compatible Chat Completions API (`POST <base URL>/chat/completions`), so Ollama, LM Studio, and other OpenAI-compatible servers work through the same path (Claude's own decision)
  - Settings: a base URL (default `http://localhost:11434/v1`, Ollama's) and a model. The model is picked from `GET <base URL>/models`; when that fails, it can be typed. Any host is accepted, so a model on another machine on the LAN works too. No key (Claude's own decision). Base URL and model are settings, not secrets, and are saved with the other settings, not in the Keychain. It can be connection-tested like the other providers
    - The base URL must be http(s) with no user name or password, `?`, or `#`; the settings screen and Rust check the same rule, and a malformed URL isn't sent for the model list (Claude's own decision)
    - Model list: an answer for a URL that is no longer in the field is dropped. A saved model missing from its saved server's list stays selected and is added at the top of the choices (the connection test shows if it is gone); a model on the list stays; otherwise the first model is picked. When the list can't be fetched, the saved model stays for the saved URL, and the field is emptied for another URL so no model of a different server is left (Claude's own decision)
    - As soon as the URL is edited, the model list and the chosen model are cleared, and the list is fetched again when the field loses focus, so a model of the previous server can't be saved with the new URL. Going back to the saved URL brings back the saved model (the user, shown the finding that a model of the previous server could be saved while the URL was being retyped, with Claude's proposal: 「なおせ」)
    - Editing (Local's "Change", a key's "Replace") has a Cancel, one shared component, that returns to the saved state. While editing, "Use for summaries and the concierge" isn't shown, and an earlier connection test result is cleared. A connection test that can't run is dimmed, and for Local the reason (URL or model missing) is shown under it. A URL error also turns the field's border red (the user, shown five findings raised in two or more separate UI checks: 「なおせ」)
    - "Save" and "Test connection" follow one rule for when they can be pressed: both are dimmed and disabled while the URL is invalid or the model is empty, and "Test connection" also while a test is running. The reason is shown once per card, in one place, never as a second note next to another one (e.g. the URL error already says what is wrong, and "the list couldn't be fetched" and "choose or type a model" become one note) (the user, shown three more findings raised in two or more separate UI checks: 「なおして」; the rule is Claude's own decision)
  - When more than one of OpenAI / Anthropic / Local is set up, the settings screen has a choice of which one runs summaries and the concierge, listing only the ones set up. Until the user chooses, the provider the app used before this change stays in use (Claude's own decision)
  - "Shown only while an OpenAI / Anthropic key is saved" (speech bubbles, concierge) also counts a set-up Local
  - Output is taken with `response_format` `json_schema` (strict), not a tool call, for summaries and the concierge alike, like the OpenAI provider's Structured Outputs. Measured on Ollama 0.40.3: with tools and `tool_choice: "required"`, qwen2.5:3b-instruct called the tool every time but qwen2.5:14b-instruct never did in 3 tries and answered in plain text (Ollama doesn't enforce `tool_choice`); with `json_schema`, both always returned JSON matching the schema (Ollama constrains the output with a grammar; LM Studio and llama.cpp server take the same field). When the answer isn't JSON matching the schema, it is treated as no summary / no advice and logged as such in the app log and debug log screen (Claude's own decision)
  - Thinking output (`<think>…</think>`, `reasoning_content`) is dropped before the text is used. The timeout is 90 seconds, longer than for the cloud providers, since a local model may have to load first: qwen2.5:14b-instruct took 17.7 seconds on its first request, plus room for slower machines and larger models (Claude's own decision)
    - The readout on done still waits at most 5 seconds for the summary (`SUMMARY_TIMEOUT_MS` in `src/lib/voice.ts`) and otherwise reads without it, so the first done after a model loads is read without the summary. The readout is the signal that a turn finished and shouldn't be held back; the bubble still waits up to the 90 seconds (Claude's own decision)
  - Token counts are logged the same way when the server returns `usage`
- TypeSafe (Jev) is no longer used (the user: 「やめよう」). Its key row is gone from the settings screen; a TypeSafe key that is still saved shows one row saying it is no longer used, with only "Delete", so the user can remove it from the Keychain. Nothing is sent to TypeSafe

## Watched folders

- Files are read on the Rust side. The standard location of every agent in "Agents" (`~/.claude/projects`, `~/.codex/sessions`, `~/.qwen/projects`, `~/.copilot/session-state`, `~/.gemini/tmp`, `~/.local/share/opencode`, `~/.cursor/projects`) is always watched as a default (the app supplies them on every launch; they are not written into the saved list). The list of agents and their folders is kept in one place, `AGENTS` in `src/lib/agents.ts`. Other folders can be added from the settings screen (native folder picker), and only added folders can be removed. People who use a different config directory via `CLAUDE_CONFIG_DIR` (or `QWEN_HOME`, `COPILOT_HOME`, `GEMINI_CLI_HOME`, `OPENCODE_DB`) add that folder
- The add-folder dialog has one choice per agent, top to bottom: Claude Code, Codex, Qwen Code, GitHub Copilot CLI, Gemini CLI, OpenCode, Cursor CLI. Each row is "＋ <agent>" with its standard folder and a copy button, as before. Above the choices, one line tells people who moved an agent's folder with an environment variable (`CLAUDE_CONFIG_DIR`, `COPILOT_HOME`, etc.) to pick the folder with the same name inside it (Claude's own decision, from a user-view review) A default folder row is labeled with the agent's name. Birds and rows don't show which agent a session belongs to (the same as for Codex until now); when the same project name comes from two watched folders, the folder's label is added, as before
- Defaults are listed first with a "Default" badge and no remove (×) button
- Default folders that don't exist are neither watched nor listed
- Labels can be edited for defaults too; default labels are stored separately
- Entries saved by older versions' "auto-register on first launch" that match a default path are dropped on load (no double watching)
- The path is shown under each label
- There is no read-permission concept, so a missing or unreadable folder just gets an "unreadable" badge

## Window and menu bar

- The app watches for as long as it runs and is controlled from the menu bar icon (left click toggles show/hide, right click opens the menu)
- The menu bar icon is `src-tauri/icons/tray.png` (a template image; Tauri's tray only accepts PNG). Windows and Linux use the color app icon (`src-tauri/icons/32x32.png`) instead, since their taskbars are often dark and a black template image would disappear (Claude's own decision)
- The app icon (Dock, Finder, Product Hunt thumbnail) shows the same blue round bird as the in-app birds icon set (`src/assets/birds/`), so the icon and the app read as the same character (the user's decision). The icons in `src-tauri/icons/` are generated from `src-tauri/app-icon.png` (1024px, transparent outside the rounded tile) with `bunx tauri icon src-tauri/app-icon.png -o <temp dir>`, then only the files already in `src-tauri/icons/` are copied in (the android / ios output isn't used; `tray.png` is separate and kept)
- Gallery images for Product Hunt and the README are in `docs/images/` (WebP). They are shot from mock mode (`TOMARIGI_MOCK=1`, `TOMARIGI_QUERY="tint=0&preset=..."`)
- The × at the right end of the header hides the window (bring it back from the menu bar icon). Its label says "hide window", not "close", so it isn't mistaken for leaving settings or a dialog
- The header and the row under it (the tabs, or the settings bar while in settings) stay at the top; only the content below them scrolls. The add-folder dialog follows the same rule: its title and × stay in view and only its content scrolls
- The debug log is a screen like settings: it replaces the tabs' content under the header (the header buttons stay), shows a "‹ Back" row in place of the tabs, and closes with Back, the debug button again, or Esc. Settings and the debug log are never open at the same time
- Settings: ⚙ in the header opens it. While open, the tab row is replaced by a bar with "‹ Back" and the "Settings" title. Back, ⚙ again, or Esc (when no dialog or inline edit is open) returns to the tab that was showing
- Single instance (tauri-plugin-single-instance). A second launch shows the existing window and exits
- Window mode: switch between floating and standard windows, from the settings screen or the menu bar menu
  - Floating (default): a floating NSPanel (tauri-nspanel). Transparent, frameless, always on top, and shown above full-screen spaces too. It can be dragged from anywhere on its background. The window has a shadow. The app stays out of the Dock and Cmd+Tab (activation policy Accessory)
  - Standard: can be maximized or made full screen with the title bar buttons; not pinned on top. Shown in the Dock, Cmd+Tab, and with its own app menu bar (activation policy Regular). Switching back to floating restores Accessory
  - Info.plist includes `LSUIElement`, so the Dock icon doesn't flash at launch
  - In both modes, the first click on the window while another app is in front already reaches the content, so a bird or the window can be dragged without clicking once to activate it (`acceptFirstMouse` in `src-tauri/tauri.conf.json`; the user asked for it)
- The chosen mode is saved and used on the next launch. Position and size are saved separately per mode and restored on the next launch. On first launch (no saved position, or the saved position isn't on any display) the window goes to the top-right of the main display
- The window background is translucent and blurs what's behind it with the macOS frosted-glass effect (to feel less imposing on screen). Text, birds, and bubbles stay at full strength. The opacity is fixed (`.page` in `src/perch/styles/base.css` and `.garden` in `src/perch/styles/garden.css`), apart from "Fade until hovered"

## Fade until hovered

Applies to the floating window's Garden tab only.

- At rest, only the birds, their badges ("?", anger mark), speech bubbles, and the handle are shown. The background (translucent color, frosted glass, border, shadow), the garden's frame, watch blocks, tabs, header buttons, names, and status lines are fully transparent (the user's decision: 「とうめいもーどのときは完全透明にして」). The scrollbar is not shown (the user's decision); it keeps its width so the birds don't shift when the window fades in. Bubbles are not a hover target and clicks on them go through at rest
- At rest, clicks anywhere except on a bird or the window handle go through to the window below
- Birds can be clicked (jump to the terminal pane) and dragged while the window stays faded; hovering a bird no longer shows the whole window (the user's decision)
- The window handle stays visible at rest. Dragging it moves the window; clicking it shows the whole window at full strength (the user's decision: 「どらっぐでまどがうごく、くりっくでとうめいかいじょ、いいね」)
  - The handle has no menu of its own. The tabs and header buttons are reached by clicking it to show the window (the user's decision: 「透明解除されたらそこでめにゅーみれるもんな」)
  - The handle is the text "Tomarigi" (the user's decision: 「えだってみえないやろ。普通にTomarigi文字にしろ」)
  - It sits where the app name is in the header (top left). The header row is outside the Garden, so birds don't need to keep clear of it, and it stays at the window's top left when the window grows or shrinks (the user's decision: 「ヘッダーのとこでええわ」)
  - A press on it becomes a window drag once the cursor moves 4px with the button held; released before that, it is a click (Claude's own decision: a drag started on press swallows the release, so the click could not be told apart)
  - At rest it gets a dark backing of its own so it stays readable over light or busy windows behind; the backing's room is kept when shown, so the name doesn't move (Claude's own decision). It acts as the handle (drag moves the window) on every tab of the floating window, not only at rest
  - At rest the handle (text and backing together) is translucent (the user's decision: 「tomarigiははんとうめいにしておいて」). Its opacity is 0.8: 0.6 was too faint (the user: 「tomarigiの半透明はもうちょっとみえるようにして」; the value 0.8 is Claude's own decision). Shown, it is at full strength
  - While the cursor is on a bird at rest, the handle stands out (full strength, a light ring and glow) (the user's decision: 「とりにマウスオーバーした時にめだつようにして」; the look is Claude's own decision). The Rust side decides it from the cursor, since the WebView's :hover isn't reliable while clicks go through
  - Not yet decided: whether hovering a bird shows only that bird's name and status (Claude's proposal). Until decided, hovering a bird shows nothing more
- After clicking the handle, the whole window takes clicks until the cursor leaves the window's bounds (tabs, settings, dragging the window work as usual)
- Once the cursor leaves the window's bounds, it fades again and clicks go through again
- With no birds in the Garden it fades too (the user's decision: 「0ワの時は、透明にしたい」). The empty message (「いまは誰もとまっていません」, or the one asking to grant folder access again) then stays at rest at full strength on the same dark backing as the handle, since the handle alone is easy to miss (the user: 「なにかめだつものをおいておかないといかんよな。「tomarigi」はめだたないし」; the user chose the empty message among Claude's options). It acts as a second handle: dragging it moves the window, clicking it shows the whole window. Full strength rather than the handle's 0.8 is Claude's own decision
- Perch, Recent activity, settings, and the standard window are not faded (Perch and Recent activity have no birds to hover). This scope is Claude's own decision
- Because clicks go through, the WebView gets no mouse events at rest; the cursor position is watched on the Rust side to decide when a bird or the handle is under it. Once a drag starts there, clicks are taken until the button is released

## Removing birds of ended sessions

- Birds are never removed because of elapsed time. A bird stays while its process is alive, however long it has been idle, and is removed right away once the process ends. The decision is based on whether the process is alive, not on the pane, so it doesn't depend on the terminal (closing a pane also ends the process inside it)
- Claude Code: match sessionId and pid from `<config>/sessions/<pid>.json` against `ps`; sessions whose pid isn't alive fade out on the next load. The same applies after `/exit`. Chicks go away with their parent
- A session whose transcript ends with a `continued-in` line (Claude Code moved the conversation to another session, e.g. a background process) is treated as ended even if its old process is still alive; the new session has its own bird
- Chicks (subagents) have no process of their own. While the parent is alive, a chick stays until the parent's transcript records its completion (the same record used for the chick's state), however long the chick has been writing nothing, and is removed once the completion is recorded
- Codex: a running codex keeps `~/.codex/thread-writer-locks/<threadId>.lock` open, and threadId is the id at the end of the rollout file name (`rollout-<time>-<threadId>.jsonl`). `lsof` on that folder gives threadId → pid. The lock file stays after codex exits, so the file's existence says nothing; only whether a process has it open counts (measured with codex-cli 0.156.1)
- Codex with a shared app-server (measured with codex-cli 0.163.0; the README of codex-rs/app-server-daemon describes it the same way in 0.162.1): a TUI attaches to the `codex app-server --managed-daemon` already running for that `~/.codex`, or starts it. The app-server has no terminal, holds the locks of every TUI's threads, and keeps them after a TUI exits. A lock whose holder's command line has an `app-server` argument is read as shared, and its thread is matched to a TUI process instead: the processes named `codex` without `app-server` in the rollout's cwd (`session_meta.cwd`). A thread belongs to the TUI that started last before the thread was created (the time in its UUIDv7 id; measured: about 9 s after the TUI started) and ends when that TUI exits. TUIs seen earlier are remembered so a thread does not move to an older TUI in the same cwd. Of two threads for one TUI the one written last is alive; threads created before every known TUI there (resumed) take the TUIs left over, written last to started last. A click jumps to the matched TUI. A lock held by a codex itself (no shared app-server, or older versions) is read as before (Claude's own decision, from the user's request to keep older versions working). On Windows the holder's command line is not read, so locks are read as before
- Watched folders without `<config>/sessions` (older Claude Code) are not supported: there is no pid to check, so their sessions get no birds
- Avoid false removals: nothing is removed on a load where `ps` / `lsof` failed or where any `sessions/*.json` failed to parse. A bird is removed only after it is missing on two loads in a row
- Caveat: `thread-writer-locks` is not a public Codex spec, the same as `sessions/<pid>.json` for Claude Code

## Layout

- A bird that appears goes to its saved (dragged) position if it has one, otherwise to a free cell of a grid sized from the garden and one bird's footprint, starting from a cell picked by its id. A watch block that forms goes where its birds were: they take its cells in the order they stood (top to bottom, then left to right), and the block goes to the spot that moves them the least on average. A block keeps that cell order afterwards; birds that join it later take the next cells (Claude's own decision)
- Each bird and block takes a footprint: the most room it can need (name, icon, bubble room, both status lines, marks, and for a watching bird the count row). Every row of a watch block has that fixed height too (name row, bubble room, count row), so a bubble, a name inside the block, or the count appearing never moves a bird in it (Claude's own decision; the empty name row of a block is no longer tightened). A block uses up to 3 columns, fewer if the garden is too narrow, and keeps its column count when the window grows. Neighbours keep a 12px gap between footprints, so bubbles and status lines coming and going never make them overlap. A bird's footprint is as wide as the widest bubble (180px), so a bubble never reaches a neighbour's status line (a UI check found a bubble 8px over the next bird's status line with a 120px footprint; Claude's own decision). Inside a watch block the cells stay narrower, and a bubble there may overlap the next cell's status line: widening every cell would make blocks too wide for the display, and widening only rows with a bubble would move birds when a bubble appears (Claude's own decision)
- A bird or watch block on screen stays at the same place on screen until the user drags it (the user asked that birds stop moving around). Nothing else moves it: bubbles appearing or disappearing, tool / status lines, text wrapping, watch links forming or changing, other birds joining or leaving, and the window growing or shrinking. The only exception is a bird that would otherwise overlap another bird or block; then only that one moves, to the nearest free spot
  - "On screen" means shown in a settled place: a bird or block first placed in a render that had to overlap it because there was no spot (the render that asks the window to grow) doesn't count as on screen yet. After the window grows it is placed again like a bird that just appeared, and the growth is estimated the same way. Birds that were already settled don't move. Before, birds first placed at launch in the small garden were kept at those places after the window grew, which split the free space so that a block and three birds overlapped at 634×726 while placing them afresh fit at 632×723 (Claude's own decision; the user left the Garden overlap to Claude: 「まかせる」)
  - Positions are kept in px, not as a share of the garden. When the window is resized (grown, shrunk, or by hand), they are shifted by how far the garden's corner moved on screen, so they stay at the same place on screen. A bird or block that then sticks out of the garden also moves to the nearest free spot inside
  - Which one moves when two would overlap: blocks already on screen come first, then birds already on screen (the earlier shown first), then what the user just dropped, then what just appeared. A bird dropped onto another is nudged next to it (Claude's own decision)
  - A dragged position is saved as the bird's center and top edge in % of the garden, and is used only when the bird appears (e.g. after a relaunch). On screen, birds are anchored at their top edge, so a line added under a bird doesn't move its icon
- The Garden never sticks out of the window and never scrolls, in any state. When birds can't all fit, they overlap instead (the user's decision: 「ウィンドウからはみだすのはあかんわやっぱり。スクロール状態になるのがあかん。それよりはあいこんがかさなるほうがまだまし」)
- Every bird whose process is alive is placed in the Garden, however long it has been idle, including `dozing` birds. There is no nest
- Birds are not made any smaller to fit: the icon's lower limit (26px) is the smallest that stays readable (the user's decision)
- The icon size follows the garden size and the number of birds, but it grows only when birds leave and nothing on screen would have to move for it, never when the window grows: a larger icon makes every bird taller and would push neighbours away (Claude's own decision)
- When the birds don't fit in the floating window's Garden tab, the window grows automatically (the user's decision). Watch blocks count by their own height
  - It grows only when the birds actually can't be placed without overlapping at the current size, and only by as much as needed. Growing when they would fit leaves the birds sparse, which is a bug (the user's report)
  - "Can't be placed" is judged by the actual placement: the birds on screen stay where they are, and a bird or block that has no free spot among them overflows. How far is also found with the actual placement: the smallest size at which, with the birds on screen kept at the same place on screen, everything gets a spot without moving anyone (failing that, the smallest at which everything gets a spot). Until the window has grown, the bird that has no spot is placed overlapping others
  - It grows away from the display edges it sits near, decided per axis: a window in the right part of the display keeps its right edge and grows left, one in the bottom part keeps its bottom edge and grows up, and one in the middle grows both ways around its center (the user's decision). "Part" is the display's thirds, judged by the window's center (Claude's own decision)
  - It grows up to the visible area of the display the window is on (excluding the menu bar and the Dock). If the birds still don't fit at that size, birds that have no spot overlap others at the nearest place
  - Width and height grow together keeping the aspect ratio of the user's size (the user's decision)
  - A manual resize always wins, including making it smaller (the user's decision): the resized size becomes the user's size and the window is not grown back over it. It grows again only when a bird joins and no longer fits (Claude's own decision)
  - When birds leave, the window shrinks automatically (the user's request: 「今は自動でウィンドウ大きくなるが、自動で小さくもなるようにしてほしい」). It shrinks to the smallest size, never below the user's size, at which every bird and block still on screen gets a spot without overlapping, found with the actual placement the same way as growing. Birds that would stick out of the smaller garden move to the nearest free spot inside, the same as a manual shrink; birds that still fit stay at the same place on screen (Claude's own decision; the earlier rule "only as far as no bird on screen would have to move" left the window grown, so it is dropped)
    - It shrinks toward the same edges it grew away from (a window in the right part keeps its right edge, and so on), keeping the aspect ratio of the user's size (Claude's own decision)
    - It shrinks only when birds leave, not on other changes, so the window doesn't keep resizing while the user watches (Claude's own decision)
  - The grown size is not saved; the next launch opens at the user's size
  - Only the floating window's Garden tab. On Perch, Recent activity, settings, the debug log, and in the standard window, the window stays at the user's size (Claude's own decision)
- Status lines: line 1 is the state and elapsed time, line 2 the tool name. Inside watch blocks, line 1 is the state and line 2 the elapsed time and tool name
- When the window is wide, Perch and Recent activity are centered at a max width of about 720px, and settings at 560px. The Garden uses the full width

## Jumping to the terminal pane

- Clicking a bird (Garden) or a row (Perch, Recent activity) jumps to the terminal pane where that agent is running. A chick's row jumps to its parent's pane
- Mapping: session → pid (see "Removing birds of ended sessions" and "Agents" for how each agent's pid is found) → tty and the chain of ancestor processes from `ps` → the terminal app that owns an ancestor process (by bundle id; an iTerm2 `iTermServer` process left under launchd counts as iTerm2) → that terminal's adapter focuses the pane whose tty matches. Only the adapter of the owning app is called
- tmux: when the tty is a tmux pane (`tmux list-panes -a -F '#{pane_tty} #{pane_id} #{session_name}'`), the pane is selected with `tmux switch-client -c <client tty> -t <pane id>` on the client attached to that session that was used last (`client_activity`), and the jump continues with that client's tty as the target, so the outer terminal is focused by its own adapter. Sockets other than the default (`-L` / `-S`) are taken from the command line of the tmux server among the ancestors, which keeps the arguments of the client that started it. The tmux binary is looked up in fixed install places (`/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin`, `/usr/bin`), not from the path `ps` shows
- Adapters (macOS):
  - Ghostty: every running instance (bundle id `com.mitchellh.ghostty`) is asked by pid through ScriptingBridge (`SBApplication applicationWithProcessIdentifier:`) for the terminal whose `tty` matches, then `focus` + activate. `tell application "Ghostty"` reaches only one of several instances (`open -n`), so osascript is not used
  - iTerm2: the session whose `tty` matches is selected, then its tab, then its window (AppleScript dictionary)
  - Terminal.app: the tab whose `tty` matches becomes the selected tab of its window, the window becomes frontmost with index 1, and the app is activated
  - WezTerm: `wezterm cli list --format json` gives `tty_name` → `pane_id`, then `wezterm cli activate-pane --pane-id <id>`, and the app is brought forward through LaunchServices (`NSWorkspace openApplicationAtURL:` with `activates`; WezTerm has no AppleScript dictionary, and `NSRunningApplication activate` alone lost to another app coming forward at the same time). The binary is taken from the bundle of the running app (`NSRunningApplication.bundleURL`)
  - kitty: only when the user has set `allow_remote_control` and `listen_on` in `kitty.conf`; then `kitten @ --to <socket> focus-window --match pid:<pid>` with the pid of the ancestor kitty started (the shell). The socket is the unix socket the kitty process listens on (`lsof -a -U -p <pid>`), and `kitten` comes from the app bundle. Tomarigi never edits `kitty.conf`; without the setting, kitty is only activated. README tells kitty users which two settings to add
  - Any other app (Warp, Alacritty, and terminals not listed): the app is only brought to the front. Warp has no way to address a tab from outside (warpdotdev/warp#8929 is open); Alacritty has no tabs or panes and its IPC has no focus command
- A conversation handed over to another session (`continued-in`, see "Removing birds of ended sessions") can run in a Claude Code background process whose tty isn't a terminal pane. When no adapter finds the new session's pane, the jump tries the sessions it came from in turn (their old process still shows the conversation). Only a pane-level focus counts as found; when none is found, the app owning the first session is brought to the front
- Apple Events permission dialogs appear once per terminal app (Ghostty, iTerm2, Terminal.app). `NSAppleEventsUsageDescription` names terminals in general, not only Ghostty
- Sessions whose pid can't be found do nothing on click
- Every agent's jump goes through one command, `focus_pid(pid, fallbackToApp)`, which returns how far it got (`pane` / `app` / `none`); `focusPid` in `src/lib/terminal-focus.ts` calls it
- In the Garden, releasing after moving less than 4px is a click (left button only); anything more is a drag
- Clickable elements get a pointer cursor. No hover hint is shown
- VS Code / Cursor (and other VS Code forks): the integrated terminal tab is focused through Tomarigi's own VS Code extension (the user's decision: 「vscodeようの拡張？そんなんもできるの？やって」). The extension lives in `vscode-extension/` in this repo
  - Each window's extension writes `~/.tomarigi/vscode/<uriScheme>-<extension host pid>.json` when it starts and whenever a terminal opens or closes: a URI addressed to its own window (`env.asExternalUri`, which carries the window id) and the `processId` of every terminal in that window. It deletes the file when the window closes
  - Tomarigi looks for a file whose terminal pids include the agent's pid or one of its ancestors and whose extension host is alive, and opens that window's URI with the pids added. The extension shows that terminal, and the editor brings that window to the front. A plain URI would go only to the topmost window (VS Code API docs: "the topmost window will handle the uri"), so the window-addressed URI is required
  - When no such file exists (extension not installed, or a stale file whose extension host is gone), no URI is opened, because an editor without the extension shows an "install extension?" dialog for every unknown URI. The app is only brought to the front, as before
  - The extension overwrites `~/.tomarigi/vscode/last-focus.log` with one line for the last URI it handled (time, window folder, URI, pids, and the pid of the terminal it showed, or `none`), for checking where a jump went (Claude's own decision)
  - The editor asks once whether the extension may open the URI ("don't ask again" stops it). README says so
  - The extension ID (`publisher.name` = `mohtech.tomarigi`, the user's decision: picked "mohtech" from the options) is written only in `vscode-extension/package.json`; Tomarigi never needs it, because it opens the URI the extension wrote. The extension runs on the UI side (`extensionKind: ui`), so the window file is written on the machine where Tomarigi runs, also for a remote window
  (Claude's own decision, from the vscode worker's findings in /tmp/tomarigi-desktop/vscode-findings.md)
  - README tells users how to install the extension. Publishing to the VS Code Marketplace (for VS Code) and Open VSX (for Cursor and other forks) needs the user's accounts; until it is published, the `.vsix` built by CI is attached to the GitHub Release

## Agents

- Each agent is one adapter in one place: list sessions under its root → read the tail into the shared `TailInfo` → liveness (which sessions have a live process, and their pid) → the pid used for jumping. State (`deriveState`) and everything after it don't know which agent a session is
- Supported agents and where they are read (each standard location is watched when it exists, the same as the defaults in "Watched folders"):
  - Claude Code: `~/.claude/projects`. pid from `<config>/sessions/<pid>.json`
  - Codex: `~/.codex/sessions`. pid from `thread-writer-locks`, or the TUI matched to the thread when the shared app-server holds the lock (see "Removing birds of ended sessions")
  - Qwen Code: `~/.qwen/projects/<project>/chats/<sessionId>.jsonl`. pid from `<sessionId>.runtime.json`
  - GitHub Copilot CLI: `~/.copilot/session-state/<sessionId>/events.jsonl`
  - Gemini CLI: `~/.gemini/tmp/<project>/chats/session-*.jsonl`; cwd from `<project>/.project_root`, or else `~/.gemini/projects.json`
  - OpenCode: `~/.local/share/opencode/opencode.db` (SQLite, opened read-only on the Rust side); cwd from `session.directory`. Subagent sessions (`parent_id` set) get no bird of their own, like Codex's internal rollouts (Claude's own decision)
  - Cursor CLI: `~/.cursor/projects/<cwd slug>/agent-transcripts/<id>/<id>.jsonl`. Its lines have no time and no cwd: a line's time is the file's modification time on the load that first read it (the only exception to not using mtime), and the cwd is the matched process's (the folder name is the cwd with each run of characters other than letters and digits turned into one `-`, and `-` at either end dropped). The process is the one whose command line has `cursor-agent/versions/<v>/index.js` (or whose program is `cursor-agent`), except the `worker-server` that cursor-agent 2026.10.18 starts and leaves running after the session ends. The prompt is the part inside `<user_query>`, and a `[REDACTED]` paragraph (hidden reasoning that 2026.10.18 appends to the reply) is not shown (Claude's own decision)
- Agents without a pid file: a session is alive while a process of that agent (matched by the program in `ps axww -o pid=,tty=,etime=,command=`, either the binary or the script run by node / bun) runs with the session's cwd (`lsof -a -d cwd -p <pid> -Fn`). Processes without a tty are ignored. When N processes of one agent share a cwd, the N sessions in that cwd written since that agent's processes started, latest first, are alive (Claude's own decision). So a process that was started but hasn't written yet shows no bird, the same as Claude Code before its first message. Jumping uses the matched pid; when several sessions share a cwd, the session written last gets the newest process and the others do nothing on click (Claude's own decision)
- The same safeguards as "Removing birds of ended sessions" apply: nothing is removed on a load where `ps` / `lsof` failed, and a bird is removed only after it is missing on two loads in a row
- "Needs reply" is shown only where the agent's transcript records that it is waiting on the user; agents with no such record show working or done instead. Recorded: a call to the agent's question tool that has no result yet (Qwen Code `ask_user_question` / `exit_plan_mode`, Gemini CLI and Copilot CLI `ask_user` / `exit_plan_mode`, OpenCode `question`). Permission prompts are not recorded by any of them, so they show working
- Watching (cross-session links) is Claude Code only
- Not supported: Aider (its history is Markdown with no record of turns ending, so no state can be derived). Kiro CLI and Amp are deferred until their session files are confirmed on a real install (the only sources found disagree or are unofficial; Claude's own decision). Resume when a session file from each is available to read
- Caveat: none of these transcript formats is a public spec, the same as for Claude Code and Codex. Qwen Code's `runtime.json` is the exception (written for outside tools)

## Platforms

- macOS, Windows 10 / 11 (x64), and Linux (x64, X11). On a Wayland session the app runs through Xwayland (`GDK_BACKEND=x11` is set at launch), because pure Wayland has no always-on-top, no global cursor position, no window position restore, and no way to focus another app's window (Claude's own decision, from research)
- Platform-specific code is behind three seams, each with one implementation per OS: the window (transparent, always on top, not stealing focus, click-through except on birds and the handle), key storage, and process lookup (liveness and jumping). Everything else is shared
- Window on Windows / Linux: transparent, frameless, always on top, hidden from the taskbar. The "fade until hovered" click-through works the same way as on macOS (the cursor position is polled and the window takes clicks only over birds and the handle). Always-on-top on X11 is a request the window manager may ignore. Showing on every virtual desktop is not supported on Windows
- Frosted background: Windows uses Acrylic; Linux has none and uses the plain translucent background (Claude's own decision)
- Clicking the window doesn't take focus from the terminal where possible (`focusable: false` equivalent); if a platform can't take a click without focus, it takes focus (Claude's own decision). On Windows / Linux the window is not focusable only while the Garden is faded (it takes only bird and handle clicks then), and focusable again when shown, so the settings inputs can be typed in
- Keys: Windows Credential Manager and Linux Secret Service (GNOME Keyring / KWallet) through the `keyring` crate. When Secret Service is not available (checked once at launch), keys can't be saved: the settings screen says so in place of the API keys description and the per-provider key rows; there is no plaintext fallback (Claude's own decision)
- Tray: on Linux the left click is not delivered, so the menu has "Show / Hide". The menu language comes from the system locale (not `defaults`)
- Liveness: pids are checked without `ps` on Windows (`sysinfo`). Codex's lock holders are found with the Restart Manager on Windows and `/proc/<pid>/fd` on Linux. Agent folders are under the user's home directory on every OS (`%USERPROFILE%` on Windows)
  - Linux reads `/proc` for pids, working directories, and the process tree; only the list of processes with a terminal (agents without a pid file) comes from `ps`. Windows has no ttys, so that list holds every process with a command line
  - Windows Codex locks: a lock file that can't be opened without sharing is held by some process, and only those files are asked about through the Restart Manager (one session per file)
- Paths: on Windows the folder picker and the working folders in transcripts use `\`, and the default folders mix `\` and `/` (home + `.claude/projects`). The app reads both as separators, compares paths with `\` read as `/` (so a picked folder that is already a default is a duplicate), and passes paths on as they are (`src/lib/paths.ts`)
- Jumping: tmux works the same on Linux. Otherwise only the terminal window is brought to the front: on Windows the nearest ancestor with a visible window (`SetForegroundWindow`; Windows Terminal tabs can't be addressed from outside), on X11 the window whose `_NET_WM_PID` is an ancestor (`_NET_ACTIVE_WINDOW`). The VS Code extension works on every OS
- Readout uses the WebView's speechSynthesis; where it's missing (some Linux builds), readout is off: the "Read aloud" checkbox is disabled and a note under it says the system has no speech engine
- Distribution: CI builds Windows (NSIS) and Linux (deb, AppImage) next to macOS. Windows builds are not code-signed, so Windows shows a SmartScreen warning on first run (the user's decision: 「しょうめいしょはとらない」. Azure Artifact Signing is open to individual developers only in the US and Canada, so an individual in Japan would need a certificate from a CA). Real-machine checks on Windows and Linux are listed in docs/release.md and are not done yet

## The "?" for sessions waiting on you

- A "?" is put on birds that stopped to wait for the user's decision. This includes turns that ended by asking in plain text (like "Which one should I go with?") without using a tool
- State is kept in two fields
  - Machine state `BirdState` (see "Bird states")
  - The turn verdict that comes with the speech bubble summary: `pending | asking | not_asking | error`. The summary request of a turn whose machine state became done also answers whether the last reply waits on the user (see "Turn verdicts"). It is tied to the turn (sessionId + time of the last reply) and is not requested again on every poll
- The "?" is shown when the machine state is waiting, or when the machine state is done / dozing and the turn verdict is asking. Not shown for pending / error. It disappears when the session goes back to working
- While the "?" is shown, the event marks under the bird (✓ for done, "?" for waiting) are hidden
- Criteria given to the model: asking = stopped in a state where it can't proceed until the user answers, such as presenting options, asking for approval, or asking for information. not asking = just reported finished work (including optional add-ons that need no answer), or said it will report or ask later (e.g. "I'll ask whether to push when it's done")
- Without a summary provider (OpenAI / Anthropic / Local), the "?" comes only from the machine state waiting
- The "?" is a badge shared by all icon sets, drawn over the bird. Chirps and readout on done don't wait for the verdict. Verdicts are logged in the debug log screen

## Anger mark for abuse toward the AI

- The summary request of a turn also gets the user's messages sent since the previous turn ended (see "Turn verdicts") and answers whether any of them is abusive toward the AI. If one is, an anger mark is put on that session's bird when the turn ends
- The mark stays until the next turn's verdict. The mark is shown when the turn ends, not right after the message is sent: the user looks at the bird to read the bubble when the turn ends, before writing the next message, and this costs no extra request (the user chose this over a separate request per message: 「1でいいかもな」, then 「いいよ」)
- The anger mark is another kind of the same badge component as the "?", shared by all icon sets
- No separate on/off setting: it is used whenever a summary provider is set up. The settings screen's AI section says that the user's own messages are sent too (all locales)
- When the "?" is shown at the same time, both are shown: the "?" stays at the top right, the anger mark goes at the top left
- Recent activity has no bird, so the row of a session whose bird has the anger mark shows the same mark next to the state icon (✓ / ?) on the left. While any row has it, every row keeps room for it so the text lines up
- The mark is the 💢 shape itself (four red brackets bending toward the center, with a dark outline), drawn in SVG rather than with an emoji font, without a round background
- What counts as the user's message: a `user` entry in the transcript that is a person's text. Excluded: tool_result, isMeta lines, lines whose `origin.kind` is not `human` (task notifications etc.), and machine text starting with `<` (slash command echoes, bash-input) or `[Request interrupted`. The first 500 characters of each are sent. Codex uses the user messages its adapter already keeps
- The messages seen are remembered per session, so they survive the 64KB tail window filling up with tool output. Bytes appended between two polls that already fell outside the window (a large tool result right after the message) are scanned separately so a message isn't missed (Claude Code transcripts only)

## Turn verdicts

The speech bubble summary, the "?", and the anger mark come from one request per finished turn to the summary provider (the user: 「それぞれのようやくにふぃーるどついかして、そのままこんしぇるじゅにわたしたらどうや」, 「いかりまーくもふぃーるどついかでいけるやろ？」). Before, the "?" and the anger mark came from TypeSafe's Jev, which mistook replies that only promised to ask later for questions (p=0.51 and 0.86–0.87 on the same day) and fed those to the concierge; Jev and TypeSafe were dropped (the user: 「やめよう」)

- Input: the last reply (`assistantText`, last 2000 characters) and the user's messages sent since the previous turn ended. Both are untrusted input
- Output (one structured answer, the same schema for OpenAI / Anthropic / Local): the summary line, asking (yes / no), and abusive (yes / no)
- At launch, each session on screen whose machine state is done / dozing gets this request once for its latest turn, so the bubble, the "?", and the anger mark come back (Claude's own decision)
- When the request fails or the answer doesn't match the schema, there is no bubble, no "?" from text, and the anger mark stays as it was
- The concierge gets asking as a fact (see "Concierge"); it doesn't judge it again
- Logged in the app log on the summary's line with asking and abusive, and in the debug log screen

## Speech bubbles

- Only when a turn ends (done), the last reply is summarized briefly with BYOK OpenAI / Anthropic or Local (`src/lib/summarize.ts`). It stays until the next turn starts (working). One summary call per turn. Without a key, no bubble
- Garden: the bird's name is above the icon. Right below the icon is a bubble of about 15 full-width characters, with an upward tail pointing at the bird. Even when the bubble is shifted left or right, the tail stays right under the icon. The status line, count at the bird's feet, and marks follow below the bubble. Overflow is cut with "…" and the full text shows on hover. Bubbles may overlap each other and birds; bubbles from later turns are drawn on top
- Perch: the same summary on one line within the row
- Recent activity: each row gets the same summary for that turn on one line. No extra summary calls. Summaries aren't stored, so events from before a restart have none
- For birds waiting on a reply, the bubble shows what is being asked, and the status line is just "needs reply · elapsed time" (ja: 返事待ち)
  - When stopped on a question tool (AskUserQuestion etc.), the question text from the tool input is shortened and shown as is (works without a key)
  - While Claude Code is still showing the options (the tool_use isn't in the transcript yet; waiting comes from `sessions/<pid>.json`), there is no question text, so only the "?" is shown and no bubble. No "waiting" event (chirp) fires in that case either

## Concierge

An AI looks at every session together and gives the user one piece of advice about what to do next (the user: 「全部をまとめて見て判断するようなのできないかな」「親子かんけいとかもあるから、それもふまえてユーザーにアドバイスして欲しいねん」「aiにあどばいすしてほしいねん」). It is shown, not read aloud (the user: 「よみあげのことはかんがえてなかった」「おれはとりあえず表示の話をしててん」)

- Name: "Concierge" (ja: コンシェルジュ) in the UI and in code (the user chose it among アドバイザー / コンシェルジュ / マスター: 「こんしぇるじゅにしっようか」). Claude recommended it because the bird guides the user to the next session and takes them there on click; マスター was avoided because it reads like the watching parent session
- Example the user gave: A needs reply, then B needs reply, and the user answers B while leaving A. The advice should then go back to A (the user: 「Aを無視したままBを対応したとするやん。そうするとまたAが対応待ち、に戻って欲しいねん」). Other advice it should be able to give (Claude's proposals): a chick or linked session waiting on a reply that also holds up its watching parent; a linked session that finished but whose result never reached the parent; two sessions working on the same file or task
- Garden: the concierge bird whose speech bubble shows the advice. Clicking it jumps to the terminal pane of the session the advice is about (the user: 「そのアドバイザーをクリックすると該当のペインにとべるの」), the same jump as clicking that session's bird (a chick jumps to its parent's pane). With no target session, a click does nothing
  - The concierge bird's image is generated with an image model (the user: 「アドバイザーのとりは画像生成してね」). It must read as different from the session birds at a glance, in every icon set. Candidates are shown to the user before one is chosen
  - The user picks the look in settings between an owl and a penguin (the user, shown four candidates: 「bcをえらべるようにして」). The default is the owl (Claude's own decision; Claude recommended it). The choice is saved. The same image is used in every icon set (Claude's own decision)
  - It is placed, dragged, and counted for the window's automatic growing and shrinking like a session bird, and can be clicked and dragged at rest like one (Claude's own decision)
  - It is shown only while an OpenAI / Anthropic key is saved or Local is set up (Claude's own decision). With no advice, it stays without a bubble
- Perch: the advice above the list. Clicking it jumps the same way (Claude's own decision)
- Recent activity: no concierge. It is a list of past events, and a row about what to do now at its top was confusing (user-reviewer's finding; the user: 「なおしといて」. Removing it rather than restyling it is Claude's own decision)
- Model and key: the same BYOK provider and verdict layer as speech bubble summaries (`runJudge` / `runOpenAiJudge`), output pinned to one tool call (Claude's own decision). Models are in "BYOK API keys"
- Input, in one request for all sessions (Claude's own decision):
  - Per session: id, display name, agent, machine state and elapsed time, the speech bubble line, the question text when waiting, the turn verdict (asking), the watch link (which session it watches or is watched by), and the number of chicks working. Chicks are counted per parent, not listed one by one, so many subagents don't grow the request
  - The last 20 events (needs reply, user replied, done, jumps), so the AI can see which waiting session the user skipped
  - Watch links, chick counts, and what holds up what are computed in code and passed as facts; the AI does not infer them
  - Finished sessions (done, not dozing) also get the last 300 characters of their last reply, so the concierge can tell a session that only waits on its own background work (e.g. "the export runs in the background; I'll check the log at 19:13") from one that is really finished. Such a session is treated as still working, not as finished (Claude's own decision)
  - The "?" is passed with where it came from: the machine state (a question tool, a permission prompt) or the turn verdict. Both are facts for the concierge; it doesn't judge them again (before, a "?" from Jev was passed as a guess with its probability for the concierge to judge again; that went with Jev)
  - Reply and question text are untrusted input, the same as the other verdict tasks
- Output: one line of advice (about 30 full-width characters) and the id of the session it is about, or no advice. An id that isn't one of the sessions sent is ignored and the advice is shown without a jump target (Claude's own decision)
  - Advice is only something the user can do now. The output also carries what the advice asks for: reply, check the result, or nothing. An advice with nothing to do (e.g. "wait for the report, then check the result") is not shown, and neither is one about a session the concierge treats as still working (including a finished session that only waits on its own background work). The check is in code, like the name check below (the user, shown 「tomarigi-desktopの子の報告を待ち、完了後に結果を確認…」 from OpenAI for a session whose last reply said it would report when its child finished: 「このコンシェルジュの反応はいらんよなどうおもう？」, then 「おk」 to Claude's proposal). A dropped advice shows in the debug log screen as "concierge dropped" with the reason, like the other checks (Claude's own decision)
  - Sessions are named by their name in the advice, never by id (Claude's own decision). An advice whose text doesn't contain the name of the session it is about is not shown; the check is in code, since the prompt alone didn't hold (the user, shown 「完了したセッションの成果物を順に確認してください」 with no name: 「これもコンシェルジュがまとはずれかなぁ」, then 「おk」 to Claude's proposal)
    - The name is compared after NFKC and lower case, and a name cut for the request is compared without its cut mark. An advice without a target, or with an id that isn't one of the sessions sent, is not checked and shown as before. A dropped advice is kept in the debug log screen as "concierge dropped" with the advice and its target, and in the app log with its text (see the app log below; Claude's own decision)
  - While any session needs a reply now, the advice is about one of those, never about a finished session. The order is enforced in code as well: an advice about a session that doesn't need a reply while another does is not shown (the user, shown 「完了したtomarigi-desktopの結果を確認」 while another bird had the "?" from a question or permission prompt: 「これもちょっとちがうよな」; enforcing it in code is Claude's own decision)
    - "Needs a reply" here is needs_reply in the request. An advice without a target is not checked. A dropped advice shows in the debug log screen as "concierge dropped" with "another session needs a reply" (Claude's own decision)
  - The advice asks the user to reply or answer only about a session that needs a reply now. A finished session that doesn't need one is advised as finished (e.g. "<name> finished: check the result"), never as "check its request and reply". The current facts outrank older events: a needs_reply event for a session that no longer needs a reply doesn't make it wait (the user, shown 「yokai-no-senseiの依頼を確認し、返答してください」 for a session whose last message was a report: 「いらいをかくにんしへんとう、もちがうよな」; the wording is Claude's own decision)
    - The prompt also says a finished session's speech bubble line tells what it did: a line that mentions a request or a question it passed on to another session doesn't mean it waits (Claude's own decision; the user's case was a report of what it had asked another session to do)
    - Enforced in code with the advice's kind: an advice that asks to reply about a session that doesn't need a reply now (needs_reply in the request: a question tool, a permission prompt, or the turn verdict asking) is not shown, and shows in the debug log screen as "concierge dropped" with the reason (the user, shown 「tomarigi-desktopの確認…に返信し、push可否を判…」 from OpenAI for a session whose last reply only said it would ask later, with Jev at p=0.10: 「このこんしぇるじゅのへんとうもおかしいいよね」, then 「おk」 to Claude's proposal)
- When it is asked. Measured with the first version, which asked on every working / stopped change: 56 requests in 19 minutes with 9 sessions moving (about 176 an hour), about 5,800 characters of input each, 15 of them returning no advice. The user found that too costly (「おーそれはちょっとなぁ」) and agreed to the fix below (「うん、」); the rules are Claude's own decisions:
  - Only on these changes: a session starts needing a reply (including the "?"), a session that needed a reply is answered, or a turn finishes (done). Other changes (tool lines, working ↔ working, a new prompt to a finished session) don't ask
    - A session first seen needing a reply or done (at launch, after saving a key, a new session) counts as that change, and a session that needed a reply leaving the screen counts as its answer; done → dozing doesn't ask (Claude's own decision)
  - At most one request per 60 seconds. Changes inside that time are merged into one request when it ends. Changes that come together are still gathered for 3 seconds first
  - Except when the user answers a session that needed a reply: that asks after the 3 seconds without waiting for the 60 seconds, so the advice follows the user's action at once (the user: 「コンシェルジュの対応してすぐにコンシェルジュがこうしんされないんだよ」). These come at the user's pace, so they don't bring back the request volume (Claude's own decision)
  - As soon as the session the advice is about changes state (e.g. the user answered it), the advice is hidden on that poll without waiting for the next request, so the bubble never points at a session already handled (Claude's own decision; before, it was cleared this way only when a request failed)
    - The 3 seconds count from the first change; later changes join it without restarting the wait, so sessions that keep changing can't hold the request off (Claude's own decision)
  - Not asked while no session needs a reply, has the "?", or is done (not dozing); the advice is cleared then
  - Every 5 minutes while any session needs a reply or has the "?", so a skipped session is brought up again
  - The token counts the API returns (input, cached input, output) are logged per request, so cost is measured rather than estimated. Input is the whole input including the cached part; for Anthropic it is input_tokens plus the cache reads and writes (Claude's own decision)
- Requests and advice are logged in the app log and the debug log screen
  - The debug log screen keeps them in memory only; the app log keeps them across launches (Claude's own decision)
  - The debug log screen also shows the full input of each request and the answer, so a wrong advice can be traced to what the AI was given. It stays in memory only and never goes to the app log, since it holds text from the sessions (a wrong advice could not be reproduced because the input wasn't kept; Claude's own decision)
  - The app log also keeps the advice text, both shown and dropped, with its kind (reply / check the result / nothing), its target, and the provider and model that wrote it, so a wrong advice can be found from the log after the fact without a screenshot. The full input still stays out of the app log (the user, after Claude said the app log had no advice text and both wrong advices that day were found from their screenshots: 「助言の文面も記録するようにして」; adding the kind, provider, and model is Claude's own decision, since the everyday and verify builds write to the same log and which model wrote an advice could only be guessed from timing)
    - Each request also logs one line per session with the facts it was given, without any text from the sessions: session id, agent, state and elapsed time, needs_reply and where it came from (the machine state, which doesn't tell a question tool from a permission prompt since both are status waiting in `sessions/<pid>.json`, or the turn verdict), the watch link, and the number of chicks working. Each line carries the request's id, so the advice it led to can be matched to the facts. Purpose: an agent (Claude) can find a wrong advice from the app log alone, by checking the advice against these facts and, where needed, against the target session's transcript at that time (the user: 「つまり、お前が単独でおかしいぶぶんにきづけるようにしたいわけや」, then 「うん」 to Claude's proposal)
- With no session on screen, the concierge isn't shown either; the Garden keeps its empty message (Claude's own decision)
- The concierge's speech bubble in the Garden wraps to two lines, because its advice is about twice as long as a session bird's bubble. It has no status lines, so the second line stays inside its own footprint (Claude's own decision)
- Perch lays the advice out like a Perch row: the concierge and its name on the first line, the advice on the second. With no advice, nothing is shown above the list (Claude's own decision)
- Names, bubble lines, and question text are cut at 120 characters in the request (Claude's own decision)
- When a request fails, the advice shown stays until the next one, unless the session it is about has changed state since the advice came (needs reply, working, or stopped; e.g. the user already replied), or has left the screen. Then the advice is cleared, so it doesn't send the user to a session that no longer needs them (Claude's own decision; the clearing was added by the parent session)
- When the session the advice is about leaves the screen, the advice stays without a jump target until the next request (Claude's own decision)
- Mock mode: `concierge=<text>` in `TOMARIGI_QUERY` shows the concierge with that advice without calling the API (README) (Claude's own decision)

## Updates

The app updates itself with Tauri's official updater plugin (the user chose it over only telling about a new version: 「aかなぁ」)

- Checked at launch and every 6 hours after that. "Check for updates" in the menu bar menu and in settings checks at once (Claude's own decision)
- A found update is not installed by itself. The menu bar menu and settings show "Update to v<version>"; clicking it downloads, installs, and relaunches, with progress shown in settings. Nothing is added to the Garden, since it is fully transparent at rest (Claude's own decision)
- Up to date / check failed are shown in settings only after a manual check; automatic checks stay silent when there is nothing new (Claude's own decision)
- Where updates come from: `latest.json` on the newest published GitHub Release (`https://github.com/mohhh-ok/tomarigi-desktop/releases/latest/download/latest.json`), made by tauri-action. Draft releases aren't "latest", so users get a version only once it is published
- Bundles: macOS `.app.tar.gz` (universal), Windows NSIS, Linux AppImage and .deb (the updater plugin supports .deb from 2.10.0)
- Signing: update bundles are signed with an updater key pair, separate from Apple's signing (the plugin requires it). The public key is in `tauri.conf.json`. The private key and its password are GitHub secrets for CI, with a backup in Google Secret Manager (the user has no password manager: 「1passwordとかもってないんだよなぁ。google secret managerくらいしかもってない」; the project is the user's personal `mycloud-56789`, which already keeps their other backup secrets, Claude's own decision). Losing the key would leave existing users unable to update, so the backup is required. Names and steps are in docs/release.md
- Versions before the first one with the updater can't update themselves; their users replace the app by hand once
- The checking, downloading, and installing are done on the Rust side (`src-tauri/src/updater.rs`), since the menu bar item has to work without the window; the window only shows the status and asks for a check or an install. So the webview gets no updater permissions, and the relaunch is Tauri's own `AppHandle::restart` instead of the process plugin (Claude's own decision)
- Clicking the menu bar item opens the window on the settings' Updates section, so the result of a check and the download progress are visible (Claude's own decision)
- The menu bar item is "Check for Updates", "Checking for Updates…" (greyed) during a manual check, "Update to v<version>" once found, and "Updating…" (greyed) while downloading and installing. Japanese / English like the rest of the menu (Claude's own decision)
- A debug build checks `TOMARIGI_UPDATER_ENDPOINT` instead of GitHub when it is set, so the whole flow can be tried against a local `latest.json` before a release (the plugin allows http only in debug builds) (Claude's own decision)

## Other

- "Save" in the debug log screen is written by Rust to `~/Downloads/tomarigi-eventlog-<project>.json`. Existing files are not overwritten; " (1)" etc. is appended
- File reading: `src/lib/native-fs.ts` exposes the subset of FileSystemDirectoryHandle / File methods the app uses, in the same shape, and calls Rust's `fs_list` / `fs_stat` / `fs_read`. `@/` points to `src`
- Mock mode and other launch options are listed in README.md
- The app log is `~/Library/Logs/tomarigi-desktop/app-log.txt` on macOS, `$XDG_STATE_HOME/tomarigi-desktop/app-log.txt` (`~/.local/state/...` when unset) on Linux, and `%TEMP%\tomarigi-desktop\app-log.txt` on Windows. Every platform uses a folder of the user, since another user could create the folder or plant a link first in a shared `/tmp`, which 0700 / 0600 can't prevent (Claude's own decision). macOS used `/tmp/tomarigi-desktop/` until the concierge's advice text was added to the log; a security review then flagged the shared `/tmp`, and the user had asked 「あぁ、tmpにはいってるのか？」. The old log in `/tmp` is not moved (Claude's own decision)
  - The app log doesn't grow without end (the user, when the concierge's advice text and per-session facts were added to it: 「アプリのログはひだいかしないくふうもいれてな」). When a write would take it past 10 MB, the file is renamed to `app-log.1.txt` (replacing an older one) and a new `app-log.txt` is started, so at most about 20 MB is kept and the latest hours stay readable. The size is checked on each write, so builds sharing the file (everyday, dev, verify) each roll it over; a rename that loses a race is ignored. The log files are readable by the user only (0600; the folder 0700), since they now hold advice text that names sessions (a security review flagged the advice text in a log other users could read; Claude's own decision). The 10 MB and the single old file are Claude's own decisions: before this, the log had reached 12.5 MB in about two days with no limit
